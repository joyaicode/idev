# 根因分析的六条强约束

> 根因分析最危险的不是「没有答案」,而是**「给出一个听起来合理但无法验证的答案」**。

这页是那句话的机检版本。六条约束各自挡住一种「看起来对」的错法,
全部由 `hypothesis.py check` 与 `delegation.py` 执行。

---

## 一、六条

| 约束 | 挡什么 | 机检 |
|---|---|---|
| **服务名必须有来源** | 凭记忆说出一个服务名,然后围绕它推理一整轮 —— 而它可能不存在 | `facts-sourced` |
| **时间窗必须可追溯** | 把时间范围放宽到「正好能解释现象」,无关证据就卷进来了 | `window-without-source` |
| **调用链必须穿透** | 把中间服务的报错当根因 —— 它往往只是在转述上游的失败 | `root-cause-not-terminal` |
| **关键判断至少双证据** | 单一信号配上一个说得通的故事 | `proven-needs-two-sources` |
| **快照不等于根因** | 现象发生过 ≠ 解释了为什么 | `proven-needs-code-evidence` |
| **排除也要举证** | 排除了但没写依据,下一轮重走同一条路 | `disproven-needs-proof` |

### 服务名必须有来源

只能来自:**系统拓扑**(`codegraph_*`)· **工具返回** · **源码** · **用户输入**。

`FACTS:` 要点名是哪一类,不能只写一个名字。一个凭经验编出来的服务名,
是后面整条推理链的第一环 —— 而那一环是空的。

### 时间窗必须可追溯

只能来自**问题发生时间** / **告警时间** / **数据更新时间**。

```bash
python3 scripts/hypothesis.py set --feature <f> --id H1 \
  --window "2026-10-15T09:00..2026-10-15T09:30" --window-source "告警时间"
```

写了窗口却不说来源 → FAIL。**随意扩大时间窗**是把无关证据合理化的常见手法。

### 调用链必须穿透

原则上要追到**数据库 / 缓存 / 消息系统 / 第三方 / 明确的业务输入异常**。
**中间服务不能作为唯一根因。**

根因落在「某某服务返回空」这类描述上会给 WARN —— 它报错往往只是在转述上游。
确实追到底了,就在 `claim` 里写明是哪一类终端原因。

### 关键判断至少双证据

两类**互相印证**的证据:错误日志 × 监控异常、代码路径 × 配置变更、trace × 发布记录。
**单一信号只能标 `open`**,不能 `proven`。

识别的证据类型:`code`(file:line)· `log` · `metric` · `trace` · `config` ·
`change`(发布/变更/回滚)· `repro`(用例)。

### 快照不等于根因

一条日志证明**现象发生过**,不证明**为什么**。`proven` 必须有 `code` 级证据
(`file:line`)解释机制 —— 见 [boost.md](boost.md) 4.1 的证据分级。

### 排除也要举证

`disproven` 要写 `--note` 说明怎么排除的,或挂证据路径。没有依据的排除,
下一轮会重走这条路 —— 而**排除的记录正是为了阻止这件事**。

## 二、根因报告先回答三问

报告不是一篇推理,是三个答案 + 证据链:

| 问 | 字段 | 内容 |
|---|---|---|
| **根因是什么** | `claim` + `evidence` | 异常服务、根因类型、代码位置或配置项 |
| **影响是什么** | `impact` | 影响范围、异常时间窗、受影响业务或数据 |
| **建议怎么做** | `remedy` | 修复建议、验证方式、回滚或止损动作 |

后两项缺任何一项 → FAIL。**只说根因是什么,拿到它的人不知道下一步做什么。**

结构化输出比长篇推理更利于复核 —— 这也是为什么回报格式是字段,不是散文。

## 三、经验沉淀:候选 ≠ 权威

有效的排查路径和关键证据先成为**候选经验**,不直接入库。

```bash
python3 scripts/lessons.py add --feature <f> ...      # 记成候选(六问必答)
python3 scripts/lessons.py promote --id L1 \
  --by <人> --repro <复现证据>                         # 人确认 + 复现才入库
python3 scripts/lessons.py recall --scope <域>        # 下次排查前召回
python3 scripts/lessons.py retire --id L1 --why ...   # 过时就清
```

```
一次排查 → 候选经验 → 旁路复现 → 人工确认 → 入库复用
```

**一条可复用经验至少回答六个问题**,否则它只是过程日志:

| 问 | 字段 |
|---|---|
| 在什么范围内 | `scope`(系统 / 业务域 / 节点) |
| 什么现象下 | `symptom` |
| 依据哪些证据 | `evidence` |
| 采取什么动作 | `action` |
| 得到什么结果 | `outcome` |
| **何时不适用** | `not_when` —— 最常被跳过,而它正是边界 |

`not_when` 必填不是形式。**没有边界的经验会被用在它不成立的地方** ——
那正是一条正确经验变成错误经验的方式。

### 召回只给建议,不给答案

`recall` 输出的形状是「出现 X 时先核对 Y,若 Z 则不适用」,不是「原因就是 Y」。
用它的 Agent 仍要回到当前证据自己走一遍,六条强约束照常生效。

**一条短路掉证据链的经验,比没有经验更糟。**

### 门禁在读取时也校验

手工把 `candidate` 改成 `authoritative` 会被 `lessons.py check` 识破:
它重新验 `confirmed_by` 是不是人、`repro` 在不在。写入时的门禁挡不住绕过写入的人。

**为什么不能直接入库:** 错误的结论一旦进了经验库,会被后续分析反复引用 ——
一个错误变成一类错误。这条和本层既有的规矩同源:提案 → grill 拷问 → 人确认用语 → land,
见 [feedback-loop.md](feedback-loop.md) 第五节。

`ticket-metrics` 的「签字后被推翻次数」就是这条链没把住时的事后信号。

## 四、这些约束不保证什么

全绿只说明**答案是可验证的形状**,不说明它是对的。

一个满足六条约束的根因仍可能错 —— 两类证据可以同时指向一个巧合,
穿透到数据库也可能穿透错了那张表。所以:

**根因仍要用例证明** —— 在用户那条现象上红过、修完绿、`blast.guard` 保住邻居。
见 [boost.md](boost.md) 4.3。

机检挡住的是「听起来合理但无法验证」,人要挡的是「可验证但验错了」。
