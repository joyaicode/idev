# 双向反馈环:下游怀疑上游,订正后全线对准

交付不是单向流水线。**下游每一格都有资格质疑上游的需求是真是假、合理不合理** ——
越早发现越便宜,而发现之后要让全线重新对准同一个基准。

这页把已有的零件串成一条环,并指出哪些**已经有机器在查**。

---

## 一、为什么要双向

单向流水线的失效很具体:`req-review` 把需求密封了,后面每一格都按它做。
如果那条需求本身是错的 —— 它会被忠实地实现、忠实地测试、忠实地交付。

每一格的视角不同,**能看见上游看不见的东西**:

| 谁 | 能发现什么 | 上游为什么看不见 |
|---|---|---|
| `req`(拆解) | 这条 must 译不出可执行的 slice | 评审时它读起来很顺 |
| `arch`(架构) | 实现它要动三个不该动的契约 | 评审时不知道代码长什么样 |
| `code`(编码) | 代码里早有一条相反的规则 | 没人读过那段代码 |
| `test`(测试) | 验收标准无法证伪 | 写的时候以为很清楚 |
| `ops`(排障) | 线上现象说明前提就不成立 | 上线前没有真实流量 |

所以不是「下游不许质疑上游」,而是**质疑要走通道、要有依据**。

---

## 二、反馈通道:`baseline-conflict`

任何阶段发现需求有问题,**不自己改,写 `baseline-conflict` 并停**。

```
发现  →  标 baseline-conflict  →  停,回报 BLOCKED(logic)
                                      ↓
                        导体问人:基线内改实现,还是解封重评审?
                                      ↓
               ┌──────────────────────┴──────────────────────┐
         基线内改实现                                   人写 reopen_baseline
      (基线不动,改 req/arch/code)                      (回 req-review 重拷问)
```

**为什么 agent 不能自己改基线:** `deliver-schema.md` 原文「Agent 不得自行 unseal」。
基线是验收的尺;让被量的人改尺,这一格就没有意义了。

**反馈必须带依据。** 这是 `conventions/evidence.md` 的要求落到这里:
「我觉得这个需求不合理」不是反馈,「这条 must 和 `src/auth.py:resolve` 里已有的规则相反,
见那一行」才是。agent 回报里的 `FACTS:` 正是为此 ——
见 [boost.md](boost.md) 第零节。

### 两条路分别意味着什么

| 选哪条 | 什么情况 | 后果 |
|---|---|---|
| 基线内改实现 | 需求是对的,是实现/译法错了 | 回退 `req`/`arch`/`code`,**基线不动**,origin 之后的签字失效 |
| 解封重评审 | 需求本身错了 | `revision + 1`,**旧 id 的 slice / case 全部作废**,从 `req-review` 重走 |

`defect_origin` **不得**是 `req-review`,除非人已 `reopen_baseline` —— 这条防的是
「悄悄把需求改了当成实现缺陷修掉」。

## 三、订正之后:全线重新对准

需求一变,**所有已过阶段的产物都可能在指向一条不存在的需求**。最危险的一类:
一条 `PASS` 的 case 还挂在旧 item 上 —— 于是**新需求被旧证据验收**。

```bash
python3 scripts/realign.py --feature <f>          # 哪里没对准
python3 scripts/realign.py --feature <f> --plan   # 按什么顺序重做
```

它查七类漂移:

| 类型 | 说明 |
|---|---|
| 产物建在旧基线上 | `req`/`arch` 的 `baseline_revision` 对不上当前 `revision` |
| 挂的 item 已不存在 | slice / case_intent / case 指向一个消失的 id |
| 订正后的 item 没人覆盖 | 新增或改动的 item 没有 slice |
| 没有 case 在证明它 | item 没有任何 case |
| 按 schema 已失效但仍是 true | 回退 origin 之后的 `accepted` / `aligned` / `semantic_gate` |
| 证的是旧需求 | 解封后旧 plan 里的 `PASS` |
| 回退没落实 | ops 定了 `defect_origin`,但 `deliver.last_rewind` 还没记 |

**重做顺序是向前的一段** —— 从最早漂移的那一格起,确保后面每一格都建在当前基线上。
每一格仍走原有停问点:`check-feature` + `stage-gate` + 人确认用语。

**失效的签字要清掉,不是留着。** 下一轮会把它读成当前有效。`realign.py` 只让漂移可见,
**不写任何文件** —— 清签字是人的动作。

## 四、每一格的质量把关

三道一起过,职责不重叠:

| 工具 | 查什么 | 性质 |
|---|---|---|
| `check-feature.sh <f> <stage>` | **结构**:字段齐不齐、原文锁、语义门、维表覆盖 | 既有 |
| `stage-gate.py --feature <f> --all` | **专业硬错**:验收含主观词、弱断言、根因未复现…… | 新 |
| 人按 `experts.md` 过清单 + grill 拷问 | **专业判断**:拆解忠实吗、架构合理吗、用例有意义吗 | 不可替代 |
| `realign.py --feature <f>` | **基准对准**:产物还指向当前基线吗 | 新 |

前两道 PASS **不等于**这一关过了。两个工具都会在 PASS 时显式说这句话 ——
因为一个声称能判质量的门禁,会让人停止自己看。

## 五、交付之后:持续跟进

`done` 不是终点。两个既有工具就是事后反馈的入口:

```bash
bash scripts/ticket-metrics.sh --repo <仓>    # reopen 次数 · 签字后被推翻次数
bash scripts/audit-traces.sh 50               # 路由纪律的 HARD 计数
```

`ticket-metrics` 的两列正是**需求质量的事后信号**:

| 列 | 高了说明什么 |
|---|---|
| reopen 次数 | 需求评审这一格没把住 —— 密封了不该密封的东西 |
| 签字后被推翻次数 | 签字时的证明上下文不够,人在信息不足时点了头 |

**这两列不打分,是件数。** 它们不评价某张票好坏,而是指出**哪一格的把关需要加强** ——
和 `agent-metrics` 的问题密度是同一种用法:指向下一刀改哪里。

线上现象走 `ops`:先分类,再取证,**特征缺陷回退 deliver**。
如果 ops 定出的 `defect_origin` 反复落在 `req`,那不是实现问题,是需求质量问题 ——
该改的是评审那一格的拒过清单,而不是继续修代码。

### 良性演进怎么闭合

```
交付 → ticket-metrics / audit-traces 的件数
            ↓ 有硬信号
     agent-review.sh 起草提案(只起草)
            ↓
          grill 拷问
            ↓ 人确认用语
     land:改 experts.md 的拒过清单 / stage-gate 加一条 / 委派包格式
            ↓
      下一张票在更紧的关口上跑
```

**改的是关口,不是某一张票。** 一张票修好了只值一张票;把那类错变成机检的一条,
之后每一张都受益。这也是为什么 `stage-gate` 的每条规则都写明「为什么不可接受」——
下次有人想放宽它,得先推翻那个理由。

## 六、不要

| 不要 | 为什么 |
|---|---|
| agent 自己改基线 / 自己 unseal | `deliver-schema.md`:Agent 不得自行 unseal。让被量的人改尺 |
| 「我觉得需求不合理」当反馈 | 反馈要带依据:哪个文件哪一行、哪条用例红过 |
| 订正后只改代码,假装基线没变 | `deliver-schema.md`:不得只改代码假装基线已变 |
| 留着失效的签字不清 | 下一轮读成当前有效,新需求被旧证据验收 |
| 把 `UNPROVEN` 悄悄当通过 | 提测门的拒过清单第一条 |
| 用 reopen 绕过「需求写错」的责任 | reopen 本身要记 `revision + 1`,次数会出现在 ticket-metrics 里 |
| 事后只修这张票 | 修了关口才有复利;修一张票只值一张票 |
