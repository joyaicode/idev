## 三、真缺口

### 1. 循环变量被闭包 / goroutine / defer 捕获，读到的不是当轮值

**书中依据**：第 5 章 5.6.1「警告：捕获迭代变量」——「在该循环中生成的所有函数值都共享相同的循环变量……函数值中记录的是循环变量的内存地址，而不是循环变量某一时刻的值」（L5761）；「后续的迭代会不断更新 dir 的值，当删除操作执行时，for 循环已完成，dir 中存储的值等于最后一次迭代的值」（L5763–L5765）；纠正方式是「引入一个与循环变量同名的局部变量，作为循环变量的副本：`dir := dir`」（L5771）。并明确「如果你使用 go 语句（第八章）或者 defer 语句（5.8 节）会经常遇到此类问题」（L5776）。

**论据**：现有 C# 无一条覆盖「循环变量被稍后执行的函数值（闭包 / goroutine / defer）捕获」这一形状。这是 Go（1.22 前）、JavaScript（`var` 在循环）、Python（晚期绑定）共有的经典陷阱，且书中明言「即使是经验丰富的程序员也会在这个问题上犯错误」（L5732）。与 C23（多步调用间隐式状态）不同：C23 管「调用先后依赖隐式状态」，本条管「循环变量被捕获后读到终值」。

**建议落点**：`conventions/coding-tables.md` §2 末尾新增 C34（最小 diff，接在 C33 后）。

### 2. 库 / 模块代码自行终止进程，或把 panic 当普通控制流

**书中依据**：第 5 章 5.4.1「这种策略只应在 main 中执行。对库函数而言，应仅向上传播错误，除非该错误意味着程序内部包含不一致性，即遇到了 bug，才能在库函数中结束程序」（L5271）；5.10「公有的 API 应该将函数的运行失败作为 error 返回，而不是 panic」（L6236）；「不加区分的恢复所有的 panic 异常，不是可取的做法……你不应该试图去恢复其他包引起的 panic」（L6231–L6236）；「安全的做法是有选择性的 recover……只恢复应该被恢复的 panic 异常」（L6242）。

**论据**：T8（快速失败）管「catch 只处理你能处理的、失败原子性」，但未覆盖「库 / 模块代码不得自行终止进程（os.Exit / log.Fatal / System.exit / process.exit），终止只发生在入口」这一分层约束；也未覆盖「panic 只用于不可恢复 bug、不把它当 return error 的替代」。这是跨语言可推广的错误处理分层原则（Java 库不 System.exit、Python 库不 sys.exit、Node 库不 process.exit），是本书 5.4.1 + 5.10 的独立主张。

**建议落点**：`conventions/coding-tables.md` §2 末尾新增 C38（最小 diff，接在 C37 后）。
