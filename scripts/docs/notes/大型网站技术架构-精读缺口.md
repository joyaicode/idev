## 三、真缺口

### 1. 灰度发布 / 分批发布：发布期限制故障爆炸半径

**书中依据**：5.6.6（L3548–L3590，PDF 112）。大型网站集群规模庞大（上万台服务器），一旦发布引入故障，全量回滚耗时太长、故障时间不断增加；灰度发布将集群分成若干部分，每天只发布一部分，观察稳定后再发布下一批，期间发现问题只需回滚已发布的一小部分，把故障范围限制在最小。灰度发布也用于 A/B 测试（部分服务器新版本、部分旧版本，比较用户满意度）。

**落点**（已于 12ab1c4 落地）：[conventions/canon.md](../../../conventions/canon.md) T11「可运维性是架构特性」DO 清单。现有 DO 已列「指标、结构化日志、告警条件、回滚路径、降级开关」，但「回滚路径」只覆盖「发布后如何恢复」，未覆盖「发布时如何限制爆炸半径」。最小 diff：在 T11 DO 的交付前清单中补一句「大规模集群 / 高风险变更默认分批灰度发布（先小批、观察稳定再扩批），回滚只作用于已发布批次；灰度同时用于 A/B 对照时写明对照组与判定指标」。对应 A6「护栏：指标、日志、回滚、降级」同步点名灰度。

**效果**：把「可运维性」从「出了事能恢复」补成「发布时先缩小事故面」，与 T10 的失败语义、T11 的熔断/降级形成完整闭环；不新增编号、不建第二套发布框架。

## 四、重点候选裁定（防后人重复发现）

1. **「故障分 / 可用性考核」（5.1.2）不另立。** 故障分类加权（事故级/A/B/C 类权重）与责任分摊是组织绩效手段，不是代码形状或阶段门禁。T11 已承载「指标、告警条件」的技术侧；把「故障分」写成规约会混入管理偏好，误报大于收益。
2. **「一致性 Hash / 负载均衡算法」（6.2.6、6.3.3）不另立。** 余数 Hash 扩容导致缓存大面积失效、一致性 Hash 减少重映射是具体算法选型，属 T12「架构=有记录的权衡」范畴（记录被拒方案与后果），不升格为通用编号。
3. **「火车发布模型 / 自动化发布」（5.6.5）不另立。** 规则驱动的发布流程自动化已由 `docs/SKILL.md` 自动化、`deliver` 提测门与 git 工作流承载；火车模型是组织形态，原则已覆盖。
4. **「架构师领导艺术 / 职场攻略」（第 14–16 章）不落通用规则。** 关注人、发掘优秀、共享蓝图、妥协、成就他人、发现问题/提出问题/解决问题是组织与个人成长方法，非阶段门禁或代码形状；可执行部分由 `experts.md` 阶段角色、grilling 与 trace/changelog 承载。
5. **「秒杀 / 淘宝 / 维基百科 / Doris 案例」（第 9–12 章）不另立。** 具体业务案例是理解材料；其架构手段（缓存、异步、队列、限流、冗余）已由 T10/T11/A4 承载，不重复立条目。
6. **「典型故障案例」（第 13 章）不另立。** 写日志占满磁盘、高并发数据库、单例锁、缓存全关、启动不同步、大文件独占磁盘等故障，对应 F1–F7 与 T8/T10/T11 的既有纠正；作为解释材料，不新增失败模式编号。
