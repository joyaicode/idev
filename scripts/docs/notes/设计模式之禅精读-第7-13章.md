## 第7章 单例模式（Singleton）L3407-3684

### ① 定义与意图
"确保某一个类只有一个实例，而且自行实例化并向整个系统提供这个实例"（L3473-3474）。以皇帝独苗作比——同一时期只有一个皇帝，臣民提及皆知（L3409-3415）；通过私有构造函数禁止外部 new（L3416-3427）。

### ② 适用场景与触发条件
- **该用**：①生成唯一序列号（L3530）；②需共享访问点/共享数据，如 Web 页面计数器，要求线程安全（L3531-3533）；③创建对象耗资源过多，如访问 IO 和数据库（L3534）；④大量静态常量/静态方法（工具类）环境（L3535-3536）。
- **不该/慎用**：需扩展时——单例一般无接口，只能改代码；需 mock 测试时（L3516-3524）。

### ③ 反例与违反代价
- 扩展困难：一般没有接口；因"自行实例化"要求，实现接口也无意义（L3516-3519）。
- 对测试不利：单例未完成不能测试、无接口不能 mock（L3520-3524）。
- 与单一职责原则冲突："把'要单例'和业务逻辑融合在一个类中"（L3525-3526）。
- 线程不安全反例：懒汉式在 null 判断后 new，两线程交错可产生两个对象（L3538-3561）。
- 复制漏洞：实现 Cloneable 后 clone 可绕过私有构造再产生对象，"最好方法就是单例类不要实现Cloneable接口"（L3569-3573）。
- 代价：全局有状态单例被 JVM 垃圾回收后，状态"恢复原状"引发故障（L3673-3677）。

### ④ 论据
- 优点四条：内存仅一实例减少开支；重资源对象可启动时产生、永久驻留；避免资源多重占用（同文件同时写）；可设全局访问点优化共享资源访问（L3505-3514）。
- 线程同步解法：懒汉式加 synchronized，但作者"建议读者使用如代码清单7-3所示的方式"即饿汉式（L3565-3568）。
- 有上限的多例模式（7.4 扩展）：需产生固定数量对象（土木堡之变后两皇并立比喻，L3578-3597）；可在设计时决定内存实例数，如启动时初始化固定数量 reader 实例（L3663-3667）；线程安全可用 Vector 替代 ArrayList（L3638-3639）。

### ⑤ 最佳实践与忠告
- Spring 中每个 Bean 默认单例，由容器管理生命周期；非单例（Prototype）则生命周期交由 J2EE 容器（L3669-3672）。
- 防垃圾回收丢状态：①由容器管理单例生命周期（L3678-3680）；②状态随时记录——异步或观察者模式写入文件/数据库（L3681-3683）。
- 单例类中其他方法"尽量是static"（L3489-3502）。

### 模式/原则间关系
- 与 SRP：单例模式与单一职责原则冲突（L3525-3526）。
- 与工厂方法：可被工厂方法替代实现单例/多例（L4127-4129，见第8章扩展3）。

**代码示例概括**：Emperor/Minister 演示臣子三次参拜所见同一皇帝；通用单例（private 构造+static final+getInstance）；懒汉式线程不安全演示；有上限多例（maxNumOfEmperor=2、静态块初始化、getInstance 随机返回）；5 位大臣随机参拜可能见到不同皇帝。

## 第8章 工厂方法模式（Factory Method）L3686-4233

### ① 定义与意图
"定义一个用于创建对象的接口，让子类决定实例化哪一个类。工厂方法使一个类的实例化延迟到其子类"（L3854-3860）。女娲造人：女娲=场景类、八卦炉=工厂、三种人=同一接口的不同实现（L3703-3709）。

### ② 适用场景与触发条件
- **该用**：①new 的替代品，但需权衡是否为加工厂类而增加复杂度（L3949-3950）；②需灵活、可扩展的框架，如邮件服务器 POP3/IMAP/HTTP 三种连接作为产品类（L3951-3956）；③异构项目：WebService/WSDL 产生的对象视为产品由工厂管理，减少外围系统耦合（L3957-3960）；④测试驱动框架下虚拟关联类（因 JMock/EasyMock 出现已弱化）（L3961-3964）。
- **替代形态触发**：模块仅需一个工厂类时缩小为简单工厂（L3967-3991）；产品初始化复杂时升级为多工厂类（L4038-4068）。

### ③ 反例与缺点/代价
- 简单工厂（静态方法）"是工厂方法模式的弱化"：工厂类扩展困难、不符合开闭原则，但仍实用（L4034-4037）。
- 多工厂类：职责清晰结构简单，但扩展需同时新建工厂类，影响可扩展性与维护性（L4121-4124）；复杂应用需再加协调类封装子工厂、提供统一接口（L4125-4126）。

### ④ 论据
- 优点四条：①良好封装、结构清晰，调用者只需类名，降低模块间耦合（L3929-3932）；②扩展性优秀：增产品只需增类，加 BrownHuman 无需改原代码（L3933-3935）；③屏蔽产品类，只关心接口——JDBC 从 MySQL 切 Oracle 仅换驱动名（L3939-3944）；④典型解耦框架："符合迪米特法则……也符合依赖倒置原则……当然也符合里氏替换原则"（L3945-3947）。
- 通用代码"是一个比较实用、易扩展的框架"（L3927）。
- 四种扩展（8.4）：①缩小为简单工厂（静态方法，去掉抽象层）（L3967-3991）；②升级为多工厂类，"非常符合单一职责原则"（L4038-4068）；③替代单例：SingletonFactory 反射获得构造器 setAccessible(true) 创建唯一对象，可扩展为单例构造器框架，输入类型即得唯一实例（L4127-4183）；④延迟初始化：ProductFactory 用 Map 缓存+synchronized，命中直接取否则创建放入，可限制最大实例化数量（如 JDBC MaxConnections），亦适合初始化复杂的硬件访问（L4184-4228）。

### ⑤ 最佳实践与忠告
- 工厂方法使用频繁但并非人人用好，"熟能生巧"（L4229-4233）。
- 可与模板方法、单例、原型等模式混合使用，"变化出无穷的优秀设计"（L4230-4233）。

### 模式/原则间关系
- 符合迪米特、依赖倒置、里氏替换原则（L3945-3947）；多工厂符合单一职责原则（L4067-4068）；简单工厂违反开闭原则（L4036-4037）。
- 可替代单例/多例（L4127-4129）；可与模板方法、单例、原型模式组合（L4232）。

**代码示例概括**：女娲八卦炉造三种人（泛型抽象工厂+Class.forName 反射）；通用 Product/Creator 框架；static 简单工厂；三个单一职责工厂类；SingletonFactory 反射破私有构造造单例；ProductFactory Map 缓存延迟初始化。

## 第9章 抽象工厂模式（Abstract Factory）L4236-4641

### ① 定义与意图
"为创建一组相关或相互依赖的对象提供一个接口，而且无需指定它们的具体类"（L4465-4468）。意图：有多个业务品种、业务分类时借此产生需要的对象（L4471-4473）；"抽象工厂模式是工厂方法模式的升级版本"（L4471）。开篇是重构故事而非故障：女娲漏定义性别，用"八卦复制术"把八卦炉一变二成女性/男性八卦炉（L4238-4265）。

### ② 适用场景与触发条件
- **该用**：一个对象族（或一组没有任何关系的对象）都有相同的约束，即可使用（L4615-4616）；如文本编辑器、图片处理器在不同 OS 下功能界面相同而代码实现不同，共同约束是操作系统类型（L4616-4619）。
- **实践场景**：涉及 Windows/Linux/Android 等多操作系统的软件不应分别设计多套，而用抽象工厂屏蔽 OS 对应用的影响（L4632-4639）。

### ③ 反例与缺点/代价
- 最大缺点："产品族扩展非常困难"（L4607）——增加产品 C 须给 AbstractCreator 加 createProductC()，所有实现类连带修改，"严重违反了开闭原则"（L4608-4610）。
- 抽象类和接口是契约，改契约则相关代码全改，作者称之"有毒代码"（L4610-4612）。

### ④ 论据
- 人种由肤色（Y轴）+性别（X轴）两坐标唯一确定（L4249-4251、L4269-4270）；车间/生产线比喻：八卦炉=车间、生产工艺=生产线，黑黄白人种 1:4:6 比例须在车间内协调好（L4454-4460）。
- 两类约束：汽车左门右门数量相等是产品族（两对象间）约束；每个型号车门不同是产品等级结构约束（L4479-4484）。
- 规模法则：有 N 个产品族，抽象工厂类应有 N 个创建方法（L4538）；有 M 个产品等级，应有 M 个实现工厂类（L4566）。
- 优点一封装性：高层模块只关心抽象，知道工厂类即可创建所需全部对象（L4597-4599）；场景类中"没有任何方法与实现类有关系"（L4590-4591）。
- 优点二约束非公开状态：产品族内约束（如"每生产1个女性，就同时生产出1.2个男性"）对高层透明（L4600-4604）。
- 扩展方向（注意事项）：产品等级扩展容易——现实存在双性人性别，只需增加 3 个产品类+1 个工厂类，完全通过扩展实现变更、符合开闭原则（L4621-4628）。

### ⑤ 最佳实践与忠告
- 区分两类扩展难度：产品族扩展困难≠产品等级扩展困难；横向（产品等级）扩展容易、纵向（产品族）扩展困难（L4621-4624）。

### 模式/原则间关系
- 工厂方法模式的升级版本（L4471）；产品族扩展违反开闭原则（L4608-4610），产品等级扩展符合开闭原则（L4628）。

**代码示例概括**：Human 接口+黑/黄/白三抽象肤色类+性别具体类的两维人种体系；HumanFactory 定义三肤色造人方法，FemaleFactory/MaleFactory 双车间分别生产各肤色女性/男性；通用代码 AbstractCreator 定义两族创建方法、Creator1/2 按产品等级生产、Client 仅依赖抽象产生 A1/A2/B1/B2。

## 第10章 模板方法模式（Template Method）L4644-5165

### ① 定义与意图
"定义一个操作中的算法的框架，而将一些步骤延迟到子类中，使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤"（L4868-4874）。仅使用 Java 继承机制实现，但应用非常广泛（L4878-4882）。开篇：一周做 10 万悍马车模，领导要求"只做最基本的实现"引出最一般设计（L4650-4668）。

### ② 适用场景与触发条件
- **该用**（L4968-4973）：①多个子类有公有的方法且逻辑基本相同；②重要、复杂的算法可把核心算法设计为模板方法，周边细节功能由各子类实现；③重构时把相同代码抽取到父类，再通过钩子函数约束其行为。

### ③ 反例与缺点/代价
- 弯路反例：两个实现类 run() 完全相同，实现应出现在抽象类，"抽象是所有子类的共性封装"（L4786-4787）；"相同的一段代码拷贝过两次，就需要对设计产生怀疑"（L4788-4789）。
- 缺点：颠倒"抽象类声明、实现类完成"的惯常职责，子类执行结果影响父类结果，复杂项目中带来代码阅读难度、令新手不适（L4963-4967）。

### ④ 论据
- 两个角色：基本方法=由子类实现、在模板方法中被调用（L4886）；模板方法=实现对基本方法的调度、完成固定逻辑的框架（L4888-4889），防恶意操作一般加 final 不允许覆写（L4890）。
- 基本方法尽量设计为 protected，符合迪米特法则，实现类非必要不扩大父类访问权限（L4946-4947）。
- 优点：封装不变部分、扩展可变部分（加 H3 型号只需加子类）；提取公共部分代码便于维护；"行为由父类控制，子类实现"符合开闭原则（L4950-4962）。
- 扩展（10.4）钩子方法 Hook：需求变更为 H1 喇叭想响就响、H2 不要声音（L4975-4977）；抽象类增加 isAlarm 实现方法（默认返回 true），run() 中 if(isAlarm()) 才调用 alarm()（L5018-5034）；isAlarm 的返回值影响模板方法的执行结果，该方法即钩子方法 Hook Method（L5136-5138），"有了钩子方法模板方法模式才算完美"（L5138）。

### ⑤ 最佳实践与忠告
- "父类怎么调用子类的方法"三种歪路（子类传入父类有参构造、反射、调用子类静态方法）虽能解决问题，但"项目中允许使用不？不允许！"（L5151-5155）。
- 正解是换个角度："父类建立框架"，子类重写部分方法后再调用从父类继承的方法产生不同结果，"曲线救国"实现父类依赖子类，正是模板方法模式（L5156-5159）。
- 开源框架大量应用：继承抽象类、覆写 protected 方法、调用类似 execute 的方法即完成扩展（L5160-5163）。

### 模式/原则间关系
- 行为由父类控制、子类实现，符合开闭原则（L4962）；基本方法 protected 符合迪米特法则（L4946-4947）；仅凭 Java 继承机制实现（L4878）。

**代码示例概括**：抽象 HummerModel 定义 start/stop/alarm/engineBoom 五方法、H1/H2 各自实现后 run() 汇总检验；run() 改为实现方法上移父类，按固定顺序 start→engineBoom→alarm→stop 调度；通用 AbstractClass 基本方法+templateMethod 调度框架；扩展版 run() 加 final 并依 isAlarm() 条件响喇叭，H1 由客户输入控制、H2 覆写关闭。

## 第11章 建造者模式（Builder Pattern）L5168-5719

### ① 定义与意图
"将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示"（L5595-5598），也叫生成器模式（L5595）。核心意义："组装顺序不同对象效能也不同"（L5707）。开篇：XX公司奔驰宝马车模合同，四动作"都由客户自己控制"顺序（L5171-5174）且须批量生产（L5181-5182）；手写场景类拼顺序的需求组合无穷，"直到把你逼疯为止"（L5319），最终"找一个导演，指挥各个事件的先后顺序"、"为每种顺序指定一个代码"（L5448-5450）。

### ② 适用场景与触发条件
**该用**（L5688-5694）：①相同方法、不同执行顺序产生不同事件结果；②多个部件装配到同一对象但运行结果不同；③产品类复杂或调用顺序不同产生不同效能；④创建产品时依赖的对象"不易得到"时。第④条仅是"补偿方法"——设计阶段竟未发觉对象难获得，事后柔化创建过程"本身已经违反设计的最初目标"（L5694-5696）。

### ③ 反例与缺点/代价
- 不用的做法：每来一需求就手写场景类逐个拼顺序 setSequence（L5286-5311）；而"需求是无底洞，是无理性的"（L5442），排列组合不可能逐个写场景类（L5319-5320）。
- 弯路反例：ArrayList 作成员变量未在方法中 clear，出现"出乎意料"数据，"花费了几个通宵"才解决（L5558-5562）。
- 代价：有几个产品类就要有几个具体建造者，且这些产品类须具有相同接口或抽象类（L5655-5656）。

### ④ 论据
- 四角色（L5607-5619）：Product 产品类（通常实现模板方法模式）；Builder 抽象建造者（规范产品的组建，一般由子类实现）；ConcreteBuilder 具体建造者（实现全部方法并返回组建好的对象）；Director 导演类（"负责安排已有模块的顺序"并"告诉Builder开始建造"，即故事中的老大）。
- 优点（L5679-5686）：封装性——客户端不必知道产品内部组成细节；建造者独立、易扩展——BenzBuilder 与 BMWBuilder 相互独立；便于控制细节风险——逐步细化建造过程而不影响其他模块。
- 导演类起封装作用，"避免高层模块深入到建造者内部的实现类"；模式庞大时导演类可以有多个（L5674-5675）。
- 与工厂方法对比：建造者关注"零件类型和装配工艺（顺序）"，是"与工厂方法模式最大不同的地方"（L5698-5699）；建造者最主要功能是基本方法的调用顺序安排（零件装配），"工厂方法则重点是创建"零件，组装顺序非其所关心（L5709-5712）。
- 扩展（11.4）：书称"已经不用扩展了"——车模例子已引入模板方法模式完成扩展（L5700-5701）；并点出其他书籍常漏掉的角色"零件"：建造即零件的组装，引入模板方法"是非常简单而有效的办法"（L5705-5708）。

### ⑤ 最佳实践与忠告
- 用建造者时"考虑一下模板方法模式"，"别孤立地思考一个模式"，"僵化地套用一个模式会让你受害无穷"（L5714-5715）；按本书写法组合使用"比单独使用建造者是高效、简洁得多"（L5716-5717）。
- 工程忠告：调类成员加 this、调父类加 super 更清晰，靠约束与程序员自觉（L5553-5557）；ArrayList/HashMap 定义为类的成员变量时，方法中调用前必须 clear 防数据混乱（L5558-5560）。
- "代码是让人看的"（L5590），重构的最终目的是"简单、清晰"（L5590），高级语言要写得让别人能看懂（L5591-5593）。

### 模式/原则间关系
- 与模板方法模式（第10章）：CarModel 的 run() 机制与之"非常类似"（L5202）；Product 通常实现模板方法模式（L5608-5610）；最佳实践要求两者结合使用（L5714-5717）。
- 与工厂方法模式：同为创建类模式，建造者重装配顺序、工厂重零件创建（L5697-5712）。

**代码示例概括**：CarModel 抽象类定义 4 个抽象动作+final run() 遍历 sequence 按名分发+setSequence；奔驰/宝马模型各自实现动作打印；场景类手动拼顺序生产；CarBuilder 抽象组装者声明 setSequence/getCarModel，奔驰、宝马组装者持有对应产品委托组装返回；Director 导演类 getA/B/C/D 四方法各自 clear 后拼顺序、经 Builder 返回模型；场景类循环批量调用导演方法生产万辆级车模；通用代码 Product/抽象 Builder（setPart/buildProduct）/具体建造者/Director 封装 builder 调用。

## 第12章 代理模式（Proxy Pattern）L5722-6704

### ① 定义与意图
"为其他对象提供一种代理以控制对这个对象的访问"（L5884-5885，OCR 丢失"为"字按语义补正）。代理模式也叫委托模式，是一项基本设计技巧，状态、策略、访问者模式本质上是"在更特殊的场合采用了委托模式"（L5890-5891）。开篇演变：作者玩网游两月升到80级仍被砍（L5725-5728）→把账号交给代练公司（L5815-5817）→"这就是代理模式"（L5881）。

### ② 适用场景与触发条件
**该用**：①不想卷入中间过程是非——打官司找律师（L5986-5988）；②需控制访问并在方法前后做预处理和善后处理（L5908-5909）；③需增强/拦截目标方法（L6317-6318）；④对扩展性要求高的场合（L6098-6099）；⑤延迟初始化（虚拟代理，L6402）；⑥横切关注——审计/日志/事务/权限（L6535、L6691-6692）。典型应用：Spring AOP 是"非常典型的动态代理"（L5989）；Struts2 的 Form 元素映射采用动态代理（L5895-5896）。

### ③ 反例与缺点/代价
- 弯路实验：直接 new 真实角色被三连拒"请使用指定的代理访问"（L6249-6252）；自己 new 的代理仍被拒，因"它不是真实角色指定的对象"（L6275-6281）。
- 代价：①普通代理靠构造函数校验这类技术约束，"对系统维护是一种非常不利的因素"（L6101-6102）；②虚拟代理"需要在每个方法中判断主题对象是否被创建"（L6403）；③JDK 动态代理"被代理类必须实现一个接口"（L6693）；④静态代理须手写代理类（L6415-6416）。

### ④ 论据
- 三角色（L5901-5909）：Subject 抽象主题（最普通的业务类型定义、无特殊要求）；RealSubject 具体主题/被代理角色，"是业务逻辑的具体执行者"（L5906）；Proxy 代理主题/委托类，把方法委托给真实角色并在处理完毕前后做预处理和善后处理（L5907-5909）。
- 优点（L5973-5983）：职责清晰——真实角色"不用关心其他非本职责的事务"；高扩展性——实现类怎么变都"逃不脱如来佛的手掌（接口）"；智能化——在动态代理中体现。
- 一个代理类可代理多个被委托者，具体代理谁"由高层模块来决定"（L5959-5962）。
- 普通代理 vs 强制代理（谁找谁）：普通代理客户端"只能访问代理角色，而不能访问真实角色"（L5999），真实角色用构造函数限制创建者（L6027-6034）；强制代理"必须通过真实角色查找到代理角色，否则你不能访问"（L6105），"由真实角色管理代理角色"（L6110），高层模块"只要调用getProxy就可以访问"（L6313）。明星比喻：直接找明星被推给经纪人（L6111-6116）。对照网络代理：透明代理≈强制代理，普通代理须自己设置（L5992-5997）。
- 扩展（12.4）五种形态：①普通代理——只改两个构造函数即切换访问路径（L6019-6021）；②强制代理——真实角色指定并管理代理；③代理有个性——可实现多接口（IProxy 计费），代理职责"并不一定单一"，可"预处理消息、过滤消息、消息转发、事后处理消息"（L6379-6386）；④虚拟代理——需要时才初始化，避免初始化缓慢（L6402）；⑤动态代理——"压轴大戏"，"在实现阶段不用关心代理谁，而在运行阶段才指定"（L6408-6413）。
- 动态代理机制：按接口生成所有方法、默认空实现，"所有被代理的方法都由InvocationHandler接管"（L6462-6463）；客户端"既没有创建代理类，也没有实现接口"（L6498）。
- 动态代理主旨："解决我们常说的'审计'问题，也就是横切面编程"，不改变已有代码结构而增强或控制对象行为（L6691-6692）。
- AOP："AOP编程没有使用什么新的技术"（L6534），日志、事务、权限可"在设计后通过AOP的方式切过去"（L6535-6536）；通用模型（图12-8）是"两条独立发展的线路"，代理职责与业务逻辑无必然耦合，"通知Advice从另一个切面切入"（L6552-6554）；DynamicProxy 中 if(true) 演示"在什么地方（连接点）执行什么行为（通知）"（L6598-6608）。

### ⑤ 最佳实践与作者忠告
- "Spring AOP和AspectJ……拿来主义即可！"（L6701）；调试时看到 $Proxy0 这样的结构即知是动态代理（L6702）。
- 学 AOP 弄清四个名词即可：切面、切入点（JoinPoint，OCR"切人点"系误植）、通知（Advice）、织入（Weave）（L6703-6704）。
- 普通代理约束尽量走团队编程规范而非技术约束，实践中"通过约定来禁止new一个真实的角色"（L6099-6102）。
- DynamicProxy 是通用代理框架，设计自己的 AOP 框架可"在此基础上扩展"——"只要有一个接口，一个实现类，就可以使用该代理"（L6695-6697）；CGLIB 等技术可实现不需接口的动态代理（L6694）。

### 模式/原则间关系
- 委托是基本技巧：状态、策略、访问者模式"在更特殊的场合采用了委托模式"（L5890-5891）。
- AOP"核心就是采用了动态代理机制"（L6423-6424）；Spring AOP 是典型应用（L5989）。
- 代理实现职责分离（L5973-5975），呼应单一职责；实现类可变而代理不动（L5977-5981），符合开闭思想。

**代码示例概括**：IGamePlayer+GamePlayer 玩家亲打怪；代练者全方法委托、运行结果不变；通用 Subject/RealSubject/Proxy 源码（before/after 是"引子"）；普通代理——真实角色构造函数校验创建者、代理只传名字；强制代理全套——getProxy 接口、isProxy 校验、三次访问实验两败一成；IProxy 计费、upgrade 后 count() 报 150 元；虚拟代理懒初始化 RealSubject；GamePlayIH+Proxy.newProxyInstance 首个动态代理，invoke 判断方法名 login 发盗号提醒（AOP 雏形）；通用模型 MyInvocationHandler、DynamicProxy（内嵌 BeforeAdvice）、IAdvice；SubjectDynamicProxy 把三参数封装为一个 subject、简化高层调用。

## 第13章 原型模式（Prototype Pattern）L6705-7243

### ① 定义与意图
正式定义（L7018-7019）："用原型实例指定创建对象的种类，并且通过拷贝这些原型创建新的对象。"另一种表述（L7014，定义句全引）："这种不通过new关键字来产生一个对象，而是通过对象复制来实现的模式就叫做原型模式。"原型模式"简单程度仅次于单例模式和迭代器模式，正是由于简单，使用的场景才非常地多"（L7016-7017）。开篇演变：银行广告信一晚发600万客户（L6714）→单线程0.02秒/封，600万封需33小时，"今天的不发送完，明天的账单又产生了，日积月累，激起甲方人员一堆抱怨"（L6882-6884）→直接改多线程则线程2把共享 mail 的收件人改掉，"线程不安全了"（L6885-6887）→"通过对象的复制功能来解决这个问题"（L6888）。

### ② 适用场景与触发条件
**该用**（L7071-7078）：①资源优化场景——"类初始化需要消化非常多的资源，这个资源包括数据、硬件资源等"；②性能和安全要求的场景——"通过new产生一个对象需要非常繁琐的数据准备或访问权限"；③一个对象多个修改者的场景——"一个对象需要提供给其他对象访问，而且各个调用者可能都需要修改其值时……拷贝多个对象供调用者使用"（正是开篇多线程邮件的解法）；④循环体内产生大量对象（L7066-7067）。**实际形态**："原型模式很少单独出现，一般是和工厂方法模式一起出现"（L7079-7080）。

### ③ 反例与缺点/代价
- 原始版单线程程序发不完（L6882-6884）；直接多线程共享同一 mail 对象被改坏（L6885-6887）。
- 逃避构造函数约束："这既是它的优点也是缺点……优点就是减少了约束，缺点也是减少了约束，需要大家在实际应用时考虑"（L7069-7070）。
- 浅拷贝风险："两个对象共享了一个私有变量，你改我改大家都能改，是一种非常不安全的方式，在实际项目中使用还是比较少的（当然，这也是一种'危机'环境的一种救命方式）"（L7175-7176）。
- clone 与 final 冲突：深拷贝梦想"在final关键字的威胁下破灭了"（L7231）。

### ④ 论据
- 核心机制：Cloneable"只是一个标记作用，在JVM中具有这个标记的对象才有可能被拷贝"（L7027-7029）；从"有可能被拷贝"到"可以被拷贝"须覆盖clone()方法（L7031-7032）；@Override 覆写的是 Object 类的 clone（L7040-7042）；"实现一个接口，然后重写clone方法，就完成了原型模式！"（L7062）。
- 优点①性能优良："原型模式是在内存二进制流的拷贝，要比直接new一个对象性能好很多"（L7066-7067）。②逃避构造函数的约束——构造函数不会被执行。
- 构造函数不执行原理："Object类的clone方法的原理是从内存中（具体地说就是堆内存）以二进制流的方式进行拷贝，重新分配一个内存块"（L7122-7123）。
- 浅拷贝机制："Java做了一个偷懒的拷贝动作"，clone"只是拷贝本对象，其对象内部的数组、引用对象等都不拷贝，还是指向原生对象的内部元素地址"（L7173-7175）。
- String 特殊性："对于String类型，Java就希望你把它认为是基本类型，它是没有clone方法的"，通过字符串池在需要时才创建新字符串，"读者在使用的时候就把String当做基本类使用即可"（L7178-7181）。
- 注意框：引用成员变量不被拷贝（即共享）须满足两条件——是类的成员变量而非方法内变量；是可变的引用对象而非原始类型或不可变对象（L7182-7183）。
- 深拷贝：对私有类变量独立拷贝，"该方法就实现了完全的拷贝，两个对象之间没有任何的瓜葛了，你修改你的，我修改我的"（L7204-7205）；另一实现是自己写二进制流操作对象（L7205-7206）。
- "原型模式已经与Java融为一体，大家可以随手拿来使用"（L7080-7081）。

### ⑤ 最佳实践与作者忠告
- "深拷贝和浅拷贝建议不要混合使用，特别是在涉及类的继承时，父类有多个引用的情况就非常复杂，建议的方案是深拷贝和浅拷贝分开实现"（L7207-7208）。
- 注意框："要使用clone方法，类的成员变量上不要增加final关键字"（L7234）；删除 final 是"最便捷、安全、快速的方式"（L7232）。
- 与工厂方法搭配：clone 创建对象、由工厂方法提供给调用者（L7079-7080）。
- 13.5 精髓："一个对象的产生可以不由零起步，直接从一个已经具备一定雏形的对象克隆，然后再修改为生产需要的对象"（L7240-7241）；DNA 比喻：不从1岁长到30岁，"直接找一个人，从其身上获得DNA，然后克隆一个，直接修改一下就是30岁了"（L7241-7243）。

### 模式/原则间关系
- 复杂度排序：仅次于单例模式和迭代器模式（L7016）。
- 与工厂方法模式共生："通过clone的方法创建一个对象，然后由工厂方法提供给调用者"（L7079-7080）——原型负责"怎么生"，工厂负责"给谁用"。
- 开篇故事即"一个对象多个修改者"场景的具象化：多线程共享 mail → clone 出副本各自修改（L6885-6888 与 L7076-7078 呼应）。

**代码示例概括**：AdvTemplate 广告模板 + Mail 五字段类 + Client 单线程循环发送（埋下隐患）；Mail implements Cloneable 覆写 clone()、场景类改用 mail.clone() 后再设称谓/收件人——多线程亦安全；通用 PrototypeClass 源码；Thing 构造函数打印测试——clone 后不打印，验证构造函数未执行；Thing+ArrayList 浅拷贝实验输出 [张三, 李四] 暴露共享；深拷贝在 clone() 内对 arrayList 再 clone，输出 [张三]；final+ArrayList 编译报错实验，验证 clone 与 final 冲突。
