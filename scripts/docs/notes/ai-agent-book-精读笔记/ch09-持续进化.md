## 一、本章主张

1. 从经验中持续学习正在成为 Agent 最重要的能力之一；它是应用系统工程，不能只等下一轮基础模型训练（L3, L11）。
2. 部署中的反馈很少逐步标明对错，系统得自己判反馈可信度；未经核验的反馈一旦写成规则或训练材料，错误归因会延续到后续任务（L9）。
3. 现阶段优先在模型外围建可验证的学习系统：能明确表达的经验走知识/指令/程序，参数学习留给后训练；每次更新先回归评估再发布（L13）。
4. 轨迹验证分三层并按序做：结果验证（环境实际变化）→ 过程验证（动作是否合规）→ 质量验证（rubric，需语境）（L25-31）。
5. 评价输出四件一起在：整体任务状态、各维度结论、证据位置、错误类型；证据不足的维度标待确认，交补充验证或人复查（L45）。
6. 失败描述要具体到轮次/调用才能定位改法；「退款失败，表达清楚」提不出改动（L47）。
7. 验证器自身会错：评「合规变通」的模型漏看没办成的替代方案，评「承诺一致」的程序查错工具——检查对象必须对上任务实际要求，不是字面近似（L57-61）。
8. 改哪里由错误出在哪个环节决定：引用旧版指南改知识库，没交代来源改指令——两份报告都被退回，改稿处不同（L65-67）。
9. 四类载体分工：事实例外→知识库；需语境的判断原则→Prompt/Skill；可精确执行的约束→程序；感知与隐式模式→参数（L78-80）。
10. 事实要连同适用条件与来源保存；具体时限会过期，做法本身可迁移（L84）。
11. 不能照抄整段轨迹当经验：一次超时后换工具查到，照抄就把偶然故障当成换工具的规律（L86）。
12. 材料分三层：原始轨迹（只追加、按版本）、单次运行分析、正式经验文档（随新证据修订）；记录与整理分开（L88）。
13. 同一条经验的正例反例放在一起：两次订票是同一版工具吗？成败差在少做一步还是条件本不同（L94）。
14. 提炼五步：存原始轨迹并固定任务与工具版本→逐次分析→按任务族聚合列正反例→选证据充分的写初稿→在未参与提炼的新任务上验证（L96-100）。
15. 更新层级由证据广度决定：一句纠正动当前任务与个人偏好；多个独立案例才动共用 Skill；材料已加载仍判断失当才收集训练案例（L118）。
16. 生产更新用带来源的最小 diff，保留触发案例、修改理由和旧版本，便于逐项撤回（L126）。
17. 从失败轨迹归纳规则时，输入材料决定规则内容——只给错误文本，归纳出的往往是「少做刚刚那一步」；归纳出的规则还会把过早放弃学进去，要靠结果校验（L138-142）。
18. 稳定、重复、可验证的操作优先转成程序；回放失效先核对哪些已完成，避免从头回放造成重复提交（L188, L201）。
19. 更新补丁在隔离分支上做，依次跑相关检查、失败轨迹重放、旧任务回归；运行中的系统继续用稳定版本（L211）。
20. 每次改动附可检验说明：失败证据、推断根因、涉及组件、补丁、要纠正的错误、原本正确的行为、分别验证两者的用例（L215）。
21. 拟修改方案时同时提供成功轨迹与历史被拒方案：只给失败会扩大修改范围破坏原对行为，缺被拒记录会重复同一无效思路（L217）。
22. 业务验证组件与发布控制面分离：业务 Agent 改不了自己的测试集、发布标准和稳定版本备份（L227, L383）。
23. 两次回放区分「找不到经验」（路由错）与「不会运用」（遵循错）；只看端到端分数就重写，会丢掉本来正确的规则（L269, L329）。
24. 在线执行与离线进化双循环分离：新规则验证并发布后才供后续任务；版本化经验库连接两侧，可回退（L311）。
25. 评估分「更新能力」与「受益能力」四步追问：改得对吗、需要时能加载吗、加载后照做吗、做完后任务表现提高了吗（L327-338）。
26. 长期跟踪五类变化：能力退化、泛化、token 与运行成本、安全合规、工程质量（L340-346）。
27. 只追加经验会让检索与遵循负担一起涨，逐渐抵消学习收益；合并、淘汰、重验证是常规工作，不是一次性清理（L401）。
28. 安全上沿信息、版本、权限立三道边界：证据与指令隔离、测试环境与生产分开、更新权限与批准权限分离（L377-383）。

## 三、缺口汇总

1. **等待约定的留痕与事后对照**（弱缺口）
   - 落点：references/self-evolution.md「学习信号写到哪里」→「学习信号」小节末补一句
   - 拟落文案：「委派或巡检里写了等待约定的（何时再查、何时算结案），约定本身进留痕；事后拿实际发生的事对照——到点没动、已结案仍重查、几路信号同时到达没先查结案，才算可归因偏差进学习信号，其余留在轨迹里。」
   - 书里依据：L315-317（在轨迹里记下当时约定的唤醒条件，再用实际发生的事对照；到点没查、已送达仍重查才有具体偏差；提醒与订阅同时到达先查是否已结案）
   - 说明：agents.md「这一轮之外到达的事」只管到达后的处置，学习信号四件只定义了信号形状，都没有「约定本身要留痕」这半句；idev 场景里等待较少（人签、环境就绪、巡检），故标弱。

## 四、勘误与存疑

- 实验9-2 的数字要谨慎引用：114 道迁移题基线 12.3%→19.3%（L136），且「每种策略在每道题上只运行了一次」（L148），无方差报告。
- 实验9-1 一致率 92.9% 的分母是 56 项（8 轨迹×7 维度），四处分歧三处同属一笔改签（L55-61）——偏差集中指向维度设计问题，样本小，不宜外推「LLM 评维度可靠」。
- PreAct 8.5~13 倍加速只对重复任务成立（L203）；本地邮件例 5.31s→4.45s 省的是模型调用，浏览器本身仍占大头——一次性交付为主的场景收益远小于此，书自己也写明「取决于原来有多少时间花在模型判断上」。
- 实验9-9 规模 126 次调用、三种子（L354），方向（可替换优于只追加）与机制相符，幅度不宜外推。
- DeepSeek Harness/Cordis 一节基于 2026-08 发布的开发者预览版（L257），接口未稳，判据不可照抄；插件更新对 KV 缓存前缀的影响（L255）是宿主层事实，与 idev 无关。
- 与 idev 无关的部分：表9-1 客服七维度、医疗影像案例、SFT/RL/LoRA 训练管道（L261-269）、RSIGym/发现树（L281-301）、Discovery Loop 叙事——参数侧与研究基建 idev 明确不做。
- 「改规则后用原案例重放验证」（L128 Inbox Zero）在 idev 判为有意不做：rootcause-guards 与 self-evolution 均明确「不建会执行 Agent 的回归运行器/不做回放」，替代是旁路复现 + 第二份不同结果（sediment gate），方向一致但机制不同，不视为缺口。
