## 一、本章主张

1. 上下文工程负责选择、组织和更新模型当前决策所需的信息；上下文的质量决定模型能否把已有能力用到当前问题上——能力够用的模型配上完整准确的上下文，表现可以优于缺少必要资料的更强模型 (L3, L17)。
2. 构建 AI 原生团队首先要把关键知识文档化：选用某技术的理由、业务规则变更不能只存在单人记忆或私聊里；对远程协作友好的团队往往也对 Agent 友好；人和模型都依赖 Context (L19–23)。
3. Agent 的下一步行动依赖截至当前的交互历史（ReAct 形式化 c_t = 观测与动作交替序列）(L29–35)。
4. KV Cache 友好三做法：保持可复用的前缀稳定（系统指令与常用工具定义确定的内容与顺序）；运行中的变化追加到后部（时间、余额、次数、进度经新消息或工具结果提供，标明生效时点）；按模型协议组织消息（正确角色、调用 ID、工具结果格式）(L460–464)。
5. 在生产系统中缓存已成为架构约束：提示词排列、子 Agent 起点、会话恢复结构在设计之初就要安排缓存边界 (L594)。
6. 保存已经发送的内容：大型工具输出压缩成摘要后应保存实际送入模型的版本；会话恢复时重放这份记录，不重新生成摘要（重新生成会引入新的措辞和前缀变化）(L600)。
7. 语气要求落实到具体表达：给出行数上限、适用情况与应采取的行动；「NEVER do X」式大写强调要说明适用于什么情况 (L642–646)。
8. 任务有明确阶段时优先按流程组织提示词：输入条件、处理顺序和异常出口写在对应阶段，模型据此判断当前走到哪里、下一步做什么 (L672)。
9. 业务规则由产品负责人主导设计（结合线上数据与运营经验），工程师再落实到提示词、工具参数和验证规则；宽泛分类词（「根据任务情况选择」）必须写成明确类别边界 (L710–718)。
10. 输出要求难以用几条规则表达时，优先给两三个高质量示例；重复处理同类任务用经过筛选的固定示例集（同时保持前缀稳定）(L722–724)。
11. 提示注入是上下文安全的核心威胁；分析风险沿「内容入口—上下文组织—调用决策—实际执行」逐层检查 (L762–764)。
12. 外部材料进入上下文时保留来源并用清晰边界包裹；来源标记由 Harness 生成，外部文本放在受控数据区；信息经过摘要、转存或重新加载后系统仍能识别原信任边界 (L768–772)。
13. Skills 渐进式披露三层：元数据目录（name + description）常驻、核心流程选中后加载、详细资料按需读取；Skill 描述首先要写成路由条件——先说明何时适用、何时应跳过，再概括能做什么 (L798–806)。
14. 设计交互方式时优先沿用模型已经训练和适配过的模式，减少模型从陌生格式中重新推断含义的负担 (L834)。
15. 反复使用的统计应优先由代码增量维护：把原始轨迹保存下来并不会自动得到一份准确、随时可取用的统计表；每次让模型重新遍历和计数既消耗推理 token，也增加漏记与重复计数的机会 (L886–888)。
16. 状态栏应尽量由代码维护——一条错误的「已拨打三次」就可能改变后续行动；需要语义理解的信息先让模型逐条抽取、再由代码汇总核验；原始事件、抽取结果与最终状态之间保留对应关系 (L991)。
17. 窗口还有空间时也应主动整理已反复使用的知识：过长或混杂的上下文导致遗漏关键事实、重复处理已解决的问题、把过时状态用于当前决策（context rot）(L1022–1024)。
18. 历史压缩优先成批进行，避免每轮都改写同一段前缀；保留最近几轮时应检查工具调用与返回值是否成对，并把未完成操作的状态写入摘要 (L1036)。
19. 压缩要算另一笔账：删去的材料若在后面用到了，要花多大代价才能找回来 (L997)。
20. 摘要设计四检查：按任务价值分配篇幅；保持语义完整（人物、时间、动作、机构共同构成一条事实）；围绕后续问题组织内容；验证摘要能否支持执行 (L1088–1091)。
21. 对于交付边界清楚、会产生大量中间材料的任务优先子 Agent 隔离：子 Agent 阅读中间结果，只向主 Agent 返回结论、证据位置和未解决问题 (L1097)。
22. 长任务应定期更新进展文档，保存「决定了什么、为什么这样决定、验证了什么、下一步做什么」——早期架构决定、约束背后的原因和失败路径容易在长历史中被遗漏 (L1093)。

## 三、缺口汇总

共 2 条。

### 缺口 1：自身轨迹摘要的事实档（对回原始证据才算数）

- **落点**：`conventions/evidence.md`「证据怎么用」信任表，新增一行。
- **拟落文案（判据式一句）**：从轨迹摘要、压缩产物或整理后的 memory 里读出的事实性内容，要在原始证据（trace/timeline 指向的日志与产物）里对得上才算数；两份摘要互相矛盾时并列存疑并回查原文，不择一采纳。
- **书里依据**：chapter2.md L1066（实验 2-10：带引用组把 Pamela Vagata 任职机构写成 Pebblebed、窗口化组写成 Stripe——两组都交付了汇总表，压缩产物会引入互相矛盾的事实）；L1056（带来源的摘要保留可回查链接）；L1089（语义完整：人物/时间/动作/机构共同构成一条事实）。
- **挂靠**：并入 evidence.md 信任表（表里已有「对不可信材料做的摘要，可信度与原材料相同」——本条把同一逻辑补到**自身产出的摘要**上），不新增编号。

### 缺口 2：执行者定义的 description 按路由条件写

- **落点**：`references/agents.md`「再派一个执行者」节末尾补一句（执行者定义治理）。
- **拟落文案（判据式一句）**：执行者定义文件的 description 写成路由条件——先写承接哪些步骤、不承接什么、由谁在什么信号下调用，不写成能力罗列；「帮助处理后端」式宽描述等于没有路由。
- **书里依据**：chapter2.md L804（「Skill 描述首先要写成路由条件。模型在加载正文之前就要决定是否使用它，因此 description 应先说明何时适用、何时应跳过，再概括能做什么……对容易混淆的任务，还可以补充排除条件」）。
- **挂靠**：agents.md「再派一个执行者」节（该节已管「什么才算再派的理由」，本条管「定义文件怎么写才可路由」），不新增编号。

## 四、勘误与存疑

1. **实验 2-10 的口径变更（L1048, L1058, 注 L1068）**：旧版用「历次请求的输入 token 之和」触发保护、`total_tokens` 为累计输入，7 月 22 日提交 `aea4d72` 改为最近一轮请求输入。书里诚实标注了，但引用该实验数字时必须先确认用的是哪个口径——同名字段两个含义。
2. **实验 2-9 样本量（L989）**：各类任务各五个案例；TODO 配置通过零项、对照组一项，详细错误配置四项 vs 对照五项——差异在 n=5 下不具统计力，只能当方向性观察。
3. **实验 2-3 的 `Hit%` 陷阱（L572）**：基线与重排组 Hit% 都是 100%，实际命中 token 数差 3 倍（768 vs 256）——按请求计数的命中率会掩盖按 token 计的真相；引用缓存指标必须先问计量单位。
4. **L912 ContextDistill-Bench 数字**（Claude 4 Sonnet 每千次查询 35.46→3.51 美元）：作者与合作者的自引研究，数字只覆盖「该基准覆盖的状态查询」；且 L98 注明实验 2-7 的输入是构造的客服退款轨迹（A/B 组各三次），结论边界窄。
5. **L622–626 自引《Models Take Notes at Prefill》**：研究延伸性质（KV 编辑/组合），非已验证工程实践；作者自己标注「所测的 8B 模型任务」，外推到生产前向缓存栈需重验。
6. **L448–450「端侧 Agent 的时代比许多人预期的更近」**：基于 Qwen3-0.6B 在 Mac 上跑通一个两工具任务（107 token/s），单一任务外推到「时代」属观点不属判据。
7. **L501 Lost in the Middle 的位置效应**：「常驻规则放前部、目标进度放末尾」是对特定模型族长上下文问答的观察转译；不同模型/模板的位置偏置不同，采信时当启发式而非定律。
8. **L573–576 实验 2-3 滑动窗口组缓存占比最高（67.9%）却没交付任务**：缓存指标与任务完成是两个正交目标——这是全章最有价值的方法论提醒（指标好≠结果对），与 idev 的「不把过程指标当验收」同源，已被 verify 只认红绿承载。
9. **与 idev 无关而不落的部分**：各家推理回传协议细节（DeepSeek/Kimi/GLM/Claude 的 thinking 规则，L527–532）、Responses API 的 `previous_response_id` 续接（L253–263）、状态更新替换 vs 追加的成本估算公式（L967–973）、dsh-superagent 细节、PPTX/写作 Skill 的制作流程（L808–836 属产线 Skill 治理，idev 用 propose→grill→land 已有更严路径）。
