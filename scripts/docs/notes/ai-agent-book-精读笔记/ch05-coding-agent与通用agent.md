# 《深入理解 AI Agent》第5章「Coding Agent 与通用 Agent」精读笔记

> 源：/tmp/ai-agent-book/book/chapter5.md，共 847 行。多Agent精读批。

## 一、本章主张

1. 通用 Agent 的架构判断：以 Coding Agent 为执行核心、以文件系统为工作空间，前一步落盘的产物是后一步的输入 (L5, L49–61)。
2. 代码生成是元能力：既产出新工具，也表达规则与推理步骤；规则写成表达式后可用几组输入逐项检验 (L7, L383)。
3. 同一操作已有 API/CLI 时优先代码调用，省去截图、视觉定位与点击；跑通且反复执行的操作固化为代码 (L45)。
4. 中间结果落盘的额外价值：用户改问相关问题时，可从合适的一步接着做，不必从头再来 (L61–63)。
5. 需要人和 Agent 共同维护的记忆，优先用可直接阅读的文件：能打开纠正、Git 溯源、比较版本、回滚 (L67)。
6. 目标较宽泛时先拆解、查瓶颈、量基线、确认约束，再定方案；方案要回答改哪些模块、为何适合、是否引入新依赖、如何验证与恢复 (L95, L99)。
7. 编码任务以通过验收为完成标准：写出补丁只是一步，测试、用户要求、交付物都要核对；回归用例必须暴露原问题并验证修复 (L103, L105)。
8. Harness 四件工程准备：验收基线、执行边界、结构化反馈信号、恢复手段 (L123–126)。
9. 任务清晰度与验证自动化度的四象限决定投入方向：先把任务推向「目标明确、结果可自动验证」象限；人工逐次验收成为吞吐上限，目标模糊时自动化可能持续优化错误指标 (L130–139)。
10. 经验沉淀为系统设计原则：可执行约束优先于提示词；优先投资自动验证；反馈越及时、越结构化越利于纠正；为变更设计恢复路径 (L152–157)。
11. 验收要同时检查结果与过程：清空数据可恢复服务却破坏数据保留；删实现可通过编译却丢功能 (L159)。
12. 恢复的第一问是「上一步留下了什么证据」；「请求已发出、远端已确认、结果已保存」三态分开记录才有恢复起点 (L167–169)。
13. 错误按层分类映射到恢复动作：API 层退避重试、工具层修输入、上下文层恢复真实记录、控制流层计数限深并升级 (L173–180)。
14. 重试阈值应从生产恢复分布确定，在拐点停止；恢复逻辑自身失败要靠重入标记、独立预算、全局迭代/时间/费用上限兜住 (L226–228)。
15. 跨厂商接续要以中立格式保存业务轨迹，任务事实与厂商协议字段分开，不透明字段留在原始记录 (L204–206)。
16. 独立工具调用可并行，但须等参数完整且校验通过再调度；两个工具同时改同一文件即写冲突，须由调度器识别 (L236–240)。
17. 交互式调试与持续服务任务默认用持久化终端；并行任务用独立会话；恢复任务时先检查昨天起的服务是否仍活 (L267–269)。
18. 文件写入后由工具层自动跑语法检查并把诊断作为工具返回值；检查范围随改动逐步扩大 (L271–275)。
19. 搜索能力先把 Grep、Glob 与按范围读取做好；语义索引是大库探索的补充而非起点；「用 grep 类接口」与「是否建索引」是两个设计维度 (L296)。
20. 编辑工具先从简单、确定性的旧字符串到新字符串开始：失败原因容易解释、差异便于复核；人类编辑器习惯不必成为模型工具的默认设计 (L327, L333)。
21. 提示注入致命三要素之外还有第四维：持久记忆会放大注入影响，记忆写入须记来源、适用范围与确认状态，读取时保留这些属性 (L343–345)。
22. 沙盒边界从网络出口默认关闭做起、按需放行；命令黑名单不足以为安全判断，须解析命令结构与参数用途 (L351, L359)。
23. 委托方忠诚需同时衡量信息保护与任务完成：只拒不完成或只完成不保护都是失败 (L369)。
24. 两种算法都能运行成功时，先确认统计口径才知道哪个数回答了用户的问题 (L381)。
25. Harness 该做多厚取决于模型在具体任务上的能力边界：模型已能稳定完成的推理加求解步骤只是开销；形式化转换出错会把原问题变成另一道题 (L424)。
26. 业务规则先由业务方确认含义，再写相邻边界用例（167h59m、恰好168h、168h01m）；真值校验放进执行接口让每次提交都过同一套规则，不依赖模型记得调独立检查工具 (L430–436, L501)。
27. 服务端按数据库真值和服务端时钟裁决；`expected_*` 参数只记录模型预期供比对与审计，不影响裁决；并发可能改状态，故提交时重新读取 (L505–507)。
28. 提议者—审核者分工在上下文管理上省钱：审核者只拿最新截图+标准+问题清单，主轨迹靠简短文本反馈推进（实验 5-6 同分但 2.4 万对 9.3 万 token）(L550, L556)。
29. 断言应对应需要验证的属性：日志里出现过退款检查只说明查过；「先查后退、检查结果允许、订单最终状态」才是要断言的——实验 5-11 里只断言调过检查的测试在错误版本上也通过 (L646, L658)。
30. 业务代码越容易被 Agent 动态改写，权限边界越应下移到稳定的数据访问层：即使生成代码出错，受信数据层仍强制实施权限；每次操作带可信访问上下文，所有连接与后台处理遵守同一访问范围 (L765–771)。
31. 生成 Agent 时保留一个没送给创建者的任务，分辨能力提升还是碰巧适应刚见过的题；优先复制经过验证的参考实现再做领域修改 (L791, L808)。
32. 把软件工程验证经验用于其他领域的三问：怎样发现错误、怎样恢复到已知状态、何时停下来请人接手 (L829)。

   - 拟落文案：「同一资源的授权检查不写在易被 Agent 重写的业务代码里，而沉到所有读写必经的受信数据访问层：生成代码出错也应被权限检查拦住；检查随资源走，不随每次改写的代码重走。」
   - 书里依据：L765–771（「业务代码越容易由 Agent 动态改写，最终的权限边界就越应下移到稳定的数据访问层」「即使生成代码出现错误，受信任的数据访问层仍能强制实施权限约束」）
   - 说明：T4 已写跨信任域主体映射与最小授权，缺的是「检查的落位层」这半句。idev 场景里对应的是写租约/专用入口已做、但产品仓代码内权限检查落位无判据。

2. **G2：断言不得弱化为「事件发生过」**
   - 落点：`conventions/canon.md` §6 F5 的「观察到」栏补一形态（不新增编号，挂靠 F5）
   - 拟落文案：「断言弱化为『工具/检查被调用过』而不断言其性质与结果（先查后退、结果允许、最终状态），视为自证式测试的变体，当轮重写。」
   - 书里依据：L646（「日志里出现过退款检查，只能说明程序查过。要知道这笔钱退得对不对，还得看程序是不是先查后退、检查结果是否允许退款，以及订单最终是什么状态」）、L658（只判调用过退款检查工具的测试在错误版本上也通过）
   - 说明：F5 现在只点名「断言从实现反推」；「断言降级为调用发生」是同一失败模式的另一张脸，书中实验给出了反例证据。

## 四、勘误与存疑

- L232 的 24.2s/8.1s 拆分依赖一款尚未制造的专用芯片推理速度估值，前提本身是假设性的；只作「测试占大头」的方向性佐证，不作为数据基准采纳。
- 实验规模普遍小（实验 5-4 84 题、实验 5-5 60 例、实验 5-16 单模型单任务），「Harness 厚度」「代码化规则」等通用结论方向合理，统计强度不足以支撑定量外推；采纳时按方向性参考。
- L414–422：骑士与无赖实验里「模型改对了程序却交不出答案」是模型/宿主边界的失败，书中如实标注；这类失败不是 Harness 能完全兜住的，归因时不应算到判据头上。
- 与 idev 场景无关、不作为缺口候选的部分：OOXML 办公文档、CAD 参数化生成、视频编辑流水线、SQL Artifact 与 ERP 查询、生成式 UI/A2UI/AG-UI、HMR 定制、快慢模型分工（产品/能力层）。
- L345 持久记忆第四维与既有 evidence.md 信任表、self-evolution 四件学习信号高度一致，无冲突。
