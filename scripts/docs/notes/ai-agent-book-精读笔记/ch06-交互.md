# 《深入理解 AI Agent》第6章「交互：观测与动作空间的扩展」精读笔记

> 源：/tmp/ai-agent-book/book/chapter6.md，共 900 行。多Agent精读批。

## 一、本章主张

1. 底层模型固定时，重新组织或扩展观测与动作接口，往往是提升 Agent 任务表现最有效的工程手段 (L3)。
2. 异步要处理三件事：长任务与交互分离；事件优先级；中断与恢复——保存任务状态、记录已发生的操作、恢复时重新检查仍然有效的条件 (L42–44)。
3. 主动服务要来得及时，最好由事件源在状态改变时通知 Agent；通知到达后 Harness 先检查是否重复、是否过期，模型再决定下一步 (L73)。
4. 把等待条件交给运行时（定时器/后台监控/事件通道），模型可以结束当前一轮；监控交给运行时、只在有用的进展、错误或停滞出现时唤醒模型，监控规则设过滤、合并与频率限制，避免每行日志引发一次模型调用 (L79–89)。
5. 多渠道通知设去重、静默时段与升级条件；通知记录与任务状态关联，用户能从收到的消息继续处理 (L107)。
6. 通用助理配置独立虚拟身份：便于单独授权、审计和撤销，误操作时更容易限制影响范围 (L111)。
7. 接入层统一事件进入系统之后的形态，保留各来源到达之前的能力差异 (L135)。
8. 「已验证」由适配器依签名、令牌或渠道账号判断，正文里的自我介绍不算；发送者在正文中自称「紧急」不改变权限 (L170, L245)。
9. 去重键的语义由来源决定：投递 ID 挡传输层重投，业务幂等键挡业务上的重复；顾客两次说「退款」是两条消息，只按客户端消息 ID 去重 (L143–148, L171)。
10. 接入层只在线程内承诺顺序；关联关系另设字段表达，不改写线程——事后合并线程要迁移数据，代价不小 (L178, L180)。
11. 适配器应当在事件写入接入日志**之后**确认来源；先写日志再确认，各来源投递保证收敛为 at-least-once，重投由去重键挡掉 (L184)。
12. 来源进度、分派进度、任务状态三种进度分开保存：把位点当作任务进度，重放日志时已经发出的回复会再发一次 (L189–196)。
13. 积压处理三规则：过期事件只记轨迹不唤醒模型；状态型事件同线程积压只交最新一条，消息型事件（人说的话、下的指令）不能丢弃；推送型来源的积压转到接入日志消化 (L200–204)。
14. 接入层去重的边界：能挡住哪些重复取决于适配器声明了什么去重键；没挡住的，靠任务状态判断 (L211–214)。
15. 事件驱动邮件处理把每次写操作和返回的回执记在同一封邮件名下；重启后发出请求却没回执，先核实实际状态再决定是否重发；既无幂等键又查不到已发送记录的渠道，只能把回复标为待人工确认 (L259, L277)。
16. 兼容同步接口时尽量保留正常调用与真实结果的配对，只在中途切换任务时补入状态响应；过早为每次调用填「仍在运行」会使轨迹充满未完成状态 (L292)。
17. 新设计的长任务工具把「启动」定义为一次完整操作，立即返回真实任务句柄——模型据此区分「已经启动」和「已经完成」，后续查询、取消和结果事件有关联依据 (L305–306)。
18. 多个事件一次进入上下文时模型可能只回应最后一条、遗漏前面：运行时保留各自处理状态、要求逐项检查、列出未处理项，处理后记录完成/等待/需澄清 (L312–321)。
19. 可靠异步三查：结果归属（延迟结果携带原调用标识并映射回任务）、恢复与取消（明确哪些后台任务继续、哪些停止）、多条要求（预算、人数等分别进任务状态，最终结果逐项检查这些条件）(L355–357)。
20. 约束变更后旧结果可能不含新答案：如果原查询已按旧条件筛掉 B，只在旧列表里改人数仍会漏选——条件影响到的取数步骤要重查 (L369, L377)。
21. 语音插问被回答后，原来的任务结果几乎没人再提及：运行时应记下尚未说出的结果，让前台答完插问接着报告 (L507, L509)。
22. 快慢模型分工中前台应区分「任务确认」与「业务结论」：快模型说出口的建议已进入用户判断，慢模型随后纠正需要解释变化并处理已产生的影响 (L517–519)。
23. 需要委派时，前台应把有把握的姓名、数字和用户刚做的更正写进任务说明（转写把「陈嘉怡」写成「陈佳宜」导致填错参数）；两份记录有出入时后台以任务说明为准 (L502, L509, L527)。
24. 交互能力与推理能力可以分别演进：前台持续改善听与插话，后台替换为更强推理模型即可跟上 (L555)。
25. Computer Use 的核心功课是每个动作跟得上眼前的界面：点击成功只表示这一击已发出，下一张截图的焦点才决定能否安全输入 (L583–585)。
26. 结构化信息完整时优先 DOM/无障碍树索引；页面刷新、滚动后须更新编号映射，避免使用过期编号 (L636, L655)。
27. 持续变化的界面把观测接口作为重点改进对象：动作间关键帧之外，持久文字描述对收益尤其关键——「页面出现通知」可能成功也可能失败，「同步失败，地址未保存」才保留决定下一步的线索 (L670–680)。
28. 机器人把任务顺序与眼前动作分开处理：高层规划与底层控制按各自合适的节奏运行 (L758)。
29. 机械臂运行完抓取程序只说明程序结束；抬升前还要通过夹爪反馈或新图像确认真的拿住。每个技能对应一个可检查的状态变化，规划器才能从实际出错的那一步恢复 (L776)。
30. 故障注入对照：开环执行只完成 205/384 回合；逐步检查全过、多花约 3 次调用；预测式执行没有比直接检查多挽回一个回合——先做直接检查，预测层不是免费的 (L840)。
31. 各交互形态共有的次序：获取观测→判断状态与执行时机→选择回复或动作→执行并取得环境反馈→继续、修正、重试、停止或重新规划 (L864–870)。

## 三、缺口汇总

1. **G1：约束变更后，旧结果不能只改参数套用**
   - 落点文件+节：`references/agents.md`「这一轮之外到达的事」节尾补一句（该节是回合外事件的既有权威页，无编号挂靠该节）
   - 拟落文案：「用户中途改了条件后，先前跑出的结果只能当参考：条件影响到的取数或执行步骤从那一步重跑，不在旧结果上只改参数。旧结果可能已按旧条件筛掉了现在需要的答案，对不上就以新条件重查。」
   - 书里依据行号：L369–377（实验 6-3：工具若只返回 20 人以上场地，“能容纳 12 人的 B 根本不在里面。这时只在旧列表里把人数改成 10，还是会漏选 B。如果原来的查询已经把 B 筛掉了，就得再查一次”）；L353–357（多条要求逐项进状态、最终逐项检查）
   - 说明：idev 已有「数据变了旧账失效」（`上下文失效:`）和「页面是上一张的」（空间时效），缺的是「约束变了、数据没变」这第三种时效。目标工具无筛选参数时（书中的实验情形），复用旧结果合法；有筛选时必须重查——判据落成「条件影响到的步骤重跑」而不是一律重跑。

## 四、勘误与存疑

- 实验 6-7 各场景仅 10 次重复、单模型组合（豆包前台+DeepSeek 后台），2.81s vs 6.96s 这类延迟结论只能作方向参考；实验明确指出「同一句好的」在上下文中的歧义靠转写无法分辨，这与 idev「继续/ok 不是答案」的既有规则同向，无冲突。
- L420 的排队模型（M/M/1，利用率 0.5→0.8 时 2s→5s）依赖到达泊松、服务指数分布假设，服务时间重尾或突发流量时低估积压；引用数字须附假设边界——与 canon T9「结论边界」判据一致。
- 实验 6-2 的事件调度由确定性脚本驱动，模型只做决策检查，其结论可信度高于同类纯模型实验；但「进度不超过 50% 的任务会被取消」是脚本设定而非学到的策略，避免把脚本规则误读为模型行为。
