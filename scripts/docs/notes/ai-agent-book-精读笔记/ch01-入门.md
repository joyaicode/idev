## 〇、前言主张

1. Skill 只在任务用得着时才加载相应提示词；工具多了以后让模型通过命令行调用，不在每次请求里列出全部定义 (introduction.md L15)。
2. Harness 把执行环境、当前时间和用户工作状态写进状态栏供模型决策；对编造结果、调错工具、漏掉指令和越权操作加执行约束 (L16)。
3. Loop 工程：一个 Agent 办事，另一个核对账单或订单，发现漏办就交回补办——proposer-reviewer 分工源自真实电话业务 (L17)。
4. 判断任务是否完成，要看这项行动在外界留下了什么结果（口头答应≠退款到账）；好的原则能够穿越模型的迭代周期 (L27)。
5. 建立系统的评估机制：一次成功可能是运气（客服恰好有权减免），用同一批案例反复比较新旧版本才能看出差异是否稳定 (L25)。
6. 积累工程优势的两个条件：选对能力要求足够高的真实业务并持续获得反馈；不以「弥补某一代模型短板」为主要产品价值 (L23)。

## 一、本章主张

1. Agent = LLM + 上下文 + 工具（功能组成）；Model + Harness（生产实现）；上下文由 Harness 组织后提供给 Model，工具调用由 Model 决策、Harness 校验调度 (L9, L25–29)。
2. Harness 五项功能：上下文管理、工具接口、约束、验证、纠正；前两项支撑运行，后三项提高可靠性 (L328–330, L338–344)。
3. 底层模型固定时，调整观测空间与动作空间是提升任务表现的重要工程手段：漏看事实→纳入数据；选错工具→合并重复接口 (L45)。
4. 观测空间的稀疏化是 Agent 设计的基本问题：持续观察环境，只把可能改变下一步行动的变化交给主模型 (L47)。
5. 工具按用途分五类：感知、执行、协作、事件触发、用户沟通；同一接口可兼具多种用途 (L85–95)。
6. 通用基础能力支持组合与探索；支付、删除、生产部署等高风险操作封装为参数清楚、权限受限、全程可审计的专用工具，必要时加预览与人工确认 (L126)。
7. 消融实验可检查各上下文组件的作用：工具定义提供可调用能力，工具结果提供环境事实，历史消息保存任务进度；历史推理信息的价值取决于能否从其他记录恢复依据 (L176–192)。
8. 方向认同、节奏务实：模型会持续接管 Harness 决策，但模型此刻的能力边界就是 Harness 此刻的价值所在；模型暂时做不稳的环节由 Harness 先补齐 (L144–146)。
9. Agent 学习机制三层：上下文适应（任务内）、外部产物 artifact（跨任务：知识文档/提示词/程序）、模型参数（训练）——同一次失败可先纠眼前、再成文档、最终进训练 (L150–162)。
10. 从演示走向生产，工程重心从接通上下文和工具转向约束、验证与纠正；权限、状态、验证和恢复是投入重点 (L381)。
11. 换提示词以前先看失败发生在哪里：模型误解约束→查指令；材料从未进上下文→查信息组织；丢已完成步骤→查运行机制——五个工程视角各自提供排查入口 (L395–407)。
12. 当候选模型都已能胜任任务时，模型之外的工程实践往往决定产品差异（LangChain 固定模型改 Harness 得分 52.8%→66.5%）(L409)。
13. 构建有效 Agent 三原则：保持简单（从最简单方案开始）、保持透明（沿执行记录可回查回执）、设计好工具接口（ACI：名称直观、参数配例、返回可决策）(L421–427)。
14. 工具设计借鉴防呆：枚举限制操作类型、参数校验、权限控制；含糊说明会在多轮调用中反复造成误用 (L429)。
15. 确认信息充分、工具可用后仍反复规划/工具错误，优先比较模型能力，再决定投入多少提示词与编排 (L437)。
16. 模型升级后应主动清理已失去作用的适配代码——原必要的格式翻译和修补步骤变成额外的调用、延迟和出错点 (L497)。
17. 结构的复杂度由业务约束和实际失败驱动：先给能力足够的 Agent 明确目标、必要上下文和可组合工具，评估发现稳定问题再加专门验证器、独立 Agent 或确定性流程 (L459)。
18. 护栏按生效位置分上下文层、执行层、数据层三层；分层的工程价值在于逐步减少安全性对模型判断的依赖，一道检查遗漏仍有机会在后续边界被发现 (L553)。
19. 安全关键的检查应放在模型上下文之外执行：不可信内容已影响模型判断时，同上下文自查会沿用受影响前提 (L562)。
20. 护栏的评估需要同时覆盖漏拦截与误拒绝——前者看危险请求是否被放行，后者看明确允许的任务是否被误拦 (L549)。
21. 人工介入两类触发：超过失败阈值（重试/操作次数达上限）、高风险操作；触发条件应写进执行规则，移交时提供原始目标、已完成步骤、当前结果、失败原因和待决定事项 (L578–580)。
22. 贯穿全书五设计模式：提议者—审核者、渐进式披露、只增不改、边界集+保留集、最小 diff+可回滚 (L608–616)。
23. 长时运行 Agent：初始化 Agent 设环境分解任务，执行 Agent 逐项推进，每个会话结束留进度记录和可接续产物，缓解跨上下文交接困难和过早宣告完成 (L600)。

## 三、缺口汇总

### 缺口 1：改指令/规则前先定位失败层

- **落点**：`conventions/evidence.md` 闭环第 1 步「猜想 → 用例 + 证据 → 复现」之前的排序判据，并入「排查递进」段。
- **拟落文案（判据式一句）**：改提示词、规则或 Skill 文案之前，先指出失败在哪一层——没说清（指令理解）、没看到（信息可达）、还是没接住（运行机制）；三层改法不同，不许先换提示词碰运气。
- **书里依据**：chapter1.md L395（「给一个失败的任务换提示词以前，可以先看失败发生在哪里。模型误解了一句约束，适合先查指令；整份账单从未送进模型，适合先查信息组织；任务中断后丢了已经做完的步骤，则要查运行机制」）。
- **挂靠**：并入 evidence.md「排查递进」既有段（不新增编号），作为猜想排序的前置一步。

### 缺口 2：门禁/护栏收紧要附误拦对照

- **落点**：`references/self-evolution.md`「学习信号写到哪里」→「三道边界」之后，或「提案路径」一节。
- **拟落文案（判据式一句）**：收紧或新增门禁、规则的提案，要附一条不该拦的任务在收紧后仍能通过的对照；只证明拦得住，不证明收得对。
- **书里依据**：chapter1.md L549（「护栏的评估需要同时覆盖漏拦截与误拒绝。前者关注危险请求是否被放行，后者关注明确允许的任务是否被误拦截」）。
- **挂靠**：并入 self-evolution.md 提案路径的判据（evolve.md「要改什么/不改什么/依据」中的「依据」面），不新增编号。

## 四、勘误与存疑

1. **L443「差距已经缩短到半年以内」**：作者对开放权重模型追赶速度的个人经验判断，无数据支撑且随时间漂移；采信时只当观点，不当判据。
2. **实验 1-1 的两次运行（L186–190）**：Kimi K3 与 DeepSeek V4 Flash 各一次，样本量 1；书里用「在本次运行中」限定，表述诚实，但「移除历史推理信息后仍正确」与「单位换算错百万倍」都是单次采样结果，读者不能外推为模型族结论。
3. **L9 / L51 产品细节（Manus、OpenClaw、Muse 等）**：产品能力与接口随版本变化快，与 idev 场景无关；引用时只取「产品能力增长来自观测与动作接口扩展」这一抽象，不引具体产品形态。
4. **L409 LangChain Terminal Bench 数据（52.8%→66.5%）**：单一基准、特定时间窗的数字，作者已注明出处与测试设置；作为「Harness 有价值」的例证可，作为可复现判据不可。
5. **L146「模型此刻的能力边界，就是 Harness 此刻的价值所在」**：口号式表述，无操作判据；idev 已有更严格的等价物（self-evolution.md 落点表按「能不能被写清楚」分流），不采纳原句。
6. **L596–598（Harness 五项功能与各章对应表）**：书的结构导引，与 idev 无对照价值。
7. **前言 L11「2026 年 9 月 Meta 推出 Muse」等产品时间线**：时效性陈述，与精读目的无关。
8. **与 idev 无关而不落的部分**：Computer Use / 手机助手 / 电话协商的模态细节（第六章域）、多 Agent 社会与经济形态（第十章域）、模型后训练（第八章域）。
