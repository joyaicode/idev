## 真缺口

1. **可变性是建模决策，默认纯值——引入可变状态须有显式理由（上下文需共享同一实体，或度量证明纯值方案成为瓶颈）**
   - 书中出处：PDF 第380–381页，第41章「设计改变结构体的函数」41.1「为什么改变结构体」
   - 关键论据：书给出两条规则：多数情况纯值方案更简单清晰、易于测试；只有当纯值造成性能瓶颈或上下文确需共享同一实体时才用变化器。「这两条规则并不是泾渭分明的……我们必须考虑哪种方案更易于编程」；「如果这种决定导致了性能瓶颈，也仅仅在此情况下，我们才选择另一种方案」。即可变性是权衡后的决策，不是默认。
   - 建议落点：canon.md §3 在 T13 之后新增 T14「可变性默认纯值」，DO 写两条准入理由（共享同一实体 / 度量出的瓶颈），DON'T 写「无理由引入可变状态」。
   - 与最相近现有条目的区别：T9 只裁决「优化的时机」（先正确再度量），不规定建模层的可变性默认值与准入理由；T10 是数据系统五项权衡（真相之源/副本/失败语义/一致性/Schema 演进），不含「实体可变性」这一项；canon.md §2 把「新增并发、锁、共享可变状态」当排查信号指向 T10/T11——真源认得可变状态的风险，却没有规定它何时才被允许引入。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/canon.md` §3 新增 T14「可变性默认纯值」，DO「默认写纯函数，值进值出；引入可变状态只认两个准入理由：① 共享同一实体（跨线程 / 请求 / 多消费方必须看到同一份），② 度量出瓶颈（有数字）」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

2. **受约束数据定义——多个消费函数都在处理同一非法输入时，修正数据定义使非法表示不存在，而不是到处加分支**
   - 书中出处：PDF 第118页，第12章 12.3「问题泛化与函数泛化」
   - 关键论据：多边形例子中，初始数据定义允许空表，导致每个消费函数都要处理空表分支；书指出「empty 并不代表多边形」，把数据定义改为「至少一条边」后，非法情况从类型上消失——「数据定义的修改使我们更接近于目标，编程更简单」。
   - 建议落点：domain-modeling.md「聚合根」小节后新增「受约束数据定义」段：触发信号（同一非法输入分支在 ≥2 个消费函数重复出现）与纠正（收窄数据定义/类型，让非法状态不可表示）。
   - 与最相近现有条目的区别：coding.md 底线5 拒绝「哑对象」（类型只有 get/set、无不变量），管的是新类型设计时的行为完备；P1 管「构造时校验、非法即抛」。两者都默认数据定义已定，只管住入口；本条管的是存量数据定义过宽、分支在消费方散布时「向上修正数据定义」的触发器，真源无此信号。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/domain-modeling.md` 新增「受约束数据定义」小节「同一非法输入分支在 ≥2 个消费函数重复出现 → 收窄数据定义使非法不可表示：构造即校验、类型收窄、去掉宽松默认」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

3. **相等语义显式化——契约涉及「同一实体/相等」时须声明按值还是按身份；比较代码须选对级别**
   - 书中出处：PDF 第398–399页，第42章「相等」42.1「外延相等」、42.2「内涵相等」；PDF 第401页，第43章 43.1（测试原则框）
   - 关键论据：「其实有两种相等的概念……对程序设计者来说，理解这两种相等的概念是至关重要的」；外延相等＝组成部分相同；内涵相等「不仅仅需要两个结构体由相同的部分组成，还要求它们对结构体的变化器同时作出同样的响应」（同一实体/别名）；测试原则框：「当比较对象的恒等性时，使用 eq?。对于其他的测试，使用 equal?。」
   - 建议落点：domain-modeling.md 新增「相等语义」小节（契约/术语表须声明值相等或身份相等，身份相等不可用值相等替代）；java.md Qodana 表增补一行（`==` 误比较内容 | 身份比较用 `==`，值比较用 `equals`，契约写明用哪种）。
   - 与最相近现有条目的区别：domain-modeling.md 现有条目管术语唯一、上下文边界、聚合根，无相等语义；T5 管命名统一，不管语义声明；java.md 全文无 equals/`==` 选择指导；C15 管「名字与契约一致」，不管比较级别选错。别名可见性问题（改 A 则 B 变）是真源完全未覆盖的建模坑。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/domain-modeling.md` 新增「相等语义」小节（每个领域类型声明值相等或身份相等，身份相等禁止用值相等替代）+ `conventions/java.md` Qodana 表增补「用 `==` 比较对象内容」行（身份用 `==`，值比较用 `equals`）。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

4. **终止论证——非结构化遍历的循环/递归必须附「每步输入严格变小」的论证，无论证即不完整**
   - 书中出处：PDF 第238–239页，第26章「设计算法」26.1「终止」
   - 关键论据：结构递归天然终止（输入按数据定义每步变小），生成式递归（生成新子问题）则可能不终止；「在设计算法的诀窍中，还需要另外一个步骤：终止论证」「如果没有这样一个论证，我们就认为算法是不完整的」；quick-sort 以「每次递归的输入严格短于原输入」完成论证。
   - 建议落点：coding-tables.md §2 新增 C20：气味＝循环/递归的收敛不依赖输入结构而依赖状态变化（无度量变小的说明）；纠正＝写出每步严格变小的论证（自定度量），否则改用结构化遍历。
   - 与最相近现有条目的区别：C9 管嵌套可读性，§2.4 圈复杂度数分支，都不问「循环是否必然前进」；T9 管优化要有数字，不管算法完整性；C19 管资源对偶。真源无任何条目覆盖死循环风险，而这是工作流引擎、重试循环、遍历收敛的真实事故源。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding-tables.md` §2 新增 C20「迭代 / 递归的收敛依赖隐式状态变化，说不出『每步严格变小』」，纠正「写每步严格变小的论证（进度度量写在注释或测试）；写不出就改结构化遍历」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

5. **计算与效果分离——有副作用的函数不得夹带业务计算，计算拆为纯函数，赋值处只留一行效果**
   - 书中出处：PDF 第324页，第36章 36.4「改变记忆的函数」
   - 关键论据：「对于其他情况，最好设计一个（没有效果的）辅助函数，读入状态变量当前的值以及函数参数，返回新的状态变量的值」——示例把颜色轮换逻辑全部放进纯函数 next-color，赋值压缩为 (set! current-color (next-color current-color)) 一行；并警告「状态变量永远不会是某个函数的参数」（防止状态变量混入计算函数形参）。
   - 建议落点：coding-tables.md §2 新增 C21：气味＝效果函数同时做业务计算，可变性与计算纠缠；纠正＝拆出纯计算函数（参数进、值出），副作用处只留一行赋值/提交。
   - 与最相近现有条目的区别：C1 管「一个函数两个变更理由」，不特指效果与纯度的纠缠；C11 管分层位置（Controller 不做业务）；T3 深模块管接口形状。真源没有「效果函数里的计算抽成纯函数」这条，而它是让 T14（默认纯值）在局部可落地的配套纪律。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding-tables.md` §2 新增 C21「效果函数（落库 / 发布 / 写状态）里夹带业务计算」，纠正「拆纯函数：计算进纯函数可单测，效果函数只留一行副作用」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

6. **do/undo 成对——探索性修改可变状态时，修改与复原同层成对实现，且复原可证明回到原状态**
   - 书中出处：PDF 第420–421页，第43章 43.3「状态的回溯」
   - 关键论据：「设计一对函数，一个函数修改问题表示法的状态，另一个函数在尝试失败时取消这种修改」；并以等式 (begin (place-queen CB i j) (unplace-queen CB i j) CB) = CB 论证 do/undo 复合恒等地回到原状态（并指出复原顺序敏感）。
   - 建议落点：coding-tables.md §2 在 C19 增补：资源获取/释放成对之外，可变状态的探索性修改同样成对——修改与还原（do/undo）同层实现，且以等式或测试证明复原回到原状态。
   - 与最相近现有条目的区别：C19 现文只覆盖资源（文件/连接/锁）的获取与释放；可变状态的试探-回退（回溯搜索、事务内试探、乐观写入）是同构问题但未被点名。增补使 C19 从「资源对偶」泛化为「状态改变对偶」，改动最小。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding-tables.md` §2 C19「气味信号」增补「状态修改与复原不同层」，「纠正」列增补「do/undo 同层，复原正确性用等式或测试证明能回到原状态」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

7. **效果与不变式注释必写——「代码看不出的那一句」点名两类：可变状态的改写效果、循环/累积器维持的不变式**
   - 书中出处：PDF 第324页，第36章 36.4（效果合约）；PDF 第288页，第31章（累积器不变式定义）；PDF 第381页，41.2；PDF 第402页，43.1（区间化）
   - 关键论据：「除了要说明函数读入和返回的东西，必须写明它影响了那些变量，以及它是怎样影响这些变量的」；41.2「设计含变化器的程序需要把效果结合起来……关键是要在程序的合约中加上定义明确的效果说明，并构造能说明效果的例子」；「累积器不变式描述了函数的参数、当前辅助函数的参数以及……必须维持的累积器三者之间的关系」「没有累积器不变式就无法给出带累积器的函数」。

   - 与最相近现有条目的区别：C5 管「注释过期则删改」，不规定效果说明必须存在；底线4 现文只说「为什么、哪条不变量」，未点名可变状态改写效果这一最大类必写项——效果恰恰是读代码看不出来的信息，点名后 review 才有据可查。

8. **测试断言无多余效果——测可变状态时，断言除「期望效果发生」外须含「未触及部分保持原状」**

   - 关键论据：add-to-address-book 的测试要「判断……是否对 address-book 产生了正确的效果，而且没有多余的效果」；给出两种方法：直接比较新旧地址簿，或保存旧值、检查特定条目已添加且其余部分保持不变。

   - 与最相近现有条目的区别：T6 现文管断言的来源，不管效果测试的完备维度；F5 管「从实现反推断言」的自证问题；evidence.md 闭环第4步「不该变的路径保持原行为」是排查修复语境，编码护栏（写新效果代码时的测试设计）缺这句——效果测试最容易漏的恰是「多余效果」维度。

9. **自底向上测试顺序——先严格测试被调用者，再测调用者，失败时定位面小**
   - 书中出处：PDF 第114页，第12章 12.1「设计复杂的程序」节末尾
   - 关键论据：「我们应该在测试一个函数之前严格测试被它调用的其他函数，这样可以减少此后逻辑错误的定位时间」——测试顺序影响排障成本，自底向上使失败最先指向责任函数。
   - 建议落点：coding.md §0「编码」步骤增补一句：自测从依赖底向上（先测被调用者再测调用者）。
   - 与最相近现有条目的区别：T6 管「先有测试再改」（护栏时序），R1 管测试覆盖的触及面，evidence.md 猜想排序管排查时的检查顺序——都未规定测试执行顺序本身；这是纯增量一句，补齐「测试怎么跑」的空档。
   - **落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding.md` §0 步骤6 增补「自测自底向上：先测被调用者（最底层纯函数），再测调用方组装；跳层直接测顶层，失败定位不到层，不算自测」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

10. **状态初始化位置决定生命周期——可变状态在创建点/外层作用域初始化一次则跨调用持久；在方法体/内层作用域每次初始化则每次调用重置**
   - 书中出处：PDF 第343–358页，第38章「设计使用记忆的函数」flip1/flip2 对照；辅证第37章 37.1「状态的初始化」（PDF 第327–342页）与第39章「封装」（PDF 第359–366页）
   - 关键论据：flip1 把 `state` 定义在 `lambda` 外层 → 每次调用翻转 0/1/0；flip2 把 `state` 定义在 `lambda` 主体内 → 每次调用重建、恒返回 0。书结论：「用 local 表达式定义的函数与主体包含一个 local 表达式的函数是不同的。前者……定义在这个函数中存在且仅存在一次。反之，后者在每一次计算函数的主体时建立一个新的（最外层）定义。」第37章 37.1「第一步是要定义状态变量，并指定每一个变量的用途」；第39章「通过把状态变量放入 local 表达式，保证了它只能按照服务管理进行改变，而不能被任意赋值修改」。
   - 建议落点：canon.md §3 在 T14 的 DO 列增补一句（不新增编号）：可变状态的初始化位置即其生命周期——创建点/外层作用域初始化一次则跨调用持久；方法体/内层作用域每次初始化则每次调用重置。持久状态初始化放在创建点，不在每次调用里重设。
