## 三、真缺口

### 缺口 1｜重构进行中的「停止与回退」纪律

**①出处：**PDF 第 434–436 页，第 15 章「结语」（重构的节奏、「得道」）。
**②论据：**「得道」的标志是你可以自信地停止重构——目标是让系统更易理解，不是「探索真善美」，达成即停；「如果你没有把握，无法证明自己所做的一切能够保持程序原本的语义，此时就应该停下来。如果代码已经改善了一些，就发布你的成果；如果没有，就撤销所有修改」；重构失控时：「停！……回到最近一个没有出错的状态，然后逐一重复刚才做过的重构项，每次重构之后一定要运行所有测试」「第一次重构用了一小时，重复它只需十分钟」。
**③建议落点：**coding-tables.md §3.1 R 系列新增一条（编号待统筹，暂记「R7 停止与回退」）：重构进行中的判停（目标达成或语义无把握即停，已改善部分可交付）与失控恢复（回退到最近全绿点，小步重来，每步全绿）。
**④与最相近条目的区别：**R4 管「单步」步幅与全绿门，管不到整个重构会话何时该停；T6（无法补护栏→缩小步子/停并标 UNPROVEN）与 F6（无护栏大改）均为开工闸门；§3.2 尾注「程序能跑且长期不会改→不必重构」管事前取舍——均不覆盖进行中状态的判停与失控后的回退程序。

**落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding-tables.md` §3.1 新增 R7「会停会退」：「目标是让系统更易理解，达成即停，不为『探索真善美』深挖；对语义保持无把握即停：已改善部分可交付，无改善即撤销全部。失控时回退到最近全绿点，小步重来，每步全绿」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

### 缺口 2｜重构前提失效判据（何时该重写而非重构）

**①出处：**PDF 第 91 页，2.5「何时不该重构」。
**②论据：**「重写（而非重构）的一个清楚讯号就是：现有代码根本不能正常运作……重构之前，代码必须起码能够在大部分情况下正常运作」；代码糟到无法重构时，折中方案是先封装成组件隔离，再对组件逐一决定重构或重写。
**③建议落点：**coding-tables.md §3.2 做/不做表增一行「不做」：代码无法大部分正常运作（无行为基线可保）→ 不进入重构，走重写/替换流程；边界情形先隔离封装再逐组件裁决。
**④与最相近条目的区别：**canon.md §4 念头表「旧的太乱，重写」行管重写的执行纪律（先用测试钉旧行为、小步替换可回退、警惕第二系统效应），T2 管先读后写沿用现状；§3.2 不做表管「何时不动手」（烂设计硬堆功能、不动模块只为评分）——均无「重构前提本身失效（代码不能大部分正常运作）」的前置判据；R 系列默认重构可行，缺前置门槛。

**落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding-tables.md` §3.2 做/不做表增一行「不做」：「代码无法大部分运作：先封装成组件隔离，再逐组件决定重构或重写（重写走念头表『重写』行：先测试钉旧行为）」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

### 缺口 3｜性能优化小步化+单步无提升即撤销

**①出处：**PDF 第 94–95 页，2.7「重构与性能」；另 PDF 93–94 侧栏「劳而无获」。
**②论据：**「和重构一样，你应该小幅度进行修改。每走一步都需要编译、测试、再次度量。如果没能提高性能，就应该撤销此次修改」；持续关注法 90% 的优化是白费功夫；「劳而无获」案例：臆测的性能瓶颈全错，实测发现一半时间耗在重复创建日期对象上。
**③建议落点：**canon.md T9 DO 增补一句：优化亦小步进行，每步重测，无提升即撤销该步；不做与度量无关的顺手优化。
**④与最相近条目的区别：**§3.2 做表已有「性能：先测量，再只动热点」，§3.3 已有「性能与重构分离」，T9 已有基线/目标/测量/再测与投入上限，但都缺「无提升即撤销该步」的单步回滚语义——T9 的「再测」只用于确认达标，未规定不达标时的动作。

**落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/canon.md` §3 T9 DO 增补「优化亦小步进行，每步重测，无提升即撤销该步」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

### 缺口 4｜YAGNI 的例外边界：难事后重构的维度设计期投入

**①出处：**PDF 第 90–91 页，2.4「重构的难题」（难以重构的设计改动）；PDF 第 92–93 页，2.6「重构与设计」。
**②论据：**「问自己：将某个设计重构为另一个设计的难度有多大？……如果预先看不到简单的重构办法，就在设计上投入更多力气」（安全系统例子：等出事再重构已无意义）；「你不必预先实现灵活方案，而是问：把一个简单的解决方案重构成这个灵活方案有多大难度？如果答案是相当容易，就只实现目前的简单方案」。
**③建议落点：**coding.md 文首「裁决先于模式」句后增补：YAGNI 只写当下的前提是「该维度重构距离近」；对安全等难以事后重构的维度，设计期按风险预置（作为 T1 的例外边界）。
**④与最相近条目的区别：**T1 DON'T「为未来需求预置扩展点」与 coding.md 文首「裁决先于模式（YAGNI + Rule of Three）」表达了默认不预置；P6/底线 3 管单实现写具体与依据可说——但均缺「何时例外、该预置」的反向判据，即「重构距离」：预置与否取决于事后把简单方案重构成灵活方案的难度。

**落地状态（已提交）**：本缺口已在 commit `bef5291`（feat: land self-evolution and book distillation updates）落地——`conventions/coding.md` 文首增补「YAGNI 的例外：预置与否看『重构距离』——把简单方案事后重构成灵活方案相当容易的维度，只写当下；预先看不到简单重构办法的维度（安全等），设计期按风险预置」。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。

### 缺口 5｜领域数据成团裸传播（数据泥团+基本类型偏执）

**①出处：**PDF 第 105–106 页，3.8「数据泥团」；PDF 第 106–107 页，3.9「基本类型偏执」。
**②论据：**3.8 判据：「删掉众多数据中的一项，其他数据有没有因而失去意义？如果不再有意义，这就是个明确信号：应该为它们产生一个新对象」；同生共死字段在多个类、多个签名中反复出现。3.9：「对象技术的新手通常不愿意在小任务上运用小对象」——以 money 类、range 类、电话号码/ZIP 等特殊字符串为例，裸基本类型使语义与约束无处安放。

**④与最相近条目的区别：**§2.4 参数 ≤3 只管数量（「缺值对象」仅括号暗示，无数码判据）；C10 管魔法字符串重复，不管「概念无类型」；底线 5/哑对象管「行为放哪」，不管「数据成团无家」；T5 管概念不建双轨，不管概念不建模——C 系列现有 19 条均为行为/结构/流程气味，无一条数据建模气味，这是真空白。

### 缺口 6｜被测试引用救活的投机符号

**①出处：**PDF 第 108–109 页，3.13「夸夸其谈未来性」末段。
**②论据：**「如果函数或类的唯一用户是测试用例，这就飘出了坏味道 Speculative Generality。如果你发现这样的函数或类，请把它们连同其测试用例一并删掉。但如果它们的用途是帮助测试用例检测正当功能，当然必须刀下留人」。
**③建议落点：**coding-tables.md C6 增补一句：生产符号（函数/类/方法）仅被测试引用、无生产调用路径 → 同判未使用，连同其测试一并删；测试辅助/fixture 及断言直接触达的目标不在此列。
**④与最相近条目的区别：**C6 判「未使用」若只看无生产引用，投机符号会被测试引用救活——本条补上「测试是唯一用户即投机」的判别与豁免；F5 管断言是否验证真逻辑，不管符号存活性；T1/P6/底线 2 管新增时闸门，不管存量清理。

### 缺口 7｜查询与修改分离（Command-Query Separation）

**①出处：**PDF 第 279–282 页，10.4「将查询函数和修改函数分离」。
**②论据：**「任何有返回值的函数，都不应该有看得到的副作用」（Meyer 的 Command-Query Separation）；「如果你遇到一个『既有返回值又有副作用』的函数，就应该试着将查询动作从修改动作中分割出来」；多线程下查询函数夹带副作用会引入额外锁开销；书中明确豁免「缓存查询结果」这类不可观察副作用（「虽然这种做法改变了对象的状态，但这一修改是察觉不到的，因为无论如何查询，你总是获得相同结果」）。范例：`foundMiscreant()` 既返回入侵者名字又 `sendAlert()`，拆成 `foundPerson()`（查询、无副作用）+ `foundMiscreant()`（修改、void）。
**③建议落点：**coding-tables.md C21 增补双向覆盖：现有 C21 只判「效果函数（落库/发布/写状态）夹带业务计算」一个方向；增补反向「查询函数（返回值）夹带可观察副作用（发通知/写日志/改共享状态）→ 拆成查询（返回值、无副作用）+ 修改（副作用、不返回值）」，缓存等不可观察副作用豁免。
**④与最相近条目的区别：**C21 管「修改函数夹带计算」（modifier + query）一个方向；本条补「查询函数夹带副作用」（query + modifier）的另一个方向——`getTotal()` 里写缓存/发通知/记日志正是 C21 抓不到的形状；T14 管「可变状态准入」（值进值出），不管「返回值 + 副作用」的函数形状；T5 管命名成本（`get*` 暗示轻量），不管副作用本身。
**落地状态（已提交）**：本缺口已在 commit `88cc428`（feat: land deadlock avoidance (T10) and command-query separation (C21) gaps）落地——`conventions/coding-tables.md` §2 C21「纠正」列增补命令/查询分离（CQS）双向覆盖。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。
