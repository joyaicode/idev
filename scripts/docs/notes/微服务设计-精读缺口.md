## 三、真缺口

### 缺口1｜测试套件配比（金字塔）

- **出处**：第 7 章 测试金字塔（p121-160 L469-480）；场景测试（L687-701）。
- **论据**：金字塔不只是分类学，是配比——下层比上层多一个数量级；端到端慢、脆、贵，堆成倒金字塔后全量慢、随机挂、没人敢常跑。端到端只留低两位数核心场景，且测**场景**（一次旅程）而非逐条**故事**（每个故事一条端到端）；失败自上而下定位，护栏修到最低层可快速重跑。
- **建议落点**：coding-tables.md §2 新增 C28（场景测试并入纠正侧）。
- **与最相近条目的区别**：C26 管单个测试体怎么写（一测一方向、命名、消息）；T6 / R1 管改结构前护栏是否存在；都不管**整个套件**的数量配比与层次结构。

### 缺口2｜脆弱测试的处置

- **出处**：第 7 章 脆弱测试（p121-160 L589-615）。
- **论据**：随机失败重跑即过、被注释 / 跳过 / 长期红灯、团队习惯性忽略——被习惯性忽略的红灯比没有测试更糟（给人有护栏的错觉）。处置要当轮化：要么修稳，要么移出套件并记录用什么更小范围测试取代。
- **建议落点**：coding-tables.md §2 新增 C29。
- **与最相近条目的区别**：C26 管测试怎么写；R1 管护栏前提；C29 管**已有测试的腐化**（随机失败、红灯被忽略）怎么处置。

### 缺口3｜mock 与 stub 的区分

- **出处**：第 7 章 mock 与打桩（p121-160 L493-514）。
- **论据**：术语混用导致过度 mock——mock 验证交互、stub 供状态 / 应答。打桩优先：stub 供测试所需状态，不验交互；mock 只验对外副作用（请求是否被正确发出）。断言绑定内部交互细节的测试一重构就碎，是 F5 自证式测试在打桩维度的表现。
- **建议落点**：coding-tables.md §2 新增 C30。
- **与最相近条目的区别**：F5 / evidence.md 管断言从哪来（契约 / 用户现象）；C30 管**打桩方式的选择**（stub 优先、mock 只验对外副作用）。

### 缺口4｜密钥与敏感数据卫生

- **出处**：第 9 章——每服务凭证（p161-200 L195-197）、硬编码 / 共享密钥（L233-235）、密钥不与被保护数据同库（L359-370、L390）、哪些数据可入日志（L374）、落盘前剔除敏感字段（L407-408）、黄金法则「不要实现自己的加密算法 / 协议」（L556-561；另 L338-341、L356-357「实现不好的加密比没有更糟」）。
- **论据**：三件卫生——密钥放哪（独立于代码与数据，每服务自己的凭证，泄露只撤销受影响一组）、什么进日志（先定哪些数据可入日志，落盘前剔除敏感字段）、用什么加密（只用平台内建 / 公认实现，自研加密比没有更糟）。
- **建议落点**：coding-tables.md §2 新增 C31（黄金法则并入纠正侧，不另立条）。
- **与最相近条目的区别**：T5 命名细则管标记（`plaintext_` 前缀）不管存放；T11 管日志结构与关联标识，不管日志内容安全；coding-tables.md 的 Java 安全 skill 路由指向外部技能，不是条目。

### 缺口5｜关联标识（T11 增补）

- **出处**：第 8 章 关联标识（p121-160 L1240-1299、L1386）。
- **论据**：跨服务调用链用同一关联标识贯穿并写入结构化日志；须标准化强制执行（L1276）；「常常直至问题出现才知道需要它，而且在后面很难加装」（L1289-1293）——所以第一版就带上。
- **建议落点**：canon.md T11 DO 增补一句（沿用 T5 / T14 增补先例，不新增条目编号）。
- **与最相近条目的区别**：T10 管跨服务一致性；T11 现有 DO 只保证**有**结构化日志，不保证跨服务**可串联**。

### 缺口6｜外部依赖超时与连接池上限（T11 增补）

- **出处**：第 2 章 2.5.3 架构安全性（p001-040 L1707-1718：L1708-1711 每个下游服务用自己的连接池、L1712-1717 返回码区分三类请求——正常处理 / 识别错误未处理 / 服务宕机；L1711 指向第 11 章深化，本批只落轻量版）。
- **论据**：无界等待会把下游故障拖垮整条调用链——一个下游挂了，调用方的线程与连接被占满，故障沿调用链向上传导（L1708-1709「一个运行异常的服务可能会毁了整个系统」）。超时 + 连接池上限是轻量防线；返回码可区分正常 / 业务错 / 下游不可用三态（L1715-1717），调用方才知道该重试还是快速失败。断路器等重手段留第 11 章批次。
- **建议落点**：canon.md T11 DO 句尾追加 + DON'T 追加「外部调用不设超时与资源上限」+ §2 信号行 + §4 念头行（沿用缺口5 T11 增补先例，四处同步）。
- **与最相近条目的区别**：T10 管重试幂等；T8 管快速失败；T11 现有 DO 只管观测，不管资源上限与故障传导。

### 缺口7｜拆分沿业务能力走（§4 首行增补）

- **出处**：第 3 章 松耦合高内聚沿业务能力切（p041-080 L94-116）、先粗后细（L228-231）、模块先行（L184-195，洋葱架构 L278-300 是同一路径的 DDD 版）。
- **论据**：按技术层切（UI / 数据库 / 业务逻辑各成服务）会把一个变化原因拆到多个服务；沿业务能力 / 限界上下文切，变化落在单服务内。边界拿不准时先粗粒度，在单块内用模块画出来，稳定后再拆——拆错了再合并的代价比模块挪边界高一个量级。
- **建议落点**：canon.md §4 念头表首行「拆成微服务 / 拆库」动作列追加，不加新行（首行已有 T1 T4 T12 拦截拆分决策，只补方向与方法）。
- **与最相近条目的区别**：念头表首行管**要不要拆**（变化原因 / 边界成本谁付）；此增补管**往哪拆**（业务能力而非技术层）与**什么时候拆**（先粗后细、模块先行）。

### 缺口8｜先功能后数据（domain-modeling.md 增补）

- **出处**：第 3 章 先功能后数据（p041-080 L216-222：L216 不从共享数据角度考虑）。
- **论据**：划边界第一问是「这个上下文做什么用」（业务能力），第二问才是「需要什么数据」。按数据切分起步会得到贫血 CRUD 服务——数据库形状绑架服务边界。
- **建议落点**：domain-modeling.md 限界上下文清单首位插入一条。
- **与最相近条目的区别**：该页管边界怎么划（同名概念转换、跨上下文依赖走接口）；此条是划界的第一问，与既有清单项正交。

### 缺口9｜协同优于编排（§4 念头表新增行）

- **出处**：第 4 章 4.5 编排 vs 协同（p041-080 L431、L449-450 协同定义、L460 中心控制点职责过重、L492-494「重量级的编排方案都非常不稳定且修改代价大……倾向于使用协同」；第 4 章小结 p081-120 L125「相比编排，优先选择协同」）。

### 缺口10｜跨边界容忍重复（T7 DO 增补）

### 缺口12｜中间状态显式建模（§4 念头表增补）

- **出处**：第 5 章 5.12.4（p081-120 L530-542；核心 L537-542「避免纯技术角度，显式创建概念表示事务……『处理中的订单』围绕它管理端到端操作及异常」）。

### 缺口14｜按团队能自主变更的边界拆（§4 念头表首行增补）

- **出处**：第 10 章 10.1 康威定律（p161-200 L626-627「设计系统的组织……产生的设计等同组织内外沟通结构」；L684 跨团队共拥一个服务→每次变更都要跨团队协调→协调成本压垮变更意愿→大家停止更改）。
- **论据**：系统结构终将同构于组织沟通结构。技术上合理的边界若横跨多个团队，每次变更都要跨团队协调，协调成本会压垮变更意愿——拆了也白拆。按团队**能自主变更**的边界切，服务所有权落到能低成本变更它的团队。

### 缺口15｜架构性安全三件套（T11 DO/DON'T 增补）

- **出处**：第 11 章 11.4 架构性安全措施（p161-200 L1035-1041 概念与级联故障故事、L1062-1064 慢响应是最坏的故障模式、L1071-1082 共享连接池 worker 耗尽、L1085-1086 修复三件事＝超时 + 舱壁 + 断路器）、11.5.2 断路器（L1140-1143 失败达阈值即打开 / 快速失败 / 试探恢复，L1185-1191 失败定义取超时或 5XX、阈值与恢复判定，L1192-1195 同步链路快速失败降级 vs 异步作业排队稍后重试）、11.5.3 舱壁（L1205-1208 每个下游独立连接池、L1234-1235 舱壁最重要——第一时间确保资源不成为限制）。
- **论据**：一个慢下游能让整个系统宕掉——所有 worker 等超时、请求继续涌入、阻塞队列越积越长（800 连接拖死 40 并发，L1071-1077）。标准化三件套：超时（已有）＋舱壁（连接池按下游独立，一个下游拖不垮其它下游）＋断路器（失败达阈值就熔断：停止调用、同步链路快速失败降级、异步作业排队稍后重试；恢复靠试探而非立即放行）。
- **建议落点**：canon.md T11 DO 第三句扩写 + DON'T 追加「所有下游共享一个连接池」；不新增 §2/§4 信号行。
- **与最相近条目的区别**：T11 既有 DO 管超时与回滚 / 降级开关（事前预防 + 事后动作）；此增补补**故障隔离与熔断判定**——舱壁管一个故障不传染，断路器管不给不健康的下游续压。

### 缺口16｜现实近似 + 不自研协调系统（§5 补充启发增补）

- **出处**：第 11 章 11.11.6 真实世界（p201-231 L530-543：账面 99 张 vs 货架 98 张——「无论系统本身如何一致，也无法知道所有可能发生的事情，特别是保存的是现实世界的记录」）、11.11.2 牺牲可用性（L485-491「不让好朋友实现自己的分布式一致性数据存储」；自研 CP 存储＝读论文 + 博士学位 + 几年试错，用现成工具或放弃一致性构建 AP 系统）、11.13（L634-636「不应实现自己的分布式协调系统」）。
- **论据**：对现实世界的一致性本就是近似——强一致的库存系统也挡不住专辑掉地上被踩坏；能容忍最终一致就不付强一致的价。分布式一致性 / 协调是数学证明级难题，自研与自研加密同罪，用现成工具（Consul / Zookeeper）或放弃一致性。
- **建议落点**：canon.md §5 补充启发 YAGNI 条后追加「现实近似」。
- **与最相近条目的区别**：§5 既有项管通用取舍心态（YAGNI、可运行性）；此条管**一致性的价**——先问现实容忍多少偏差再选 AP/CP，别把强一致当默认正确答案；T10 管单次调用的一致性等级，此条管要不要为更强一致性付费的系统级视角。

### 缺口17｜幂等落在业务操作（§4「重试一下」行增补）

- **出处**：第 11 章 11.6 幂等（p161-200 L1244-1247 定义——多次执行影响＝一次、L1258-1270 示例——加 100 积分不带标识则重发多加，带 forPurchase 4567 则同一订单只入账一次、L1277-1278「业务操作是幂等的，而不是整个系统状态的」、L1279-1282 GET/PUT 幂等是规范定义不是免费保障）。
- **论据**：重试的前提是幂等，而幂等落在**业务操作**上：带业务标识（如 reason/forPurchase）让重复调用可识别为同一笔，重复执行影响＝一次。不靠 HTTP 动词语义——用了 PUT 不等于自动幂等。
- **建议落点**：canon.md §4「重试一下」行动作列扩写。
- **与最相近条目的区别**：该行既有动作管**该不该重试**（确认 T10 一致性等级）；此增补管**重试安全的前提**——没幂等的重试是在放大故障；T10 只提幂等概念，此增补落业务标识手法。
