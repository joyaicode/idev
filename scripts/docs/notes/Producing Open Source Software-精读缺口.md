## 三、真缺口

### 1. 安全修复发布的“最小变更 + 协调披露”纪律

**书中依据**：

- L13328–L13366：安全漏洞不能按普通 bug 公开讨论；修复可用前不得公开漏洞，公开修复与公告须同轮。
- L13369–L13402：需要受控的安全报告入口与保密通道，不能落普通公开档案。
- L13562–L13612：必要时对可信大型服务方做加密预通知，并控制接收人与披露窗口。
- L13682–L13696：公开时一次性说明问题、CVE、绕过方法与永久修复；若做新发布，发布物只应与既有发布相差安全补丁。
- L15256–L15272：安全发布无法获得广泛真实测试，因此必须等于“某个既有发布 + 安全修复”，不带其他变更；变更越多，引入新 bug 甚至新安全漏洞的风险越高。

**idev 现状**：

- T11 已覆盖发布路径的观测、回滚、灰度、可复现构建与产物版本，但没有安全漏洞的保密接收、预通知、披露与修复同轮、发布基线最小差异约束。
- T6 / R3 / R4 / R7 覆盖单逻辑变更、小步与回退，但不覆盖安全披露窗口与安全发布的特殊最小基线。
- T13 覆盖契约兼容性与版本语义，不覆盖紧急安全发布中“只叠安全修复”的操作纪律。
- C31 覆盖密钥、敏感日志与公认加密实现，不覆盖安全发布范围与披露时序。

**最小落点**：扩展 `conventions/canon.md` T11 的 DO 与 RECORD；不新增编号、门禁或第二套流程。T11 既有“新增上线路径”触发已覆盖该场景，无需另加信号。

**效果**：把安全修复从普通发布中区分出来，防止两类实际事故：漏洞先于修复公开；安全发布顺手携带未充分测试的无关变更。

## 四、重点候选裁定（防后人重复发现）

1. **“一个 commit 一个逻辑变更”不另立。** T6、R3、R4 已承载；《GitHub 入门与实践》《Pro Git》精读报告也已按同一结论裁定。
2. **SemVer / even-odd / 发布兼容性策略不另立。** T13 的“语义变更即换名 / 升版本”、T12 的权衡记录与 T11 的产物版本已承载通用原则；具体版本号方案随产品契约决定。
3. **发布分支与稳定化流程不另立。** T6/R4/R7 管小步、绿线与回退；T11 管发布、灰度与回滚；具体分支模型是团队工作流。
4. **测试、回归、CI、金字塔不另立。** T6、F5、C26、C28、C29、R1、A6 已覆盖；“每个 bugfix 必配测试”是产品策略，不设绝对规则。
5. **自动化比值不另立。** T12 已要求可运行约束写成检查，T6/T11 已要求护栏与可复现发布；书中 10–20 倍比值是经验值，不适合作为通用硬线。
6. **论坛选择、档案、交叉链接不另立。** 工程侧由 T5/T12/C5 承载；邮件列表、票据、聊天与档案的具体路由是项目运营机制。
7. **公开评审与 commit 邮件不另立。** C14/T2/T6/R3/R4 已承载评审纪律；平台通知格式是工具配置。
8. **社区治理、资金、雇佣、committer、致谢、fork 不另立。** 属组织与社区管理，不是编码 / 架构真源。
9. **许可证、CLA、商标、专利不另立。** 法律结论需法务判断；工程边界与密钥安全已由 T4 / C31 承载。
