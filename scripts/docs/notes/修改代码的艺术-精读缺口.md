## 二、对照结论

**主体原则层（遗留代码总纲）几乎全覆盖：**

- 「遗留代码就是无测试的代码」→ R1（有自检护栏）的判定基点 + T6（护栏先行）DO 首句 + F6（无护栏大改）三面承载；「越晚改动成本越高」的时间法则 → coding-tables.md §3.1 R 系列章首动机与 §3.2 截止日期紧且 R1 不成立 → 只做最小必要改动行承载
- 测试用具 / 单元测试两品质（快速、独立可跑）→ R1「可自动跑、自己断言结果」「每步后能快速重跑」+ C28（端到端只留核心场景、护栏修到最低层可快速重跑）承载
- 特征测试（改动前用测试钉住当前行为）→ T6 DO「先补触及面测试钉住现有行为并转绿」+ canon.md §4「没测试，改动很小 → T6 先补触及面测试」承载；「断言取自契约或用户现象、不自证」→ T6 DO 末句 + F5（自证式测试）承载
- 感知变量 / 伪对象（在测试中替身并报告调用）→ C30（打桩优先：stub 供状态 / 应答，mock 只验对外副作用）承载且比书更严
- 库依赖一次性困境（不可控的第三方依赖用外覆类隔离）→ P3（Adapter 只包装不改第三方、公开接口挡住）承载
- 超感编辑 / 反馈周期（无反馈时脑内维护状态令人疲劳易错）→ R1「每步后能快速重跑」+ R4（小步且步步绿）承载
- 单一目标编辑（「编程是关于同一时间只做一件事的艺术」，岔出任务写纸条放下）→ R3（两顶帽子不混戴）+ T6（structure/behavior 分轮）承载
- Ch24 替代系统困境 → 与《重构》缺口 2 同源，R7（停止与回退）+ §3.2 重写前提 + canon.md §4 绞杀者模式已落地，不重复立条

- 第 3 章「感知与分离」：解依赖的两个理由（感知 / 分离）→ 缺口 A 的 R1 增补「解依赖是手段，护栏是目的」+ C30（打桩优先）承载；伪对象 / 仿对象两面性 → C30 承载且比书更严

**缺口集中在：**无护栏且直接建测试受阻时的路径。现有条目只给三条路：R1/F6「先补护栏」、T6 ESCALATE「缩小步子；仍不行则停并标 UNPROVEN」、canon.md §4「旧的太乱，重写」（系统级绞杀者）。无人覆盖第四条路：护栏补不了不是终点，先经接缝手法保守解依赖让护栏变得可补。这正是本书相对于《重构》的核心增量——重构（Refactoring）假定测试已在位，本书回答「测试怎么进得去」。

## 三、真缺口

### 缺口 A｜无护栏且直接建测试受阻时的解依赖路径（R1 判定列增补）

**①出处：**第 25 章开篇定位声明（全文提取件 L9350–9361）；25.1 参数适配末段（L9449–9455）；23.3 签名保持（L9143–9170）；第 6 章时间紧迫时的技术选择（L2088–2100）。

**②论据：**「这些是重构技术，因为它们全都保持了代码的行为。但它们与业界目前所给出的那些重构技术不同，这些技术是要在没有测试的情况下使用的，其目的是为了将测试安置到位」（L9351–9353）；「这种初始的重构注定要在没有测试的情况下完成，而且它们必须得是很保守的重构」（L9143–9144，签名保持）；「记住我们是为了将测试安置到位而解开依赖。所以应该去做那些你更有信心的修改，而不是能导致最佳代码结构的修改。一旦测试到位，一切都好办了，那时你自然会得到最佳代码结构」（L9451–9452）；「安全第一。一旦测试到位，你便可以更有信心地进行侵入性的改动了」（L9455）。

**③建议落点：**coding-tables.md §3.1 R1「不满足时」列（第四列）增补一句：直接建测试受阻（类进不了测试用具、依赖难以伪装）时，先经接缝手法保守解依赖（保持行为、签名保持、不顺带清理）再特征测试补护栏；解依赖步按无护栏小步对待，从简从保守。属改既有条目的最小 diff，不新增编号、不动 §3.5。

**④与最相近条目的区别：**R1 现行「不满足时」列只说「先补最小护栏再动结构」，未回答护栏补不了时怎么办；T6 的 ESCALATE 只给「缩小步子」「停并标 UNPROVEN」两条路，均为绕开而非打通；F6 同样停在「缩小步子，补护栏」；canon.md §4「旧的太乱，重写」行的绞杀者模式是系统级替换路径，不管类级 / 方法级的建护栏；C28 是测试套件的结构配比，不管单个类如何进测试。本条补的是类级第四条路：护栏受阻 ≠ 停，先解开使类可测的依赖（不追求最佳结构，只追求测试进得去），再特征测试——解依赖是手段，护栏才是目的。

### 缺口 B｜命令/查询分离 CQS（C21 纠正列增补）

**①出处：**第 10 章 10.3 无法探知的副作用（全文提取件 L4754–4763）。

**②论据：**「命令/查询分离是最先由 Bertrand Meyer 提出的设计准则。简而言之就是：一个方法要么是一个命令，要么是一个查询，但不能两者都是。命令式方法指那些会改变对象状态但并不返回值的方法。而查询式方法则是指那些有返回值但不改变对象状态的方法。」（L4755–4760）；「如果一个方法是查询式的，那么无需查看其方法体就知道可以连续多次使用它而不用担心会带来什么副作用。」（L4762–4763）。

**③建议落点：**coding-tables.md §2 C21「纠正」列，在「拆纯函数：计算进纯函数可单测，效果函数只留一行副作用（赋值/发布/落库）」之后追加一句：**「；命令/查询分离：方法要么是查询（返回值、不改状态、可安全重复调用），要么是命令（改状态、不返回值），不能既返回值又改状态」**。属改既有条目的最小 diff，不新增编号、不动 §3.5。

**④与最相近条目的区别：**C21 现行信号是「效果函数里夹带业务计算」（计算+效果混合），纠正「拆纯函数」；CQS 是「方法既返回值又改状态」（查询+命令混合），是方法契约层面——`pop()` 这类「返回+改状态」不被 C21 信号命中。T14（可变性默认纯值）管的是「是否引入可变状态」，CQS 管的是「返回值与状态变更能否共存在一个方法签名里」。T5（命名即设计）管的是「函数名从调用点可判断行为」，CQS 让「查询/命令」这一行为从方法形状（返回类型+副作用）本身可见，是 T5 的契约级补强。三者互补，不重复。

**落地状态（已提交）**：本缺口已在 commit `88cc428`（feat: land deadlock avoidance (T10) and command-query separation (C21) gaps）落地——`conventions/coding-tables.md` §2 C21「纠正」列增补命令/查询分离（CQS）。`deep-read-audit.py` 与 `trigger-check.py` 均 PASS。
