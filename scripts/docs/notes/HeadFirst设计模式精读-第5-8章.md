## 第5章 单件模式（Singleton Pattern）L8556-9478

### ① 模式意图
确保一个类只有一个实例，并提供一个全局访问点（L8865-8866："单件模式确保一个类只有一个实例，并提供一个全局访问点"）。类图只有一个类，是所有模式中最简单的，但实现上波折很多（L8566-8568）。

### ② 使用场景与触发条件
- **典型对象**：线程池、缓存、对话框、处理偏好设置和注册表的对象、日志对象、打印机/显卡等设备驱动对象（L8580-8582）。这些对象"只能有一个实例"，多实例会导致程序行为异常、资源使用过量或不一致的结果（L8582-8583）。
- **触发条件**：当你需要确保程序中某个类只有一个实例时，就采用单件模式（L9211-9213 工具箱提示）。
- **不用/慎用**：作者明言"通常适合使用单件模式的机会不多"——如果应用程序大量使用单件，应当回头检查设计（L9164-9168）。
- 与全局变量比较：单件给了全局访问点，又没有全局变量的缺点——全局变量必须在程序一开始就创建对象，若对象昂贵而本次执行没用到就是浪费；单件可延迟实例化（L8588, L8590-8592）。

### ③ 反例与代价
- **不用模式的反例**：靠程序员约定或全局变量（静态变量），全局变量提供全局访问但不能确保唯一实例，还会鼓励用许多全局变量指向许多小对象、污染命名空间（L9180-9186）。
- **经典实现的坑（多线程）**：延迟实例化的 `getInstance()` 在两个线程下都判 `uniqueInstance == null` 后各自 new，返回两个不同对象——巧克力锅炉因此溢出 500 加仑原料（L8896-8898, L9294-9345 "糟糕！返回了两个不同对象"）。
- **同步的代价**：同步 `getInstance()` 简单有效，但同步一个方法可能使执行效率下降 100 倍；且只有第一次创建时才真正需要同步，之后每次同步都是累赘（L8969-8972, L8984-8985）。
- **双重检查加锁的代价**：在 Java 1.4 及更早版本中，许多 JVM 对 volatile 的实现会导致双重检查加锁失效，必须 Java 5 以上（L9043-9048）。
- **类加载器陷阱**：两个以上类加载器各有命名空间，可能各自创建自己的单件实例，产生多个单件并存的怪异现象（L9102-9110）。
- **旧 JVM 垃圾回收陷阱**：Java 1.2 前垃圾收集器有 bug，单件若只有本类引用自己会被回收，下次 `getInstance()` 产生"全新"单件、实例变量归零（L9114-9122）。
- **设计代价**：单件一身两责——既管理自己的实例并提供全局访问，又在应用中担当业务角色，可以视为违反"一个类，一个责任"（L9129-9146）。

### ④ 论据（压缩转述）
- 苏格拉底式推导过程：私有构造器 → 鸡生蛋问题（必须先有实例才能调私有构造器）→ 静态方法 `getInstance()` 是类方法、用类名调用 → 合起来即经典单件（L8604-8669, L8676-8736）。
- 经典实现三件套：私有构造器、静态变量 `uniqueInstance` 记录唯一实例、静态方法 `getInstance()` 做延迟实例化——"如果我们不需要这个实例，它就永远不会产生，这就是延迟实例化（lazy instantiation）"（L8692-8728）。
- 多线程三种解法及作者点评（L8982-9048 + 习题解答 L9353-9362）：
  1. **同步 `getInstance()`**：最直截了当；巧克力锅炉无性能顾虑，可用。若性能关键则慎用（效率可能降 100 倍）。
  2. **急切实例化**：在静态初始化器中直接 `new`，"JVM 保证在任何线程访问 uniqueInstance 静态变量之前，一定先创建此实例"，天然线程安全；前提是应用总是创建并使用该实例、负担不重（L8987-9008）。
  3. **双重检查加锁**：先检查、未创建才同步，"只有第一次会同步"；volatile 确保 uniqueInstance 初始化时多线程正确处理；性能关键时用，但要 Java 5+（L9013-9042）。
- 全静态类替代单件：若类自给自足、不依赖复杂初始化可以这么做；但静态初始化控制权在 Java 手上，多类牵扯时会产生与初始化次序有关的微妙 bug——"除非绝对必要，建议使用对象的单件，比较保险"（L9079-9101）。
- 继承单件：私有构造器无法被继承；改成 public/protected 就不是"真正的"单件；且直接继承静态变量会让所有派生类共享同一实例变量，要支持子类基类须实现注册表（Registry）功能。作者反问：继承单件能带来什么好处？（L9134-9158）

### ⑤ 最佳实践 / 作者忠告
- **必须假定所有程序都是多线程的**来选择单件实现方案（L9231-9235）。先确定性能与资源限制，再选方案。
- Java 实现单件三要素：私有构造器 + 静态方法 + 静态变量（L9227-9229）。
- 多类加载器环境要自行指定同一个类加载器（L9110-9112）。
- 大量使用单件是设计坏味道的信号（L9164-9168）。

### 本章 OO 原则框（L9195-9210）
- OO 基础：抽象、封装、多态、继承
- OO 原则（累计）：
  1. 封装变化
  2. 多用组合，少用继承
  3. 针对接口编程，不针对实现编程
  4. 为交互对象之间的松耦合设计而努力
  5. 类应该对扩展开放，对修改关闭
  6. 依赖抽象，不要依赖具体类
- 工具箱新增：单件模式——确保一个类只有一个实例，并提供全局访问点

### 章末要点清单（L9222-9245，忠实摘录非重复核心条目）
- 单件模式确保程序中一个类**最多只有一个**实例，并提供访问实例的全局点。
- 实现需要：私有的构造器、一个静态方法和一个静态变量。
- 必须认定所有的程序都是多线程的，据此选方案解决多线程问题。
- 非 Java 5 双重检查加锁会失效；多类加载器可能导致多个实例；JVM 1.2 前需建单件注册表防垃圾回收。

## 第6章 命令模式（Command Pattern）L9480-11479

### ① 模式意图
将"请求"封装成对象，以便用不同的请求、队列或日志来参数化其他对象，命令模式也支持可撤销操作（L10049-10051 正式定义）。核心机制是**把方法调用（method invocation）封装起来**：运算块被包装成对象后，可以随心所欲地存储、传递和调用，且调用时完全不必知晓其内部实现细节（L9480-9496 章首引入，L11322-11324 工具箱复述）。

### ② 使用场景与触发条件
- **触发条件**：当需要将发出请求的对象和执行请求的对象解耦的时候，使用命令模式（L11338-11340 原则框新增指引）。
- **典型案例**：巴斯特家电自动化遥控器 API——7 个可编程插槽、每槽 on/off 两个按钮、一个全局撤销按钮；厂商类众多且接口各异（Light、CeilingFan、Stereo、GarageDoor、TV、Hottub、Sprinkler……），未来还会持续增加（L9500-9553, L9556-9622）。
- **延伸场景**：队列请求（工作队列 + 线程把计算两端解耦，适用线程池、日程安排，L11224-11267）；日志请求（命令序列化存盘，崩溃后重载逐条 execute() 恢复，可扩展为事务，L11269-11317）。
- **何时不用**：调用简单直接、无排队/撤销/日志/参数化需求时不需要命令对象；"聪明命令"（命令直接实现请求）虽实践中常见，但解耦程度低（L11178-11222 Q&A）。

### ③ 反例与代价
- **不用模式的反例**：遥控器内部一堆 if 判断——"slot 是灯就调 light.on()，是车库门就调 up()……"——每接入一个新厂商类就得改遥控器代码、增加分支，"错误多多，工作永无尽头"（L9646-9650）。
- **代价 1 · 类数量膨胀**：每个设备每个动作一个命令类（LightOnCommand、StereoOnWithCDCommand……），7 槽遥控器起步就需要十几个命令类。
- **代价 2 · 解耦变浅**：聪明命令把逻辑直接写进命令对象、不再委托接收者，换取代码直白但降低解耦程度（L11178-11222）。

### ④ 论据（压缩转述）
- **餐厅类比**（L9685-9797, 对应关系 L11425-11440）：顾客=Client，女招待=Invoker（takeOrder→setCommand），订单=Command（orderUp→execute，封装"做餐请求"），快餐厨师=Receiver（makeBurger 等）。女招待收单、在合适时机喊 orderUp，却不知道也不关心谁做菜、怎么做；换菜单、换厨师，女招待一行代码都不用改——调用者与接收者彻底解耦（L9770-9793）。
- **类图角色**（L10090-10129）：Client 创建 ConcreteCommand 并设置其接收者；Invoker 持有命令对象、在适当时机调用其 execute()；Command 接口声明 execute()；ConcreteCommand 通过绑定一组动作与接收者来执行；Receiver 知道如何完成具体工作。
- **基础实现**：Command 接口仅一个 execute()；LightOnCommand 持有 Light 引用，execute() 转发 light.on()；SimpleRemoteControl 持单个命令槽，setCommand() 注入、buttonWasPressed() 触发 execute()——遥控器对 Light 的存在一无所知（L9915-10001）。
- **完整遥控器**：Command[] onCommands/offCommands 各 7 槽，构造时全部预填 NoCommand；setCommand(slot, on, off) 赋值；on/offButtonWasPushed 调对应命令 execute()（L10196-10250）。
- **一个命令可执行多步动作**：StereoOnWithCDCommand.execute() 依次调 on() + setCD() + setVolume(11)（L10272-10299）。
- **空对象**：NoCommand 把"什么都不做"也封装成命令，免去 null 检查；它是 null object 模式的实例，而 null object 本身也被视为一种模式（L10439-10470）。
- **简单撤销**：Command 接口加 undo()；调用者用 undoCommand 变量记住最后一条命令（初始 NoCommand），undoButtonWasPushed() 调其 undo()；LightOnCommand.undo() 反向调 off()（L10532-10659）。
- **带状态撤销**：CeilingFan 有 HIGH/MEDIUM/LOW/OFF 四档速度；CeilingFanHighCommand 在 execute() 前先用 prevSpeed 记录原速度，undo() 按 prevSpeed 恢复对应档位——**撤销需要记录 execute() 执行前的状态**（L10777-10877）。
- **宏命令**：MacroCommand 持 Command[]，execute() 遍历执行、undo() 遍历撤销；party 场景一条宏命令同时开灯、开音响、开浴缸、开电视（L11000-11157, L11457-11468）。
- **队列请求**：命令对象可入队——工作线程循环"取命令→execute()→丢弃→取下一条"，计算两端彼此不知晓对方存在；适用于线程池、日程安排（L11224-11267）。
- **日志请求**：Command 加 store()/load()（序列化）；执行时存盘，系统死机后重载日志依次 execute() 恢复；配合检查点适合电子表格等大型数据结构；可扩展为事务——要么全部命令完成、要么一个也不执行（L11269-11317）。

### ⑤ 最佳实践 / 作者忠告
- 宏命令优于硬编码的 PartyCommand：更灵活、代码更少（L11210-11222）。
- 多级撤销：调用者用堆栈记录每条已执行命令，每次 undo 弹出一条（L11188-11192）。
- "傻瓜命令"（纯转发给接收者）与"聪明命令"（自己实现请求）之间做取舍时，要意识到聪明命令解耦程度更低（L11178-11222）。
- 命令对象的价值在"封装调用"带来的可存储、可传递、可排队、可日志、可撤销——若这些能力都用不上，引入命令模式即是过度设计（由 L9480-9496 意图与 Q&A 综合得出）。

### 本章 OO 原则框（L11328-11340）
- OO 基础：抽象、封装、多态、继承
- OO 原则（累计，本章新增第 7 条）：
  1. 封装变化
  2. 多用组合，少用继承
  3. 针对接口编程，不针对实现编程
  4. 为交互对象之间松耦合设计而努力
  5. 类应该对扩展开放，对修改关闭
  6. 依赖抽象，不要依赖具体类
  7. **（本章新增）当需要将发出请求的对象和执行请求的对象解耦的时候，使用命令模式**
- 工具箱模式箱（累计）：单件模式、命令模式（L11341-11347）

### 章末要点清单（L11350-11379，忠实摘录非重复核心条目）
- 命令模式将发出请求的对象和执行请求的对象解耦；被解耦的两者通过命令对象沟通，命令对象封装了接收者和一个或一组动作。
- 调用者通过调用命令对象的 execute() 发出请求，这使得接收者的动作被调用；调用者可以把命令当做参数，甚至在运行时动态传递。
- 命令支持撤销：实现 undo() 方法回到 execute() 被执行前的状态。
- 宏命令是命令的简单延伸，允许一次调用多个命令，宏命令也支持撤销。
- 实际操作中很常见使用"聪明"命令对象——直接实现请求，而不是将工作委托给接收者。
- 命令也可以用来实现日志和事务系统。

## 第7章 适配器与外观模式（Adapter & Facade Patterns）L11537-13286

### ① 模式意图
本章两个模式都以"包装对象"为手段，但意图不同：
- **适配器**：将一个类的接口，转换成客户期望的另一个接口，让原本接口不兼容的类可以合作无间（L11870-11873 正式定义）。它还让客户与被适配接口解耦——接口日后改变时，改变被封装在适配器内，客户无须跟着修改。
- **外观**：提供一个统一的接口，用来访问子系统中的一群接口；外观定义了一个高层接口，让子系统更容易使用（L12717-12719 正式定义）。
- **关键区分**：两模式的差异**不在于"包装"了几个类，而在意图**——适配器意图是"改变"接口以符合客户的期望；外观意图是提供子系统的一个简化接口（L12545-12556）。

### ② 使用场景与触发条件
- **适配器触发**：需要使用一个现有的类而其接口并不符合你的需要时（L12993-12995）；典型局面：系统要接新厂商类库，新接口与旧厂商接口不同，你不想改自己的现有代码、也不能改厂商代码——写一个适配器类做中间人（L11588-11631）。
- **外观触发**：需要简化并统一一个很大的接口或者一群复杂的接口时（L12996-12998）；即客户端完成一项任务须与许多子系统类打交道、手动步骤繁琐时。
- **两种适配器形式**：对象适配器（组合）与类适配器（继承，需要多重继承，Java 不可能）（L11903-11929, L13009-13011）。
- **何时不用**：接口本来就匹配就无需适配器；子系统本来就简单无需外观。与装饰者的分界：要增加职责而不改接口用装饰者，要转换接口用适配器（L12204-12259）。

### ③ 反例与代价
- **反例（外观的动机）**：家庭影院"困难的方式"看一部电影——开爆米花机、爆米花、调暗灯、放屏幕、开投影机、设宽屏、开功放、设 DVD、环绕声、音量、开 DVD 播放器、播放，共 **13 步操作跨 6 个类**；看完还得反向关一遍；听 CD/收音机同样痛苦；系统升级还得重新学习操作流程（L12286-12419）。
- **适配器代价**：实现工作量与目标接口的大小成正比（L11822-11863）；适配器并不完美——Enumeration→Iterator 例子中 remove() 只能抛 UnsupportedOperationException，"客户必须小心潜在的异常，但只要客户够小心，而且适配器的文档能做出说明，这也算是一个合理的解决方案"（L12151-12155）。
- **类适配器代价**：需要多重继承，Java 做不到（L11903-11929）。
- **最少知识原则的代价**：减少了对象之间的依赖、研究显示可降低软件维护成本；但会制造更多"包装"类来处理与其他组件的沟通，导致复杂度和开发时间增加、降低运行时性能（L12857-12865）。

### ④ 论据（压缩转述）
- **真实世界类比**：欧洲壁式插座与美国插头——交流电适配器转换接口让不兼容的两端接通；OO 适配器同样把一个类的接口转换成另一个接口，以符合客户的期望（L11560-11582）。
- **火鸡适配器**（代码一句话）：TurkeyAdapter 实现 Duck 接口并组合 Turkey——quack() 转发 gobble()，fly() 连调 5 次火鸡的 fly() 补足飞行距离；客户的 testDuck() 根本不知道"这是一只假装成鸭子的火鸡"（L11634-11778）。
- **运作机制**：客户通过目标接口调用适配器的方法→适配器将被适配者接口上的一个或多个调用进行转换→客户收到结果但未察觉转换发生；客户与被适配者解耦、互不相识（L11803-11813）。
- **类图与组合的好处**：Adapter 实现 Target 并组合 Adaptee；因为用组合，被适配者的**任何子类**都能搭配这个适配器；客户绑定的是接口而非实现（L11878-11899）。
- **对象 vs 类适配器围炉夜话**（L12014-12046）：对象适配器用组合，可适配某类及其任何子类、更具弹性；类适配器继承 Target 与 Adaptee，不必重新实现整个被适配者、可覆盖其行为、只需一个对象——但需要多重继承。
- **双向适配器**：适配器实现两个接口，可同时服务新旧客户端（L11822-11863）。
- **真实世界例子 Enumeration→Iterator**（代码一句话）：EnumerationIterator 把 hasNext/next 映射到 hasMoreElements/nextElement，remove() 抛异常（枚举只读）（L12048-12196）。
- **装饰者 vs 适配器围炉夜话**：两者都包装对象、纸面相似，"但其实我们的意图差异颇大"——装饰者不改变接口只加责任，适配器转换接口；适配器的好处是客户无须改任何代码就能使用新类库（L12204-12259）。
- **三模式意图对照**：装饰者=不改变接口但加入责任；适配器=将一个接口转成另一个接口；外观=让接口更简单（L12273-12282, L13143-13152）。
- **家庭影院外观实现**（代码一句话）：HomeTheaterFacade 构造器组合全部 8 个影院组件（amp/tuner/dvd/cd/projector/screen/lights/popper），watchMovie() 把手动 13 项任务依次委托给相应组件，endMovie() 反向关闭一切（L12563-12645）；客户只调 homeTheater.watchMovie() 一个方法（L12657-12681）。
- **外观 Q&A**：外观没有"封装"子系统类，只是提供简化接口，客户仍可直接使用子系统的完整功能；外观可附加"聪明"功能（知道爆米花机要先开才能爆）；一个子系统可以有多个外观；升级组件时只改外观代码，客户与子系统解耦（L12491-12533, L12902-12909）。
- **最少知识原则（新OO原则）**："只和你的密友谈话"——减少对象交互、只留几个密友，避免太多类相互耦合形成易碎、难维护、难理解的系统（L12737-12751）。方针：方法内只应调用四类对象的方法——**该对象本身、作为方法参数传进来的对象、方法内创建/实例化的对象、对象的组件**（HAS-A 实例变量引用者）；**不要调用"从另一个调用返回的对象"的方法**（L12764-12777）。
- **原则正反例**：`station.getThermometer().getTemperature()` 违反（调用了"从另一个调用返回的对象"的方法）；改进：让气象站自己提供 `getTemperature()`，减少依赖的类的数目（L12755-12757, L12786-12802）；Car.start(Key) 展示四类合法调用的样子（L12813-12848）。
- **与得墨忒耳法则的关系**：两者是同一原则；作者偏好"最少知识"名称——更直接，且"法则"给人强制感，而"没有任何原则是法律"（L12833-12841）。
- **机械遵守的荒谬**：习题解答把违反代码改成向 helper 传 thermometer 参数后"没有违反最少知识原则，但是，把程序改成这样真的有意义吗？"——作者借习题点破机械套用原则之荒谬（L13119-13120）。

### ⑤ 最佳实践 / 作者忠告
- 判断用哪个模式**看意图而非形态**：转换接口=适配器；加责任不改接口=装饰者；简化统一接口=外观（L12263-12283, L13014-13018）。
- 外观只是提供更高层的操作，并不将原来的子系统阻隔起来——需要低层功能时仍可使用原子系统（L12482-12485）。
- "所有的原则都应该在有帮助的时候才遵守。所有的设计都不免需要折衷……虽然原则提供了方针，但在采用原则之前，必须全盘考虑所有的因素"（L12850-12856）。
- 常用 API 也有违反最少知识的地方（如 System.out），"你应该注意吗？"——作者以此提示：原则是指南不是法律，不必因原则而不敢用便利的常用 API（L12896-12897, L13057-13059）。

### 本章 OO 原则框（L12951-12964）
- OO 基础：抽象、封装、多态、继承
- OO 原则（本章清单 7 条，新增"只和朋友交谈"）：
  1. 封装变化
  2. 多用组合，少用继承
  3. 针对接口编程，不针对实现编程
  4. 为交互对象之间的松耦合设计而努力
  5. 类应该对扩展开放，对修改关闭
  6. 依赖抽象，不要依赖具体类
  7. **（本章新增）只和朋友交谈（最少知识原则）**
- 注：第6章原则框中的"使用命令模式解耦请求者与执行者"条目在本章清单中未再出现——中文版各章设计箱的原则清单并非严格累加，此处忠实按本章原文记录。
- 工具箱模式箱（累计 4 个）：单件模式、命令模式、适配器模式（转换接口以符合客户期望）、外观模式（提供子系统的统一简化接口）（L12977-12989）

### 章末要点清单（L12993-13018，忠实摘录非重复核心条目）
- 当需要使用一个现有的类而其接口并不符合你的需要时，就使用适配器；当需要简化并统一一个很大的接口或者一群复杂的接口时，使用外观。
- 适配器改变接口以符合客户的期望；外观将客户从一个复杂的子系统中解耦。
- 实现一个适配器视目标接口的大小与复杂度而定，可能费力也可能不费力；实现一个外观需要将子系统组合进外观中，然后将工作委托给子系统执行。
- 适配器模式有两种形式：对象适配器和类适配器，类适配器需要用到多重继承。
- 可以为一个子系统实现一个以上的外观。
- 适配器将一个对象包装起来以**改变其接口**；装饰者将一个对象包装起来以**增加新的行为和责任**；外观将一群对象“包装”起来以**简化其接口**。

## 第8章 模板方法模式（L13287-14914）

### ① 模式意图
在一个方法中定义一个算法的骨架，而将一些步骤延迟到子类中。模板方法使得子类可以在不改变算法结构的情况下，重新定义算法中的某些步骤（L13767-13769）。

### ② 使用场景与触发条件
- **触发条件**：两个或多个类的算法结构完全相同、只有个别步骤实现不同。章首案例：咖啡与茶的冲泡算法同为“烧水→泡/冲→倒杯→加调料”，其中烧水、倒杯完全相同，泡制与加调料各不相同（L13304-13487）。
- **典型场景——创建框架**：框架决定算法如何进行、按什么顺序调用方法，使用者只需提供算法中各步骤的实现细节（“当你要写框架的时候，模板方法就会派上用场”，L14172-14189）。
- **标准库中的模板方法**：Arrays.sort()（排序算法骨架固定，compareTo() 由待排序类实现）、java.io InputStream.read(byte[],int,int)（依赖子类实现抽象 read()）、Swing JFrame.update()/paint()（paint() 为钩子）、Applet 生命周期钩子（init/start/stop/destroy/paint）。
- **什么时候不用**：需要在运行时整体替换整个算法→用策略模式（组合更弹性）；想避免继承耦合、按更细粒度复用→用组合而非继承。

### ③ 反例与代价
**反例（抽象出模板方法之前的写法）**：
- 咖啡类与茶类各自掌控一切：冲泡四步算法在两个类中逐字重复（L13424-13487）；
- 算法知识分散：对算法做一点改变（如调整步骤）就得同时打开多个类修改，无弹性、无组织（L13733-13760）；
- 新增饮料必须重新复制同样的算法框架；
- 无法对冲泡过程整体做统一控制（如统一插入钩子判断）。

**模式的代价与局限**：
- 基于继承而非组合，不够弹性：新增行为变体要新建子类（围炉夜话中策略模式的批驳：“因为我使用对象组合，所以我更有弹性，客户可以在运行时改变算法”，L14639-14643）；
- 子类依赖父类中的方法实现（L14646-14648）；
- 步骤切分粒度是设计负担：切得太细子类必须实现一堆方法，太粗则弹性不足（L14028-14056）。

### ④ 论据
**演进路径（章首案例）**：
1. 先抽象共性步骤到父类：boilWater()/pourInCup() 移入 CaffeineBeverage，brew()/addCondiments() 声明为抽象（L13424-13583）；
2. 再抽象整个算法框架：prepareRecipe() 只写一份、按序调用四个步骤，声明为 final；具体饮料类只实现两个抽象步骤（L13585-13635）。代码一句话：CaffeineBeverage.prepareRecipe()（final）依次调用 boilWater→brew→pourInCup→addCondiments，Tea/Coffee 各自实现 brew/addCondiments；
3. 命名定式：“模板方法定义了一个算法的步骤，并允许子类为一个或多个步骤提供实现”（L13676-13677）。

**结构**：AbstractClass 持有 templateMethod()（具体、声明 final）、abstract primitiveOperation()（子类实现）、concreteOperation()（可选的具体操作，供模板方法或子类使用，与子类化无关的辅助功能）（L13774-13832）。

**钩子（hook）**：
- 定义：“钩子是抽象类中声明、实现为空或默认实现的方法。钩子的存在让子类有能力对算法的不同点做出反应。要不要挂钩，由子类自行决定”（L13881-13884）。
- 案例：customerWantsCondiments() 作为 if 条件包裹 addCondiments() 步骤，CoffeeWithHook 覆写它询问用户（L13874-13962）。代码一句话：父类模板方法中 `if (customerWantsCondiments()) addCondiments();`。
- 钩子的三种用法：作为算法的可选部分；让子类对即将/刚刚发生的步骤做出反应；让子类为其抽象类做决定（L14017-14043）。
- 抽象方法 vs 钩子：必须由子类提供实现的用抽象方法；可选步骤用钩子，减轻子类负担——子类不必实现不想要的空方法（L14007-14016）。
- 粒度折衷：算法步骤不要切得太细也不要太少——太少限制弹性，太多加重子类负担，设计时取平衡（L14028-14056）。

**好莱坞原则**：“别找我，我们会找你”。防止依赖腐败：高层直接调低层、低层又调高层、横向乱调，最后没人能理清系统如何运作（L14060-14093）。
- 与模板方法的关系：模板方法正是好莱坞原则的实例——父类（高层）决定调用哪些步骤、何时调用，子类（低层）只提供实现，不主动调用（L14096-14125）。
- 与依赖倒置原则的关系：DIP 教我们尽量依赖抽象、避免具体类；好莱坞原则是创建弹性框架/组件的技巧，用于构建防止依赖腐败的类库（L14131-14146）。两者殊途同归。
- 低层并非绝对不能调用高层：低层组件常调用从超类继承来的方法，关键是避免明显环状的直接依赖（L14147-14153）。

**Arrays.sort() 辨析**：sort() 静态方法委托 mergeSort() 控制排序算法；依赖待排序类实现 Comparable.compareTo() 填空。“sort() 控制算法，不让任何类改变；sort() 依赖 Comparable 提供 compareTo() 的实现”（L14414-14417）；“它不使用继承，不像典型的模板方法”（L14421-14423）。问答结论：模式的要点在于提供算法、让别的类实现其中某些步骤——野生模式不会总是一板一眼，要适配当前环境与实现约束；此处静态方法+Comparable 组合让排序更有弹性也更实用。为何不算策略模式：策略模式中组合的类实现的是整个算法，而排序算法并不完整、需要类填上 compareTo()（L14432-14465）。
- 同族例子：InputStream.read(byte[],int,int) 是模板方法，依赖子类实现抽象的 read()（L14466-14473）；JFrame.update() 控制屏幕更新算法、paint() 是默认空实现的钩子，覆写它插入自己的绘图代码（L14486-14523）；Applet 的 init/start/stop/destroy/paint 全是钩子，“具体的 Applet 大量使用钩子提供行为”（L14528-14573）。

**围炉夜话：模板方法 vs 策略（L14576-14651）**：
- 策略：定义算法家族、可互换、完全封装整个算法、用组合委托；
- 模板方法：只定义大纲，子类填步骤，算法结构保持不变；
- 模板方法胜在控制权：决定步骤顺序，还有共享代码、不重复；
- 策略胜在弹性：运行时可换算法，不依赖任何人提供实现；
- 模板方法最常见的用武之地是框架创建。

**模式配对（L14156-14168 / L14789-14801）**：模板方法=子类决定如何实现算法步骤；策略=封装可互换行为、以委托决定；工厂方法=子类决定实例化哪个具体类。章末明确：“工厂方法是模板方法的一个特殊版本”（L14765-14766）。

### ⑤ 最佳实践 / 作者忠告
- 把模板方法声明为 final，防止子类改变算法结构（L13813-13819, L14751-14753）。
- 算法步骤不要切得太细也不要太少，在弹性与子类负担之间取平衡；可选步骤尽量做成钩子而非抽象方法（L14028-14056）。
- 决策权放在高层模块：由高层决定如何、何时调用低层组件；低层组件绝不直接调用高层组件（L14091-14092, L14754-14757）。
- 现实世界中的模板方法有许多变体，“不要期望它们都可以一眼认出来”（L14758-14761）。

### 章末要点清单（L14736-14766，非重复核心条目）
- 模板方法定义了算法的步骤，把这些步骤的实现延迟到子类。
- 模板方法模式是很重要的代码复用技巧。
- 抽象类中可以定义三种方法：具体方法、抽象方法、钩子。抽象方法由子类实现；钩子是抽象类中不做任何事情或只做默认事情的方法，子类可自行决定要不要覆写。
- 为了防止子类改变算法，把模板方法声明为 final。
- 好莱坞原则：把决策权放在高层模块，决定如何以及何时调用低层模块。
- 现实世界中有许多模板方法的变体，不要期望都可以一眼认出来。
- 策略模式和模板方法模式都封装算法：一个用组合、一个用继承。
- 工厂方法是模板方法的一个特殊版本。
