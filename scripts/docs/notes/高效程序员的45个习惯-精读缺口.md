## 四、重点候选裁定（防后人重复发现）

1. **「警告就是错误」（习惯 34）不另立编号。** 现有 `experts.md` code 拒过清单已含「未跑扫描或留下黄条」，`agents/idev-coder.md` 与 `idev-reviewer.md` 明确「黄条视为未完成」，`coding-tables.md` §3.7 已要求跑仓内扫描并「命中译成 C# 当轮改」。再加一条「警告即错误」会重复扫描门禁。
2. **「预估与承诺」（习惯 18、23）不重复落点。** `req-quality.md` §5 已承载「预估不是承诺」「只承诺可掌控的具体行动」「每轮真实增量后复估剩余范围」「与 deadline 冲突当轮报风险与选项」。本书是同一主题的另一处出处，只作溯源。
3. **「报告所有异常」（习惯 36）不另立。** C7（`catch` 后 return 空值吞失败）、T8（快速失败禁静默兜底）、F4（静默兜底）已覆盖；本书的空 `catch` 案例是解释材料，不是新规则。
4. **「Liskov 替换」（习惯 32）不另立。** C27 已承载继承守约（前置更宽松、返回更窄、层级≤2、复用走组合），P6 已管「只有一种实现写具体类型」。
5. **「告知，不要询问」（习惯 31）不另立。** C22（`a.getB().getC()` 链式取值）与 T3（深模块）已承载；本书的命令/查询分离是同一原则的另一种表述。
6. **「5 个为什么」（习惯 8）不落编码表。** 根因追问归 `ops/SKILL.md` 根因约束与 `evidence.md` 证据规则；作为提问技巧不具代码形状，不建机检。
7. **「代码集体所有制 / 结对编程 / 站立会议 / 成为指导者」（习惯 38、40–42、44）不作为通用硬规则。** 现有独立 reviewer、分片、写租约、角色分工已解决协作与冲突风险；把「必须两人一起写」或「必须每日站会」落到单人或多 agent 场景会误伤。
8. **「架构师必须写代码」（习惯 39）不另立。** `experts.md` arch 阶段已要求产出可评审的 `design.md` + `arch.yaml`，拒过清单含「只有一行 approach、没有 design.md」；「PowerPoint 架构师」反模式已被承载。
