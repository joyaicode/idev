## 三、真缺口

### 1. 持有资源 / 身份 / 锁的类型被按值复制，导致双重释放 / 状态不同步 / 锁失效

**书中依据**：第 5 章 5.3「类型的本质」——「这个类型的本质是什么。如果给这个类型增加或者删除某个值，是要创建一个新值，还是要更改当前的值？」（L3386–L3388）；「大多数情况下，结构类型的本质并不是原始的，而是非原始的」（L3523）；os.File 例子「这个类型的值实际上不能安全复制」（L3543–L3544），「正是这层额外的内嵌类型阻止了复制。不是所有的结构类型都需要或者应该实现类似的额外保护。程序员需要能识别出每个类型的本质，并使用这个本质来决定如何组织类型」（L3546–L3547）；「因为 File 类型的值具备非原始的本质，所以总是应该被共享，而不是被复制」（L3572）；「是使用值接收者还是指针接收者，不应该由该方法是否修改了接收到的值来决定。这个决策应该基于该类型的本质」（L3573–L3574）；5.7 小结「设计类型时需要确认类型的本质是原始的，还是非原始的」（L4706）。

**论据**：现有 C# 无一条覆盖「持有资源 / 身份 / 锁的类型被按值复制」这一形状。C19 管「资源获取与释放在同一抽象层次、由获取方释放」，不管「复制一个持有资源的类型会造出第二个所有者，导致双重释放 / 关闭错误的文件描述符」；T14 管「可变共享状态的别名与保护性拷贝」，方向相反（对数据拷贝是隔离手段，对资源拷贝是事故）。这是跨语言可推广的形状：Go `sync.Mutex` 按值复制锁失效（`go vet` 的 `copylocks` 检查）、C++ 持有裸指针的类默认拷贝导致 double-free、Rust `File`/`Mutex` 不实现 `Copy`、Java 值对象须不可变才可安全共享。书中明言「没有方法阻止程序员进行复制，所以 File 类型的实现使用了一个嵌入的指针」——这是需要显式编码的护栏。

**建议落点**：`conventions/coding-tables.md` §2 末尾新增 C39（最小 diff，接在 C38 后）。
