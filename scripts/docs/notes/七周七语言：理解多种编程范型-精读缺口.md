## 二、对照结论

### 1. 主体原则已被真源覆盖

| 书中主题 | idev 承载 | 结论 |
|---|---|---|
| 可变状态限制并发：函数式编程消除副作用与可变状态 → 竞争条件随之消除（Scala 5.1.4「最大的问题在于可变的状态……函数式编程语言通过去除等式中的可变状态来解决这些问题」L3440–L3470；5.3.1「可变的状态是糟糕的……可变状态限制并发」L3790–L3810） | T14（可变性默认纯值、纯函数值进值出）/ C21（命令/查询分离、查询无副作用） | 承载 |
| OO 的并发弱点：面向对象「围绕状态包装行为」，状态会改变，并发时引发严重问题（Ruby 2.5.2「面向对象编程有一个重大弱点……状态是会发生改变的……并发时就会引发严重问题」L1566–L1593） | T14（可变状态让正确性局部不成立）/ T10（并发） | 承载 |
| 消息传递优于共享内存：actor 通过严格控制的队列接触其他 actor，而线程不受限制改变彼此状态 → 竞争条件（Io 3.4.3「一个 actor 改变其自身的状态，并且通过严格控制的队列接触其他 actor……线程容易受到竞争条件影响」L2285–L2296） | T10（并发控制与业务分离、共享可变数据与锁绑定）/ T14 | 承载 |
| 「就让它崩溃」：不防御式处理每个错误，监测崩溃进程并重启，而非逐错误兜底（Erlang 6.1.1「Erlang 解决这一问题的秘诀是『就让它崩溃』……终止相关进程并启动新进程」L4430–L4434；6.5「你不必理会进程为什么崩溃，因为你只要重启它就好」L5340–L5341） | T8（快速失败、禁静默兜底）/ C38（失败向上传播，不把异常当控制流）/ T11（监控、告警、恢复） | 承载 |
| 事务型内存（STM）：多版本并发控制，事务内修改共享引用，保持一致性（Clojure 7.4.1「其策略是使用多版本维持一致性和完整性……不能在事务之外修改引用」L6175–L6180） | T10（离线并发策略：乐观（版本号）还是悲观（独占锁）） | 承载 |

| 鸭子类型/对接口编码：根据对象支持的方法而非继承层次确定类型（Ruby 2.2.5「对接口编码，不对实现编码……对象若有 push 和 pop 方法，它就能当作栈来用」L1025–L1031） | T3（深模块、公开面最小）/ T1（先砍偶然复杂度） | 承载 |

## 四、重点候选裁定（防后人重复发现）

1. **可变状态限制并发（Scala 5.1.4/5.3.1）不单列。** T14（可变性默认纯值、纯函数）已承载；「消除副作用与可变状态 → 竞争条件消除」是 T14 该条的函数式实例。
2. **消息传递优于共享内存（Io actor）不单列。** T10（并发控制、共享可变数据与锁绑定）已承载；「actor 通过队列接触、线程不受限制改彼此状态」是 T10 的并发实例（Go 源码剖析报告已同向裁定「share memory by communicating」）。
3. **「就让它崩溃」（Erlang）不单列。** T8（快速失败）+ C38（失败向上传播）+ T11（监控/告警/恢复）已承载；「不逐错误兜底、崩溃即重启」是这三条的并发/分布式实例，不另立监督树编号。
4. **事务型内存/乐观并发（Clojure STM）不单列。** T10「离线并发策略：乐观（版本号）还是悲观（独占锁）」已承载；STM 多版本是「版本号」的具体机制。
5. **future/异步（Io、Clojure）不单列。** T10（异步、至少/至多一次）已承载。
6. **鸭子类型/对接口编码（Ruby）不单列。** T3（深模块、公开面最小）+ T1（砍偶然抽象）已承载；「对象有 push/pop 就能当栈」是 T3 的接口实例。
7. **失败条件显式化（Haskell Maybe monad）不单列。** C7 + P15 + T8 已承载（失败就抛、禁 null/空对象、快速失败）。
8. **类型系统编译期捕获错误（Haskell/Ruby 类型模型）不单列。** T8 + C2 + C25 已承载（非法输入立刻抛错、必要约束抛错、值对象把校验进类型）；「让非法状态不可表示」是这些条目的类型层推论。
9. **为读者写代码（第 9 章 9.4）不单列。** T5 + C1–C40 已承载（命名即设计、可读性气味全表）。
