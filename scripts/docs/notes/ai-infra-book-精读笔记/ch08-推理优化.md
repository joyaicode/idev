## 一、本章主张

1. 同一模型单用户几十 token/s、全体用户上千 token/s：个体延迟与整体吞吐是两个指标，优化前先分清这轮在改哪一个 (L3)。
2. decode 读一遍权重只做很少计算，受限于显存带宽而非峰值算力——先找真正的瓶颈资源再选优化方向 (L3)。
3. 仅调整执行顺序就可能使请求超时：插入一条 prefill 把输出间隔从 26.5 ms 拉到 123 ms，总耗时 7.05 s 超 7 s 时限 (L40)。
4. 时间线两段分治：TTFT 决定用户何时看到响应、ITL 均匀性决定可读性、总耗时决定答案何时可用——所有调度优化都是改其中某一段 (L42, L94)。
5. 接收请求时按生成完毕所需空间预留，避免执行到一半才发现内存不足；代价是尾部预留未用 (L76)。
6. 合批减少每输出 token 分摊的权重读取，但收益递减：b_KV = ⌈D_w/(Lk)⌉ 之后 KV 读取反超权重，继续加大 batch 不再省读取 (L125-137)。
7. 合批省读取、增驻留：批越大，分摊越少但同时驻留的数据越多——吞吐与容量的取舍随 batch 变化 (L139)。
8. batch 从 1 增至 64 吞吐 37→1165，但 TTFT 96 ms→3.29 s、平均间隔 27→40 ms：每轮输出更多不等于用户等得更少 (L151)。
9. 连续批处理缩短总时间却拉长单次间隔（总时间 −12%、最大间隔 ×14）；分块 prefill 用 844 ms（略慢于 766 ms）换最大间隔降到 133 ms——先定要优化哪个指标再选策略 (L173-187)。
10. 同样大小的块随上下文增长变慢：注意力配对 ch + c(c+1)/2，末块配对数为首块 31 倍 (L193-212)。
11. 缩小块长的代价是更多执行次数与重复权重读取：调度器应选满足输出间隔要求的较大块 (L214)。
12. 动态形状下少处理一个 token 未必少做计算（17 行仍填到 32 行图）；预设形状的档位差是收益边界 (L218-220)。
13. 先由允许的输出间隔定一轮最长执行时间，再换算为 token 预算——从约束反推参数，不从资源正推 (L224)。
14. 分页、共享、压缩节省的是不同部分：分页减少预留浪费（上限 p−1）、共享去重前缀、压缩减少每数值字节——三者分别计费 (L244-260, L416)。
15. 引用计数归零且加速器操作不再访问，块才能回池；取消调用 1.6 ms 返回 ≠ 31 ms 后块已释放——回收绑定的是资源真正空闲的事件 (L268-302)。
16. 写时复制：修改共享内容前取得私有副本，已填满的只读块继续共享 (L274)。
17. 前缀复用沿连续前缀发生：把变化内容放前面会毁掉后面的复用；上下文组织要同时计内存、重算与后续读取 (L312, L332)。
18. 缓存保留的期望净节省 V_h = p_h(T_r−T_f) − T_m：低于命中阈值就不值得留；比较候选时按单位容量收益排序 (L354-372)。
19. 压缩是否省时间由 ΔD/β 是否大于转换时间 T_c 决定；上下文越长节省越多，短上下文可能反亏（交点约 7000 token）(L418-426)。
20. 卸载的净空间要扣除预取缓冲；能否用计算掩盖复制由每轮搬移量与链路带宽之比决定，每轮 ≥42.5 ms 时 255 轮必超 7 s 时限 (L434-448)。
21. 压缩后搬移更快需解压吞吐 R_dec > B_link/(1−r)：链路越快对解压要求越高——优化一项资源时先算另一项会不会成为新瓶颈 (L458-464)。
22. 逐项比较存储格式与计算精度才能找出输出差异的来源：只改 Q 精度结果就变了；正确数相同但答错的题不同 (L476-492)。
23. 错误答案重试的额外生成时间计入总耗时：更快但更易错的配置完成整个任务可能更慢 (L494)。
24. 平均每 token 耗时必须总时间除以总 token 数：先算每轮平均再等权平均会错（0.5 vs 0.9 ms）(L542)。
25. 加长草稿的边际判据 ΔT/ΔN < T/N：接受概率逐位相乘递减，越靠后的草稿越难赚回时间 (L574-584)。
26. 有效吞吐只计正确且按期完成的请求；完成吞吐涨而有效吞吐跌（2.38 vs 0.60 req/s）说明多收的请求只贡献了排队 (L616-636)。
27. 评价配置先内存、再时限、最后每个合格结果的 GPU 时间与能耗；内存或输出缩短时最优方案会切换且解释可从数据量、执行时间与输出数量中找到 (L683-693)。
28. 配置比较应记录三类结果：给定条件下能同时保存多少请求状态、prefill/decode 各多快、延迟随 batch 与到达率如何变化 (L791)。

## 三、缺口汇总

1. **取舍三角显式化：方案写明牺牲了哪一角**
   - 落点：conventions/canon.md §3 T12（DO 并入一句），挂靠 T12、A3。
   - 拟落文案：「方案记录除被拒方案外，显式写明牺牲了哪一角（吞吐 / 单请求延迟 / 资源成本）：同一资源的两种用法（合批提吞吐 vs 拉长间隔、错峰省缓冲 vs 维护相位、共享省内存 vs 争用通道）与不同资源之间的换算（容量换时间、带宽换解压），都要能说出换掉了什么、换回了什么。」
   - 书里依据：L173-187（总时间 −12% 换间隔 ×14）、L214（块长取舍）、L434-448（容量换搬移）、L558（2 s 准备需 114 token 回本）、L693（输出缩短时推测优势消失）。这是任务书点名要求判断的一条：批处理何时有效/何时伤延迟、KV 状态放置的取舍思维，判据落在 canon T12 而非 experts.md/req-quality.md——T12 已有「放弃了什么」，缺的是把三角的三个角点名成可检查的问句。
2. **有效吞吐语义：按「正确且按期」计，并从下降点反推准入上限**
   - 落点：deliver/references/experts.md `test` → `done` 行（提测门）或 `ops` 行的拒过清单并入；挂靠 T11。
   - 拟落文案：「服务效果不只计完成量：分子只计既正确又按期（或满足 SLA）完成的请求，完成吞吐与有效吞吐的差额要能解释花在了哪（错的还是迟的）；配置比较时找出有效吞吐开始下降的到达率，把准入上限设在下降点之前，不在下降后继续扩接收。」
   - 书里依据：L616-636（336 次生成 294 正确只有 155 按期；2.38 vs 0.60 req/s）、L691（B 方案 9.01 s 无一合格全部浪费）、L705（迟到回答的能量计入成本）。experts.md `test`→`done` 行现有「残留 UNPROVEN 人明确接受」的收口语义，但无「合格」的合取定义与下降点判据；req-quality.md 管验收可证伪、不管运行期吞吐语义，故落 experts.md。
3. **瓶颈迁移判据：优化一项资源前先算另一项会不会成为新瓶颈**
   - 落点：conventions/canon.md §3 T9（DO 并入一句），挂靠 T9、A6。
   - 拟落文案：「优化一项资源（带宽、容量、启动次数）前，先算改动后哪一项会成为新瓶颈（解压吞吐、共享接口、请求速率、接受概率），并写出使原优化仍然划算的边界条件；越线时收益反转的量（压缩比、块长、草稿长度、batch）要给出交点公式或实测交点。」
   - 书里依据：L458-464（R_dec > B_link/(1−r)）、L214-220（块长与形状档位）、L578-588（ΔT/ΔN < T/N、K15 边际 1.2 ms）、L125-137（b_KV 交点）、L566-568（接受率降 1 反而慢）。T9 现有「优化亦小步进行、每步重测」，缺「预判下一个瓶颈并写边界条件」这半句。

## 四、勘误与存疑

- 数值抽查通过：k=144 KiB/token（L62-65）、16 条独立长请求 18 GiB 超 12 GiB（L67）、共享后 6048 MiB（L292-296）、V_h 阈值 4.8%（Gen5）/10.1%（Gen4）（L360-366）、PCIe 卸载 42.5 ms 与 255 轮 10.8 s（L444-448）、D 方案 4.56 s 与 A/C/B 排除（L666-683）——复算一致。
- 存疑 1：L151 的 batch 扫描为同时提交、同时起跑的合成负载（L151 自注「在线服务若额外等待 batch 集满……」），TTFT 3.29 s 不可直接引用为在线值。
- 存疑 2：L624 实测 336 次生成中 42 次错误「来自同一道题」（脚注 L767）——错误集中度高，提示题集偏窄；「正确且按期」的合取判据成立，但 0.90/0.31/1.02 req/s 的具体幅度不外推到其他题集。
- 存疑 3：L660 的带宽效率（batch 1 时 33%）实验关闭了 CUDA Graph，含逐 kernel 提交开销；文中已自判「不是模型漏项」——这是方法论示范，引用 MBU 数字须注明该口径。
- 存疑 4：L550 DFlash 中位 15.2 ms 与普通 decode 16.9 ms「相当」，但两者与 8.2 节 26.26 ms 不同（低并发、短题集，脚注 L765）；跨节数字不能混用，引用时须各带各的脚注口径。
- 口径注意：L644 t_GPU 公式按「批内多条共享一次执行时每条都算完成调用、占用只计一次」折算（L642-644）——这是资源归因口径，与 L542「总时间/总 token」同理：全书反复强调统计口径先行，属可提炼的方法论（已并入 T9 相关缺口），非勘误。
- 特别判断归因：批处理调度算法（连续批处理、分块策略、token 预算）、推测解码算法（接受采样、草稿来源）、KV 分页/写时复制的数据结构设计属系统层机制，标「不落」；但「批处理何时有效/何时伤延迟」（吞吐 vs 延迟取舍，缺口 1）与「KV 管理的状态放置」（预留 vs 增长、共享 vs 私有、缓存 vs 重算的取舍，缺口 1/3）的判断结构已按任务书要求提炼，落点为 canon T12 与 experts.md 提测门，不新增编号。
