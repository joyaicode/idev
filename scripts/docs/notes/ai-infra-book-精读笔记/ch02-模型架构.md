## 一、本章主张

1. 资源预算的每个数字都要能追溯到计算图中的具体矩阵与状态；"一个 8B 模型"不说明每个 token 用哪些参数、状态存哪、先后关系如何（L3–7）。
2. 节点的运算量决定计算需求，边上的张量决定传递的数据量，边的方向决定执行次序——三方面须同时看（L17）。
3. 已知输入能否并行取决于依赖形式而非"序列"名称：RNN 同层串行、因果 Transformer 同层可并行、生成跨调用串行（L23–37）。
4. 矩阵尺寸三规则：行数 m 翻倍运算量翻倍而权重不变；输出宽 n 翻倍权重与运算量都翻倍；运算量 F=2mkn、存储 M=b·kn（L45–57）。
5. 「增加本次参与计算的 token 数」与「让每个 token 读更长上下文」代价不同：投影随 m 线性增长，全注意力随 P(P+1)/2 增长（L90、L142、L198）。
6. 保持 BP 不变只保持投影行数不变，不保持上下文交互不变；拆分输入会删掉跨分界的查询—键配对（L142）。
7. KV 缓存把"重算旧 token 表示"换成"保存并访问旧状态"；长期保存的是 K、V 而非旧查询（L220–224）。
8. 按用途和生命周期把数据分三类：权重（多次调用不变）、上下文状态（随请求持续追加）、临时数据（用后释放）——存储量取决于某一时刻需保留什么，访问量取决于执行中读写多少次（L236–250）。
9. 累计访问量与最终存储量可相差几个数量级：8192 输入＋1024 输出的请求，KV 累计读取约 1224 GiB，最终只存约 1.27 GiB，近千倍（L284–286）。
10. 容量与访问须分别计量，还要计量内存峰值（同一时刻并存的张量），三者回答不同问题（L248、L907）。
11. 节省状态的每个机制（共享、压缩、递推、索引）都要连同新增的选择/压缩/更新工作一起算账（L308、L356、L799）。
12. 结构变化的收益随条件翻转：上下文短时紧凑表示的查询变换开销占比高，长时节省的读取可观（L356）；混合结构容量＝固定部分＋每 token 增量，交点 H* 决定哪个方向有效（L441–444）。
13. MoE 把"保存多少参数"与"一个 token 激活多少参数"分开：总容量由全部专家决定，单 token 计算由选中专家决定（L528、L719、L749）。
14. 相同计算量下权重读取量可差 32 倍：均匀分派访问 256 个专家 1.5GiB，集中分派只访问 8 个 48MiB——读取量由实际访问的不同权重份数 U 决定（L544–565）。
15. 参数量相近的模型计算图可以不同：矩阵 FLOPs 相近，缓冲占用时间与串行步骤也可能不同（L589）。
16. 层数与宽度在相近参数预算下改变依赖深度：窄而深的模型依赖链更长，并行上限受串行链限制（L593）。
17. 连接方式决定哪些张量须同时保存：残差要保留输入到子层完成；跨层引用则保存到最后一次使用结束（L603、L613）。
18. 推测解码有收益的条件是每轮有效输出数 > (草稿+验证耗时)/单步耗时；多预测不增加权重但仍执行词表投影（L629–635）。
19. 汇总整模型＝按层类别加权求和，逐项可追溯；合计时最易漏的是非矩阵算术、输出头位置范围、固定递推状态、索引扫描、块边界更新（L679–699）。
20. 容量决定一实例至少多少卡，请求长度与并发决定实例要处理多少工作；并发数按整数跳变，剩余空间放不下一条完整状态就放不下（L805–823）。
21. 量化释放的空间要计入 scale、尾部填充与保持高精度的部分，不能按半字节一律折算（L825–827、L753）。
22. 比较模型须回答两个问题：能否完成同一任务（质量），以及完成任务需要多少资源（分项容量/计算/状态）；输入 token 数相同比较资源结构，同文本比较实际用途且允许不同分词器产生不同长度（L859–885、L909）。
23. 长上下文评估应分别检查：保存了多少状态、访问哪些位置、为索引和更新新增了多少工作（L799）。
24. 「每步只选少量上下文」不等于总工作量固定：主注意力、索引扫描、压缩投影三类工作增长规律不同（L1079）。
25. 设计模型时可从加速器容量反推：先扣服务状态与工作区，剩余空间给权重预算；模型规模、状态结构与卡数须一起选择（L845–853、L1241）。

## 三、缺口汇总

**G6　存储/缓存类方案的三笔账：常驻量、累计访问量、峰值占用量**
- 落点：conventions/canon.md §3 T10 DO 扩句（或 §5 A4 补半句；不新增编号）。
- 拟落文案：「涉及数据驻留 / 缓存 / 状态保持的方案须算三笔账并各给数字或 UNPROVEN：常驻量（某时刻须保留什么）、累计访问量（执行期读写多少次，随调用量怎样增长）、峰值占用量（同一时刻并存的张量 / 副本上限）；三笔可相差数量级，只报其中一笔不算算清。」
- 书里依据：L236–250（三类数据与存储/访问分计）、L284–286（1224 GiB vs 1.27 GiB 千倍差）、L248（内存峰值＝同时保存的张量）、L907（误区：状态大小固定≠访问开销可忽略）。

**G7　比较类结论须声明对照条件（同条件才可比）**
- 落点：deliver/references/req-quality.md §1 SMART 指标补一行示例（并入既有格式）。
- 拟落文案：「对比类指标（快 X%、省 Y%）写明对照条件：同输入规模、同环境、同测量口径；口径不同（如不同分词长度 / 不同数据集 / 不同预热）的对比是待拷问项，不得直接作目标值。」
- 书里依据：L883–885（同 token 数比资源结构、同文本比实际用途，二者回答不同问题）、L909（误区：输入 token 数相同≠公平比较）、L750（比较须按各自执行路径累计）。

**G8　结构参数变化须指出作用于哪一项（条件→项的映射）**
- 落点：conventions/canon.md §4 念头表「加缓存 / 索引 / 冗余字段」行动作补强（挂靠既有 T10 T9 行）。
- 拟落文案：「改结构参数（批量、长度、规模、精度、连接方式）前，先写出它作用于预算表的哪一项、哪些项保持不变；写不出映射就不动手。」
- 书里依据：L1243（面对新条件先指出改变了哪个对象，再重新代入相应公式——增大 batch、延长上下文、扩大专家集合作用于不同项）、L57（行数与宽度两条不同增长规则）。

## 四、勘误与存疑

1. 数字抽验通过：c_KV=2×36×8×128×2=144KiB（L229）、8K 上下文 1.125GiB（L232）、B_*=R_W/(c_KV·H) 得 H=8192→13、H=2048→51（L254–260）、R_old 累计 8,912,384 次 token（Σ(H+j), j=0..1023, H=8192 = 1024×8192+1024×1023/2）、GQA 4:1 共享比（L314）、V4.1 全局 KV (3/2+1)×(288+68)=890B/token（L496–499）、V4-Flash 21×652/4+20×584/128=3514.25B/token（L502–505）、B_max=4（L815–819）均可复算。
2. 表 2-E 中 Qwen3-8B 与 Qwen3.6 的 1M 行按同一结构外推（L783 书已自注），非发布配置支持；引用该表结论时须带此前提。
3. V4-Flash「生产混合格式 27.455MiB」与「BF16 参考格式读取量 27.625MiB」数值接近但含义不同（L472 书已自注）——这正是 G7「口径不同不可直接比」的域内样本。
4. 本章依赖大量 2026 年 9 月前后的模型（V4.1 Flash、Kimi K3、Qwen3.6）配置数字，时效性强；提炼判据只用其方法骨架，不带具体模型名与数字。
5. 勘误候选：L260「H=2048 时为 51」——按 R_W=15,136,811,008 / (147456×2048) = 50.13，最小整数 51，正确；L374「59.125 MiB＋11.641 MiB≈70.8 MiB」加总正确。未发现实质性数字错误。
6. 存疑不落章：本章大量注意力机制细节（MLA 紧凑/展开路径、KDA 递推、CSA2 三模式、候选池）属模型架构设计知识，与交付导体（写业务代码的编码/架构规范）相距两层，全部不落；仅其「三笔账」「对照条件」「条件→项映射」三个方法骨架值得进真源。
