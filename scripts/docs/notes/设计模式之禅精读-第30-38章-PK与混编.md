## 第30章 创建类模式大PK（L17606-18314）

**章节意图（一句话）**：在创建类模式家族内部裁决「创建一个对象到底选哪个模式」——PK 焦点是工厂方法、抽象工厂、建造者三者，单例/原型因含义直白不参与（L17608-17612）。

### 30.1 工厂方法模式 VS 建造者模式

| 五要素 | 内容 |
|---|---|
| ① 意图差异 | 工厂方法注重**整体对象**的创建方法；建造者注重**部件构建的过程**，通过一步步精确构造创建复杂对象（L17613-17615）。超人例子：工厂方法直接产出一个力大无穷、内裤外穿的完整超人；建造者则要先组装手、头、脚、躯干，再内裤外穿（L17616-17618）。 |
| ② 使用场景/触发条件 | 需要详细关注产品部件的生产、安装步骤 → 建造者；只关心「给我一个成品」→ 工厂方法（L17863-17865）。 |
| ③ 反例/缺点/代价 | 工厂方法生产的产品「都是一个模样」、粒度粗，无法干预装配过程；建造者则必须关心每个部件甚至装配顺序——相同部件、不同顺序会产生不同结果，这是它的代价也是它的能力（L17812-17817）。 |
| ④ 论据 | 工厂模式是对象创建的「粗线条」应用，建造者模式则是「细线条」勾勒出一个复杂对象（L17852-17854）；工厂方法创建单一性质产品，建造者创建由部件复合而成的产品，「粒度大小不同」（L17859-17862）。 |
| ⑤ 最佳实践/忠告 | 作者的裁决判据：「如果需要详细关注一个产品部件的生产、安装步骤，则选择建造者，否则选择工厂方法模式」（L17863-17865）。另注意：工厂产出的对象不必状态行为完全相同，「它是由产品所决定」（L17698-17699）。 |

- 代码演示概括：工厂方法版用 `SuperManFactory.createSuperMan(type)` 按类型直接返回成品超人（L17661-17693）；建造者版把模板方法模式**迁移到抽象建造者上**（`Builder` 持有产品、`getSuperMan()` 抽象、部件 setter 具体实现），子类只负责按顺序装配（L17761-17834）。
- 作者忠告（模式灵活性）：第11章把模板方法用在产品上、本章却移到建造者上——「设计模式只是提供了一个解决问题的意图……而没有具体定出一个设计模式必须是这样的实现……灵活运用模式才是其根本，别学死板了」（L17797-17800）。

### 30.2 抽象工厂模式 VS 建造者模式

| 五要素 | 内容 |
|---|---|
| ① 意图差异 | 抽象工厂实现**产品家族**（不同分类维度的产品组合）的创建，不关心构建过程，只关心什么产品由什么工厂生产；建造者按**指定蓝图**建造，通过组装零配件产生新产品（L17866-17870）。 |
| ② 使用场景/触发条件 | 希望屏蔽对象的创建过程、只提供一个封装良好的完整对象 → 抽象工厂；需要装配不同组件或相同组件的不同顺序来产生新对象 → 建造者（L18309-18312）。 |
| ③ 反例/缺点/代价 | 抽象工厂「把一辆车认为是一个完整的、不可拆分的对象。它注重完整性」，产品一旦定了工厂就是固定型号（L18057-18059）——因此**造不出混合车型**（如奔驰引擎+宝马车轮）；建造者的代价是必须掌握蓝图、关心零件级细节。 |
| ④ 论据 | 汽车案例：按「车型」维度建厂（一个厂既产奔驰SUV又产宝马SUV）「在技术上是完全可行的，但是在业务上是不可行的」——业务约束决定工厂维度的划分（L17906-17909）；运行结果证明建造者可轻松产出「BMW的引擎 + benz的轮胎」的混合车，「反观我们的抽象工厂模式，它是不可能实现该功能的」（L18287-18293）。 |
| ⑤ 最佳实践/忠告 | 隐喻裁决：抽象工厂=「工厂」（从更高层次看对象构建，车间细节隐藏在内部），建造者=「车间」（不同车间完成不同装配任务，配合基础是设计蓝图，蓝图握在导演类/车间主任手中）（L18296-18305）；「抽象工厂模式比建造者模式的尺度要大」，建造者「只要重新设计一个蓝图，即可产生不同的产品」，转型极快（L18305-18308）。 |

- 代码演示概括：抽象工厂版按 品牌×车型 两维产出完整汽车（`CarFactory`→`BMWFactory`/`BenzFactory`）（L17981-18053）；建造者版引入 `Blueprint` 蓝图类（「它是一个可以参考的模板……指导我们的产品生产，而不是一个具体的产品」，L18189-18391），`Director` 持蓝图驱动 `CarBuilder` 装配，私有方法 `createCar` 收敛对蓝图的依赖（L18216-18249）。

### 第30章 PK 裁决速查

- 工厂方法 vs 建造者：看**粒度**——关注整体选工厂方法，关注部件与装配顺序选建造者。
- 抽象工厂 vs 建造者：看**尺度与变化方向**——屏蔽过程、要完整产品族选抽象工厂；要零件级灵活组合（换引擎、换轮胎、混搭）选建造者。
- 工厂方法 vs 抽象工厂（本章隐含）：看**产品是一维还是多维分类**——本章汽车案例按品牌建厂而非按车型建厂，说明维度选择由业务可行性裁决，而不仅是技术可行性。

## 第31章 结构类模式大PK

> 结构类模式包括适配器、桥梁、组合、装饰、门面、享元、代理七种，「都是通过组合类或对象产生更大结构以适应更高层次的逻辑需求」（L18317-18319）。本章两组 PK：代理VS装饰、装饰VS适配器。

### 31.1 代理模式 VS 装饰模式

**① 意图差异（一句话）**
- 代理模式：着重对**代理过程的控制**——是否可以调用真实角色、消息是否变形，对被代理类的功能不做任何处理，「保证原汁原味的调用」（L18466-18468）。
- 装饰模式：着重**类的功能变化**——在接口不变的前提下加强（或减弱）功能，但「不做准入条件判断和准入参数过滤」（L18470-18472）。
- 作者定性：「装饰模式就是代理模式的一个特殊应用」（L18321）。

**② 使用场景与触发条件**
- 代理：需要控制对象行为的**准入**（可不可以执行、参数是否合规）时用代理；代理在 Java 开发中「俯拾皆是」，用到极致就是 AOP（Spring 架构的基石，代理+反射，L18468-18469）。
- 装饰：需要在运行期动态叠加/撤销功能强化时用装饰；典型例子是 `java.io.*`——`new DataOutputStream(new FileOutputStream("test.txt"))`（L18475-18478）。

**③ 反例/缺点/代价**
- 两者类图与代码实现非常相似（装饰省略抽象装饰角色后「两者代码基本上相同」，L18464-18465），混用不会报错但会错表意图；装饰是「比较拘谨的模式」，实际接触较少，不要为装饰而装饰（L18473-18474）。

**④ 论据（代码演示一句话概括 + 行号）**
- 代理示例：`RunnerAgent.run()` 内用随机数决定是否安排 `runner.run()`——「对于主题类的行为是否可以发生，代理类有绝对的控制权」（L18368-18378）；场景见 L18381-18393，两种运行结果证明代理的控制权（L18404-18406）。
- 装饰示例：同一个 IRunner，`RunnerWithJet.run()` 先打印「为运动员增加喷气装置」再无条件调用 `runner.run()`——「装饰类对类的行为没有决定权，只有增强作用」（L18434-18439）。
- 裁决句：代理「不对被主题角色的功能做任何处理」vs 装饰「保证的是被修饰的对象功能比原始对象丰富」（L18466-18471）。

**⑤ 最佳实践/作者忠告**
- 区分判据不是类图而是**职责**：看包装类是「决定做不做」（代理）还是「做了再加点料」（装饰）。
- 作者示例复用了完全相同的类图（L18418-18423「完全一样！不过其实现的意图却不同」），说明意图才是模式的身份。

### 31.2 装饰模式 VS 适配器模式

**① 意图差异（一句话）**
- 两者都是「包装作用，都是通过委托方式实现其功能」（L18486），但装饰模式「包装的是自己的兄弟类，隶属于同一个家族（相同接口或父类）」；适配器「修饰非血缘关系类……是伪装，因此它的本质还是非相同接口的对象」（L18486-18488）。
- 丑小鸭双重叙事：装饰视角=丑小鸭**本来就是天鹅**（is-a，L18542），通过 BeautifyAppearance/StrongBehavior 两次强化「转变为受人喜爱、羡慕的白天鹅」（L18650-18652）；适配器视角=从**鸭妈妈的立场**出发，「把一只白天鹅封装成了小鸭子」（L18684），`UglyDuckling extends WhiteSwan implements Duck` 实现不同物种的相同处理过程（L18786-18789）。

**② 使用场景与触发条件**
- 装饰：任何时候想增强类的功能都可以用（L18803）。
- 适配器：「是一个补救模式，一般出现在系统成熟或已经构建完毕的项目中，作为一个紧急处理手段采用」（L18803-18804）。

**③ 反例/缺点/代价**
- 适配器建立容易、去掉难：「需要从系统整体考虑是否能够撤销」（L18807-18808）——引入适配器是一种欠债。

**④ 论据（作者给出的四个不同点，L18790-18808）**
1. **意图不同**：装饰=加强对象的功能（「使美丽更加美丽，强壮更加强壮」）；适配器=转化，「关注转换」（L18792-18797）。
2. **施与对象不同**：装饰对象必须同宗（相同接口或父类）；适配器必须是两个不同对象——「如果是相同对象还转换什么」（L18798-18801）。
3. **场景不同**：装饰随时可用；适配器是系统后期的紧急补救手段（L18802-18804）。
4. **扩展性不同**：装饰「很容易扩展」，可继续叠加；适配器是两对象间的沟通桥梁，「建立容易，去掉就比较困难」（L18805-18808）。

**⑤ 最佳实践/作者忠告**
- 判别口诀：同宗强化找装饰，异族转化找适配器；新系统设计期用装饰，遗留系统救火用适配器。

### 第31章 PK 裁决速查

| PK | 胜负判断 | 判据 | 关键行号 |
|---|---|---|---|
| 代理 vs 装饰 | 不分胜负，按职责分流 | 控制（准入/拒绝）→代理；增强（加强/减弱功能）→装饰 | L18321-18323, L18466-18472 |
| 装饰 vs 适配器 | 按血缘与时机分流 | 同家族包装→装饰；异族伪装+后期补救→适配器 | L18486-18488, L18790-18808 |

**结构性观点**：第31章与第30章的 PK 判据一致——**先看意图（控制/增强/转化），再看对象关系（同族/异族），最后看时机（设计期/补救期）**，类图相同不代表模式相同。

## 第32章 行为类模式大PK（L18811-20023）

行为类模式关注对象间交互与职责分配。本章三组PK：命令vs策略、策略vs状态、观察者vs责任链（触发链）。

### 32.1 命令模式 VS 策略模式（L18817-19201）

- **意图差异**：策略封装的是**算法**——完整、不可拆分的原子业务，算法独立、可相互替换；命令模式的核心是**动作解耦**——执行对象（接收者）与执行行为（命令）相互独立。
- **对比场景**：zip/gzip 压缩解压缩。
  - 策略实现：Algorithm 接口 + Zip/Gzip 实现 + Context；换算法客户端只改一行。
  - 命令实现：AbstractCmd 持有 zip/gzip 两个接收者引用，4 个具体命令类（Zip/Gzip × Compress/Uncompress）+ Invoker + IReceiver。
- **关键论据（作者的裁决点）**：
  - 命令模式的接收者可按职责拆分设计（如 CompressReceiver/UncompressReceiver 分开，L19070-19119）；策略模式**不允许**这样做——违背"封装算法"意图，且新增 rar 算法时不允许修改抽象算法类（L19119-19125）。
  - 命令可排队、可撤销（点菜撤单类比，L19171-19173）；策略做不到。
- **小结3点（作者判据）**：①关注点不同（策略=算法替换+完整性封装保证自由切换；命令=请求者与执行者解耦、可撤销记录）②角色功能不同（策略的具体算法=原子业务单元、整体变更；命令的接收者只对命令负责，变更仅影响命令族、不波及请求者）③使用场景不同（策略=算法变换场景；命令=紧耦合对象间解耦，或多命令多撤销场景）。

### 32.2 策略模式 VS 状态模式（L19202-19482）

- **"亲兄弟"**：类图极似（都是 Context 封装一个行为接口），本质差异在语义：策略封装**算法**（算法间无交互），状态封装**状态**（状态切换则行为随之变）。
- **对比示例**：人生阶段工作。
  - 策略版：WorkAlgorithm + ChildWork/AdultWork/OldWork，由**高层决定**用哪个算法。
  - 状态版：HumanState 子类的 work() 有**两个职责**——完成工作逻辑 + 设置下一状态（如 ChildState.work() 末尾 setState(ADULT_STATE)，L19369-19372）；Human 环境角色用静态常量持有三个状态。
- **小结5点（作者判据）**：①环境角色职责不同（策略 Context=纯委托；状态 Context=委托+登记状态变化）②重点不同（算法改变对外影响最小 vs 状态改变引起行为改变）③方法不同（策略不决定何时用算法；状态封装状态变化、只暴露行为）④场景不同（策略=平行、可替换算法如 MD5/DES/RSA，算法不平行会产生坏味道；状态=必须同时有"状态+行为"两个维度，只有状态无行为则状态模式失去意义）⑤复杂度不同（策略结构简单易读；状态封装"无穷尽的变化"，复杂且涉及面广）。

### 32.3 观察者模式 VS 责任链模式——触发链（L19483-20023）

- **作者裁决：两者组合出"触发链"模式**，用 DNS 域名解析案例演示（观察者+责任链混编）。
- **结构要点**：DnsServer `extends Observable implements Observer`——所有 DNS 服务器具备**双重身份**（既是观察者也是被观察者），声明统一身份标志后节点可在链中**随意移动**、无需固定位置（L19829-19831，链的重要特性）。setUpperServer=设置自己的观察者（上级 DNS）；update 既是事件处理者也是事件触发者（L19833-19834）。
- **代码概括**：抽象 DnsServer 的 update 判断 isLocal（按域名后缀 .sh.cn/.cn/全真），本机可解析则生成 IP，否则 setChanged+notifyObservers 提交上级；三个实现类只实现签名与级别判断；场景类用 sh.update(null, recorder) 虚拟触发（作者自陈为减代码做了简化，完整做法应把场景类做被观察者，L19959-19962）。
- **运行结果的微妙关系（作者洞察）**：所有解析结果都显示"上海DNS服务器"返回——①**下级对上级顶礼膜拜**：下级只认上级反馈，不追究是否真是上级处理（www.xxx.com 实际由全球顶级解析，签名经中国顶级节点改写，L19990-19996）；②**上级对下级绝对信任**：上级不关心请求源头，只认直接下级（L19997-20001）。
- **小结3点（触发链 vs 责任链的判据，L20004-20021）**：
  1. **消息对象不同**：责任链基本不改变消息对象结构（节点可"雁过拔毛"但对象不变形，String 进不会 int 出）；触发链允许消息对象在链中自由变化，只要求**相邻两节点间**消息对象固定。
  2. **上下节点关系不同**：责任链节点间无关系（都接收同样对象、各按自己逻辑处理）；触发链上下级关系亲密（顶礼膜拜+绝对信任），任意相邻两节点是牢固的独立团体。
  3. **分销渠道不同**：责任链消息从链首向链尾单一固定方向流动；触发链因基于观察者，传递方式不固定，可广播、可跳跃，取决于处理消息的逻辑。

## 第33章 跨战区PK（L20024-21247）

创建类、行为类、结构类三种模式着重点不同（创建/行为/结构），但实际应用中有重叠，会出现多种模式都适用的情况，本章跨战区对比帮你选型。

### 33.1 策略模式 VS 桥梁模式（L20031-20399）

- **意图差异**：策略是行为模式，旨在封装一系列行为；桥梁是结构模式，关注抽象和实现的分离。两者"孪生兄弟"：把策略的环境角色变更为抽象类+实现类，或桥梁抽象角色未实现只有修正抽象化角色，两个类图完全一样（L20049-20051）。
- **对比场景**：发送文本邮件/HTML邮件。
  - 策略版：MailTemplate 抽象类 + TextMail/HtmlMail 覆写 getContext 加 Content-Type 标志 + MailServer 环境角色。两种格式=两种算法，**选择哪个算法由上层模块决定**，策略的任务就是提供两种可替换算法（L20237-20239）。细节洞察：抽象类可以没有抽象方法——"给我制造一封邮件"无法实例化，邮件是可描述但不可形象化的事物（L20139-20144）。
  - 桥梁版：MailServer 改为抽象类（架构视角：邮件服务器同样可描述不可实例化，必须"给我一台 Postfix"，L20316-20318）+ Postfix/SendMail 覆写 sendMail 在邮件上留下服务器标志（广告、统计、同质软件共振三理由，L20334-20335）。形成邮件×服务器两个可独立变化的维度，共 4 种组合。
- **最佳实践（裁决判据）**：策略=用继承和多态建立一套可自由切换算法的模式；桥梁=在不破坏封装的前提下解决抽象和实现都可独立扩展的模式。**桥梁必然有两个"桥墩"**——抽象化角色和实现化角色；策略只有一个抽象角色，可以没有实现也可以有很多实现（L20390-20393）。
- **作者忠告**：还是难区分时多想意图；做系统设计时可以不考虑到底用哪个，只要好用、能解决问题就成——"不管黑猫白猫，抓住老鼠的就是好猫"（L20397-20399）。

### 33.2 门面模式 VS 中介者模式（L20400-20817）

- **意图差异**：门面为复杂子系统提供统一高层访问界面，避免外部深入子系统内部产生细节耦合；中介者用中介对象封装一系列同事对象的交互，使各对象不再显式引用（L20402-20405）。
- **对比场景**：工资计算（工资、职位、税收两两相关）。
  - 中介者版：AbsColleague 持有 mediator（每个同事类都对中介者非常了解）+ 三个同事类升降动作全委托 mediator.up/down(this) + Mediator 的 12 个方法分两类——private 的各业务独立流程 + 实现抽象中介者的组合逻辑（职位升→工资增+税收增）。反例：不用中介者则每个对象都要与其他两个通信，系统复杂且僵化、难拥抱变化（L20623-20625）。
  - 门面版：HRFacade（querySalary/queryWorkDays）+ SalaryProvider 组合逻辑 + 考勤/奖金/基本工资/绩效/税收五个子系统。**关键论据**：SalaryProvider 这类具体业务逻辑若暴露给外系统，被修改的风险非常大；门面必须**无逻辑、与业务无关**，只是子系统的访问入口，全部业务在子系统内实现（L20747-20749）；门面所有行为都是委托，不做任何校验、判断、异常处理（L20770-20771）。
- **最佳实践3点判据（L20799-20817）**：
  1. **功能区别**：门面对子系统没增加任何功能，子系统脱离门面可完全独立运行；中介者增加了业务功能，把同事类原有耦合关系移植到中介者，同事类不可能脱离中介者独立存在。
  2. **知晓状态不同**：子系统不知道门面存在；每个同事类都知道中介者存在、对中介者非常了解。
  3. **封装程度不同**：门面是简单封装，所有请求处理都委托子系统；中介者需要中心协调同事类，且中心本身也完成部分业务，属于更进一步的业务功能封装。

### 33.3 包装模式群PK（L20818-21234）

- **作者提出"包装模式"（wrapping pattern）概念**：不是单个模式而是一组——**装饰、适配器、门面、代理、桥梁**。共同特征：通过委托方式对一个对象或一系列对象施行包装；从实现角度看，**它们都是代理的一种具体表现形式**（L20815-20817、L21215-21217）。
- **同一场景（明星圈）四模式对比**：
  - **代理**（追星族签字）：Agent 转发请求给明星本人，是包装模式中**最一般的实现**（L20830、L20889-20890）。
  - **装饰**（粉饰拙劣演员）：HotAir 演前吹嘘 + Deny 演后抵赖，在被装饰者行为**前后添加职责**（L20939-20985）。
  - **适配器**（替身演员）：Standin implements IStar 持有 IActor，把普通演员**转换为**明星演员——接口转换（L21077）。
  - **桥梁**（明星多元化）：AbsStar × AbsAction 两维度独立扩展；电影明星无参构造默认拍电影、有参构造可客串唱歌（L21162-21163）。
- **最佳实践（各模式使用场景判据，L21214-21233）**：
  - 代理：不希望展示对象内部细节（如远程服务）、对象访问需限制（如 AOP）。
  - 装饰：特殊的代理，不改变接口增强功能或动态加职责，比子类更灵活，运行中的项目可加装饰类轻松扩展。
  - 适配器：主要意图是接口转换，屏蔽外界接口以免深入系统内部，提高稳定性和可靠性。
  - 桥梁：在抽象层产生耦合，解决自行扩展问题，使两个有耦合关系的对象互不影响地扩展（笔×图的例子）。
  - 门面：**粗粒度**封装，提供方便访问子系统的接口，不具有任何业务逻辑，仅是访问复杂系统的快速通道——没有它子系统照样运行，有了它只是更方便访问。

## 第34章 命令模式+责任链模式（L21248-22039）——混编实战：搬移UNIX命令

> 从本章起进入第4部分"混编实战"：作者用完整项目演示多个模式如何各司其职地组合。本章目标：在 Windows 下自己写一个能解析 UNIX 命令（如 ls -l）的 shell 工具。

### 34.1 需求拆解与模式选择的推理链（核心价值）

- **需求**：UNIX 命令 = 命令名+选项+操作数（如 `ls -l /usr`）。ls 命令族的要求：①每个命令都有操作数，默认当前目录；②选项不可重复（`ls -l -l -s` 只解析出 l 和 s 两个选项）；③**每个选项返回不同结果，即每个选项应由不同的业务逻辑处理**；④ls 命令族内运算对外封闭，减少外界访问内部细节的可能性（L21300-21305）。
- **第一层推理（命令族内部 → 责任链）**：针对一个命令族，"只要把一个参数传递到链首，就可以立刻获得一个结果，中间是如何传递的以及由哪个逻辑解析都不需要外界（高层）模块关心"——选**责任链模式**（L21306-21308）。
- **第二层推理（命令族之间 → 命令）**：UNIX 命令上百个，需要派发角色——"输入一个命令，不管后台谁来解析，返回一个结果就成"，**命令模式负责协调各个命令正确地传递到各个责任链的首节点**（L21338-21341）。
- **类结构**：CommandName 抽象类（责任链 handler，控制链表）→ 每个命令族一个独立抽象类 AbstractLS/AbstractDF（标记该族+安放族的个性化数据）→ LS/LS_A/LS_L 实现类（每个选项一个节点，声明自己能处理什么参数 getOperateParam + echo 执行）。

### 34.2 关键实现与作者的取舍（五要素式摘录）

- **AbstractLS 是个空抽象类**（只定义 3 个选项名常量），两个职责：标记 ls 命令族、个性化处理。作者解释：现在还没想清楚 ls 有什么个性，"先写个空类放在这里，以后想清楚了再填写上去，留下一些可扩展的类也许会给未来带来不可估量的优点"（L21440-21446）。
- **Command 抽象类的双重职责**：定义命令执行方法 + 负责命令族（责任链）的建立。buildChain 用 ClassUtils.getSonClass 反射取出某命令族抽象类下所有子类，Class.forName().newInstance() 建链（L21556-21558）。
- **代价警告**：ClassUtils（根据父类查同包下所有子类）"请大家谨慎使用，在核心的应用中尽量不要使用该工具，它会严重影响性能"——反射建链以牺牲性能换扩展性（L21639）。
- **CommandVO 值对象**：约定命令必须有命令名/选项/操作数三项，缺失则以长度为零的字符串代替，"通过这样的一个约定可以大大降低命令解析的开发工作"（L21712-21713）；getParam 用 `new ArrayList(new HashSet(paramList))` 去重，保证选项不可重复需求。
- **CommandEnum 枚举作命令配置文件**：作者解释为何用枚举而非接口——"枚举的基本功能就是定义默认可选值，但 Java 中的枚举功能增强了很多，可以添加方法和属性，基本上就是一个特殊的类"（L21781-21783）。
- **代码示例一句话**：FileManager/DiskManager 是与操作系统交互的占位实现（示例性代码），真实实现给了三条思路：java.io.File 封装、Runtime.exec 执行 DOS dir、JNI 调动态链接库（L21519-21523）。

### 34.3 扩展验证与混编小结

- **扩展 df 命令族的验证**：仅增加 DFCommand、AbstractDF、DF/DF_K/DF_G 类 + CommandEnum 加一行枚举项即完成——"仅仅增加类就完成了变更，这才是我们要的结果：对修改关闭，对扩展开放"（L22004）。
- **四个模式的分工（L22005-22021）**：
  - **责任链**：负责命令参数的解析；所有扩展都是增加链数量和节点，不涉及原有代码变更。
  - **命令**：负责命令的分发，把适当的命令分发到指定的链上。
  - **模板方法**：CommandName.handleMessage 是典型模板方法（框架逻辑固定，echo/getOperateParam 基本方法由实现类实现）；Command.buildChain 也是模板方法（无基本方法）。
  - **迭代器**：for(Class c:classes) 语法的支撑，JDK 已融入 API。
- **遗留问题的两个方案**：`ls -l -a` 组合选项未处理。①独立处理：把"la"当一个参数扩展一个类，缺点是类膨胀太大但简单；②混合处理：修正处理链让每个节点处理完继续传给后续节点，Command 类组装各节点结果（返回值放 Collection）（L22022-22031）。
- **命名**：该框架叫做**命令链（Chain of Command）模式**——"命令模式作为责任链模式的排头兵，由命令模式分发具体的消息到责任链模式"（L22032-22033）。
- **作者忠告/优化方向**：程序还可优化为 Command 缩为一个类、通过 CommandEnum 配置传递命令；读者可继续扩展。

## 第35章 工厂方法模式+策略模式（L22040-22519）——混编实战：迷你版交易系统扣款模块

> 场景：集团"一卡通"联机交易子系统的**扣款子模块**——业务上扣款失败即交易关闭不允许发生；技术上异常/事务/鲁棒性不容忽视（饭点并发量恐怖）。IC 卡有固定金额（不可提现、特定消费）与自由金额两种，对应两套扣款规则：策略一=两种金额各扣一半（防止乱请客，请人吃饭自己也出一半）；策略二=全部从自由金额扣除。

### 35.1 模式选择的推理链（本章核心价值，L22084-22101）

1. **先识别出策略模式，但立刻点破其缺陷**：扣款策略是典型的策略模式应用，"但是你还记得策略模式是有缺陷的吗？它的具体策略必须暴露出去，而且还要由上层模块初始化，这不合适，与迪米特法则有冲突"——高层次模块对低层次模块应仅处在"接触"层次而非"耦合"关系，否则维护工作量非常大（L22087-22090）。
2. **用工厂方法修正**：工厂方法模式可以产生指定对象，"但是问题又来了，工厂方法模式要指定一个类，它才能产生对象，怎么办？引入一个配置文件进行映射，避免系统僵化"——用枚举类完成映射（L22090-22092）。
3. **交易编号↔策略的对应关系**：状态模式或责任链都可以，但作者论证状态模式不适合——"一笔确定的交易它的状态不会从一个状态过渡到另一个状态……执行完毕后即结束，不存在多状态的问题"；实际项目中用关系型数据库存储扣款规则与交易编码的对应关系，讲义用条件判断语句代替（L22093-22099）。
4. **整体封装**：复杂扣款模块不能让上层业务模块直接深入内部→请出**门面模式**（L22100-22101）。
- **设计前提**：联机交易日后允许大规模变更的可能性基本为零，系统设计要做到可拆卸（Pluggable），避免日后维护的大量开支（L22084-22086）。

### 35.2 关键实现与作者的自省

- **代码示例一句话**：Card/Trade 两个值对象 + IDeduction 接口 + SteadyDeduction（各扣 50%，除数是 2.0 不是 2 再四舍五入）/FreeDeduction 两个具体策略 + DeductionContext 封装角色 + StrategyMan 枚举（登记容器）+ StrategyFactory 工厂 + DeductionFacade 门面（deduct 静态方法串起全流程）。
- **策略模式的边界论断**："这两个具体的策略与我们的交易类型没有任何关系，也不应该有关系，策略模式就是提供两个可以相互替换的策略，至于在什么时候使用什么策略，则不是由策略模式来决定的"（L22246-22248）——选择权交给了门面/配置。
- **门面中含业务逻辑的自省**：门面模式明确说明门面类不允许有业务逻辑，但示例的 DeductionFacade 里有判断逻辑 getDeductionType——作者解释：该方法完全可以移到其他 Helper 类中，示例代码没有明确业务含义才放此处，"读者在实际应用中，请把该方法放置到其他类中"（L22343-22346）。实际项目中该方法靠数据库 SQL 返回对应扣款策略。
- **快乐路径声明**：示例没考虑余额不足、异常、并发——一张卡两笔消费同时发生（网络阻塞、MQ 多通道发送时可能出现）就会出错，"我们在这里的讲解实现的是一个快乐路径"（L22226-22230）。
- **实战细节**：金额用 int 而非 double/BigDecimal——一般非银行交易系统内存放 int，显示时才转换为货币类型（L22156-22158）；银行真实系统的交易编号用数字而非字符串，"数字运算可比字符运算快得多"（L22163-22165）。

### 35.3 混编小结与业务变化演练（L22486-22515）

- **三个模式的分工**：
  - **策略**：封装扣款策略，保证两个策略自由切换，日后增加策略简单容易。
  - **工厂方法**：修正策略必须对外暴露具体策略的问题，由工厂直接产生具体策略对象，其他模块不需要依赖具体策略。
  - **门面**：封装复杂扣款系统，避免高层模块深入子系统内部，提供高内聚、低耦合特性。
- **扩展成本演练**：
  - 新增扣款策略只需三步：实现 IDeduction 接口、增加 StrategyMan 配置项、扩展扣款策略利用规则（实际项目=增加数据库配置项）。
  - **真实变更案例**：系统投产后业务提出退休人员场景——扣款不仅看交易编码还要看 IC 卡对象。变更做法：增加一个扣款策略+扩展利用规则配置，在 getDeductionType 中根据卡号判断退休人员用新策略，"这是一个非常简单的扩展"（L22509-22513）。
- **作者忠告**：这就是 mini 版金融交易系统，"没啥复杂的，剩下的问题就是开始考虑系统的鲁棒性，这才是难点"（L22514-22515）。

## 第36章 观察者模式＋中介者模式——事件触发框架

> 行号范围：L22520-23167。主题：从零搭建一个「行为产生事件→事件通知处理者→处理者处理」的事件触发框架，观察者负责通知、中介者负责分发协调。

### ① 主题意图
用观察者模式解决「事件如何通知处理者」，用中介者模式解决「事件如何分发给多个处理者并协调它们」，二者串联构成完整事件触发架构（L22520-22521, L22848-22874）。

### ② 使用场景与触发条件
- 产品有创建、修改、销毁、克隆等行为，行为发生时要触发对应事件并有对象处理（L22530-22534, L22566-22569）。
- 事件处理者数量多（作者设想 30 多个产品类）、一类事件可能多个处理者、处理者之间还有相互通知耦合——这时不能让处理者直接互调，需要中介者统一分发协调（L22851-22857, L22871-22874）。
- 触发混编的顺序：先工厂方法+原型搭出产品层 → 引入观察者搭通知渠道 → 桥梁组合产品与事件 → 最后引入中介者处理「多处理者分发协调」问题（L22535-22539, L22666-22669, L22775-22777, L22871-22874）。

### ③ 反例 / 缺点 / 代价
- 单来源调用（Single Call）：产品构造函数必须传工厂对象且校验 `isCreateProduct()`，实现了「产品只能由工厂创建」，但代价是产品与工厂绑死（L22549-22563, L22664-22665）。作者注明：这是方法不是设计模式，适用于有单例和工厂方法模式的场景（L22549-22550, L22664-22665）。
- ProductEvent 继承 Observable（观察者）的同时在自身构造函数里就调用 notifyEventDispatch 完成通知——事件产生即通知，时机由事件对象自身控制（L22739-22740, L22753-22758）。
- EventDispatch 单例「避免了对象膨胀，但同时也带来了性能及线程安全隐患」，作者提醒注意，并类比 Spring Bean 默认单例：通常不用改，除非较大并发（L22696-22698）。
- EventDispatch 一人兼三职（观察者/中介者/处理者管理员），作者自认与单一职责原则相违背：「如果强制细分也可以完成，但是会加大代码量，同时导致系统的结构复杂」（L22875-22884, L22921-22924）。

### ④ 论据（转述+行号）
- **单来源调用机制**：工厂 createProduct 先置 `isPermittedCreate=true` 再 new 产品，产品构造函数里向工厂查权限；即使 `new Product(new ProductManager(), "abc")` 也造不出有效产品，因为 isPermittedCreate 初始为 false（L22622-22626, L22655-22658）。作者比喻：工厂出示两个证明（我是你的工厂类+我有权创建），产品才被创建（L22658-22662）。
- **桥梁模式的隐身用法**：产品与事件两个独立可扩展对象用桥梁组合；「看着不像桥梁模式？……把抽象化角色和实现化角色去掉看看，是不是就是一样了？」因单个产品对象无需抽象化，读者扩展时才需抽接口（L22775-22777, L22794-22801）。ProductManager 修正后在四个方法里都 new 出对应类型事件，组合产生「有意义的产品事件」（L22803-22843）。
- **中介者核心**：EventDispatch.update 里双层 for 循环，遍历注册的处理者与其处理能力（customType），事件类型值匹配即调 `e.exec(event)`（L22941-22959, L22964-22966）。作者强调：「在设计这样的框架前，一定要定义好消费者与生产者之间的搭配问题，一般的做法是通过 xml 文件类或者 IoC 容器配置规则」（L22966-22968）。
- **处理者按能力注册**：EventCustomer 构造函数强制声明处理级别，可多值（贵族能同时处理 EDIT 与 CLONE 两类事件）（L22975-22996, L23063-23083）。
- **替代方案提示**：贵族两类事件分别处理时，读者可能想到责任链；作者认可 Servlet Filter 就是这种设计，框架平台开发可用，扩展性稳定性好（L23082-23088）。
- 代码演示：乞丐/平民/贵族三个处理者与场景类，模拟创建/修改/克隆/销毁原子弹的四种事件，验证「有行为就产生事件、有处理者消费、三者解耦可独立扩展」（L23018-23144）。

### ⑤ 最佳实践 / 作者忠告
- 单来源调用的两个对象一般是**组合关系、相同生命期**，通常适用于有单例模式和工厂方法模式的场景（L22664-22665）。
- 「设计原则只是一个理论，而不是一个带有刻度的标尺……应该把它看成是一个方向标，尽量遵守，而不是必须恪守。」（L22925-22926）——EventDispatch 三职责合一即是此忠告的正面案例。
- 扩展框架时的候选模式：责任链（一个处理者处理多事件）、模板方法（处理者启用停用）、装饰（事件包装、处理者功能强化）（L23161-23164）。
- 扩展性验证：加处理者只需继承 EventCustomer 并注册；扩展产品需先抽产品和事件的抽象类（L23141-23144）。

### 混编结构一览（作者小结，L23148-23160）
| 模式 | 在框架中的职责 |
|---|---|
| 工厂方法 | 产生产品；实现产品与工厂紧耦合，避免产品被随意创建而无触发事件 |
| 桥梁 | 组合产品与事件，两者自由扩展不破坏封装（前提是抽取抽象化） |
| 观察者 | 解决事件如何通知处理者；支持多层级、多分类处理者 |
| 中介者 | 处理者会变化且相互有耦合，中介者完美处理这些复杂关系 |

## 第37章 规格模式（Specification Pattern）

> 行号范围：L23168-23911。主题：从零实现内存对象的条件查询（类似 LINQ 的 where 子句），引出规格模式——组合模式的特殊应用＋策略模式身影。

### ① 主题意图
把「对象群中类似 SQL where 的查询条件」封装成规格书（Specification）对象，让条件可自由进行与/或/非组合，实现可扩展的多对象筛选（L23181-23184, L23786）。

### ② 使用场景与触发条件
- 触发条件：查询条件会持续变化（今天查年龄>20，明天查年龄<30，后天查姓名含“国庆”），导致按条件命名的接口方法（findUserByAgeThan 等）必须一直修改——接口是契约，不该被修改（L23316-23320）。
- 适用场景（作者最佳实践）：多个对象中筛选查找；业务规则不适合放在任何已有实体或值对象中、且规则的变化和组合会掩盖领域对象的基本含义；想自己编写类似 LINQ 的语言工具（L23904-23907）。
- 演进路径（作者的四步迭代）：
  1. 常规做法：UserProvider 按每个条件写方法 → 接口随需求膨胀，设计失败（L23244-23281, L23316-23320）。
  2. 尝试 `findUser(boolean condition)` 把条件外置 → 「封装就没有任何意义」，方案否决（L23326-23337）。
  3. 封装整个条件为规格书 IUserSpecification.isSatisfiedBy(user)，findUser 只收规格书 → 一个方法覆盖 N 多查询路径（L23338-23364, L23429-23431）。
  4. 引入 and/or/not 组合操作解决复合条件（L23529-23552 → L23553-23556）。

### ③ 反例 / 缺点 / 代价
- **两次过滤反例**：查「名字含国庆且年龄>25」，用两个规格书先后两次 findUser 过滤：能实现，但对象数量巨大时两次循环效率太低；且与/或/非自由组合会产生组合爆炸，「这种设计就不妥了」（L23532-23535 代码，L23546-23552 论述）。
- 父类（CompositeSpecification）依赖子类（直接 new AndSpecification 等）——跳出了面向对象常规思维；作者明确：「否则是严禁出现父类依赖子类的情况的」，此处成立的前提是与或非操作固化不变（L23698-23701）。
- 注意事项（原文）：「父类依赖子类的情景只有在非常明确不会发生变化的场景中存在，它不具备扩展性，是一种固化而不可变化的结构。」（L23592-23593）

### ④ 论据（转述+行号）
- **规格书定义**：「它是对一批对象的说明性描述，它依照基准判断候选对象是否满足条件。」（L23338-23340）
- **封裝变化**：两个 find 方法唯一的不同是 if 后的判断条件，「我们一直在说封装变化，这两段程序就仅仅有这一个变化点，我们是不是可以把它封装起来呢？」（L23321-23324）
- **组合操作的设计洞察**：AND/OR/NOT 的返回结果仍是规格书，「规格书对象之间可以进行与或非操作，操作的结果不变」——这是接口加 and/or/not 三个方法的依据（L23553-23556）。
- **与或非放基类**：作者论证：与或非不可扩展、不需预留扩展空间（操作符不会增加），所以可固化在基类；返回值需规格书类型而基类是抽象类不能实例化，故基类 new 子类再递归计算（L23572-23591）。
- **模式定位**：全局看，基类代表整体（完整可组合的规格书），And/Or/Not/业务规格书是局部，「现在我们又回到了整体和部分的关系了……组合模式，它是组合模式的一种特殊应用」；同时「还能不能找到其他模式的身影？对，策略模式」，替换规格书上层逻辑无需任何改变（L23760-23785）。
- 模式出身：规格模式「不属于23个设计模式，它是其中一个模式的扩展」（L23756-23760）。
- 代码演示：UserByNameLike 规格书用 `%` 标记实现 SQL like 的前缀/后缀/包含三种匹配（L23471-23496）；场景类 `spec.and(spec2)` 链式组合查询验证（L23739-23750）。

### ⑤ 最佳实践 / 作者忠告
- **照抄清单**：一个接口（ISpecification）、一个抽象类（CompositeSpecification）、3 个实现类（And/Or/Not Specification），「只要在适用规格模式的地方都完全相同，不用做任何的修改，大家闭着眼照抄就成」；唯一要写的是业务规格书 BizSpecification 的 isSatisfiedBy 判断逻辑（L23869-23871, L23873-23883）。
- 通用类图中把四个方法名（isSatisfiedBy/and/or/not）固定定义出来，因为只要用规格模式方法名就是这四个——「把组合模式更加具体化了，放在一个更狭小的应用空间中」（L23781-23783）。
- 面向接口编程的目的是适应变化，「对于不可能发生变化的部分为什么不能固化呢？」——固化不可变部分是一种合理设计（L23586-23591）。
- 评价：规格模式「巧妙地实现了对象筛选功能」，是「非常具体的应用框架（相对于23个设计模式）」（L23786, L23904）。

### 模式结构速记
ISpecification(isSatisfiedBy/and/or/not) → CompositeSpecification（抽象类，直接 new 子类实现与或非）→ And/Or/NotSpecification（恒定不变，可照抄）＋BizSpecification（唯一修改处：业务判断）。

## 第38章 MVC框架（L23912-24791）——混编压轴：设计一个可抗衡Struts的MVC框架

**主题意图**：全书压轴实战——不讲MVC技术本身，而是通过亲手设计一个轻量MVC框架，展示设计模式在工业级框架中如何按模块落点组合应用（L23982-23983, L24752-24758）。

### 38.0 框架全貌

- **MVC意图**：通过控制器C把模型M（业务数据和业务逻辑）与视图V（人机交互界面）实现代码分离，同一逻辑/数据可具不同表现形式（如HTML浏览器与WAP手机访问同一模型，L23920-23928）。
- **Model1 vs Model2**（L23929-23943）：Model1视图中存在大量流程控制，控制器与视图部分耦合（JSP+JavaBean拆分）；Model2提倡视图与模型彻底分离，视图仅负责展示、不参与业务行为与数据处理。
- **五模块架构**（L23988-24016）：①核心控制器FilterDispatcher（MVC入口，接收反馈HTTP请求）②过滤器（Servlet容器内、必须依靠容器，本章不细讲）③拦截器（不依赖容器，只过滤框架内业务数据）④模型管理器（所有业务操作应**无状态**、不关心Session/线程池等容器对象，L24010-24012）⑤视图管理器+辅助工具。

### 38.1 核心控制器：责任链 + 策略 + 观察者 + 中介者思想

- **入口=Servlet Filter拦*.do**（L24094-24111）。doFilter流程（代码清单38-1一句话概括）：取actionName→建ViewManager→请求参数压值栈→actionDispatcher.actionInvoke→查视图路径→forward。
- **责任链**：`chain.doFilter(req,res)`表示让后续过滤器先运行，Servlet容器按web.xml配置顺序把所有过滤器组装成过滤器链——前提是所有过滤器必须实现Filter接口（L24257-24262）。
- **中介者思想变体**：类图类似中介者模式，但**没有把中介者传递到各同事类**，而是采用中介者思想、把职责分发出去由各同事类处理（L24266-24268）；最佳实践对应表述：「以核心控制器为核心，其他同事类都负责为核心控制器『打工』，保证核心控制器瘦小、稳定」（L24769-24771）。

**init方法两职责**（L24110-24118）：

1. **XML校验=策略模式**：两种完全可替换的检查算法——CommonXmlValidate（语法检查，如少写结束标志）与LogicXmlValidate（框架逻辑检查：反射初始化class属性对象→检查方法存在→返回值须String且无入参、须继承指定类/接口，L24129-24174）。
   - **为何必须可替换（判据）**：逻辑校验启动时需把所有类过滤一遍，牺牲效率——「在生产机上要花20分钟才能把一个应用启动起来……这是不允许的」，故测试机环境用逻辑校验、生产环境只用语法校验（L24137-24140）。
   - 金句：「与通用策略模式稍有不同，**每个模式在实际应用环境中都有其个性，很少出现完全照搬一个模式的情况，灵活应用设计模式才是关键**」（L24197-24198）。
2. **配置监控=观察者模式**：配置修改后不应重启应用才生效（L24115-24117）。FileWatcher extends Observable implements Watchable——启动线程每15秒扫描文件，发现日期被修改立刻notify观察者Checker（implements Observer，L24227-24255）。Watchable接口抽象所有可监视资源（数据库、日志文件、磁盘空间等，L24214-24215）。
   - **性能答疑**：死循环监控不影响性能——检查文件是毫秒级，相对15秒周期可忽略；类比Log4j每5秒检查日志是否满（L24241-24245）。

### 38.2 模型管理器：门面+代理+模板方法+迭代器+责任链变体+工厂方法

- **门面**：IActionDispatcher.actionInvoke是模型行为分发的唯一门面，隐藏「查配置→执行→值栈→异常」复杂性（L24271-24296）；「避免外部模块深入到模型模块内部」（L24783-24785）。
- **动态代理**：ActionManager根据actionName查XML节点，通过动态代理执行方法（L24346-24349）。**反射性能论**：「实际应用还没有这么高的要求，把数据库设计得优秀一点，系统架构多考虑一点，提升的性能远比这个多」（L24350-24351）。
- **ActionSupport**：默认execute()对应XML可省略method配置，还承担对象映射职责（L24302-24331）。
- **拦截器vs过滤器**（触发条件）：拦截器可脱离J2EE容器运行，过滤器不行；拦截器对进出模型的数据过滤（L24352-24353）。
- **模板方法**：AbstractInterceptor的exec为final，开发者只需两职责——setType（前置/后置/环绕）+实现intercept，不用考虑如何调用ActionInvocation（L24360-24390）。与Struts不同之处作者自陈：本书是讲模式的技术实现，Struts属工业级框架、考虑太多外界因素（L24379-24381）。
- **Interceptors implements Iterable**：迭代器模式方便遍历+链结构即责任链；但FilterChain是容器实现的，拦截器链需自己编码（L24394-24415）。
  - **与责任链的关键差异（取舍点）**：责任链「只要有节点处理就可以认为是结束，后续节点可以不再参与处理」；拦截器链的intercept委托第一个节点后**所有拦截器按顺序执行一遍**（L24418-24422）。
  - **自激行为**：Interceptors构造函数自己建链（XML中一个拦截器配置含多个拦截器），而非父类/高层模块建链（L24416-24418）。
  - 命名细节：用「拦截器链」而非Struts的「拦截器栈」，一字之差系统设计差别大（L24423-24425）。
- **工厂方法**：InterceptorFactory根据配置文件一次性创建所有拦截器链（L24431-24437）；扩展思考：配置文件修改→拦截器链应重建→还应有一个观察者（留给读者，L24437-24440）。
- **性能忠告**：「拦截器是会影响系统性能的，所有Action在执行前后都会被拦截器过滤一遍，**即使不符合拦截条件的也会被检查一遍**，所以非必要情况不要使用拦截器」（L24426-24427）。

### 38.3 值栈：两职责，模式少故从略

- 管理堆栈：不止出入栈——允许前置拦截器修改栈数据、限制后置拦截器修改、与HttpServletRequest数据建立关联（L24446-24451）。
- 值映射：HTTP字符串→业务对象（如userName/password→User对象）。约定**点号区分**：点号前是对象名、点号后是属性名，反射实现；可用开源工具dozer（L24452-24459）。

### 38.4 视图管理器：桥梁模式

- **问题**：视图三部分——静态页面（前台人员开发）/动态页面元素（语言、浏览器差异特别是JavaScript细节，「稍不注意就可能产生灾难」）/动态数据（结构固定可反复加载，L24464-24476）。难点是把动态页面元素融入静态页面：页面类型多×语言类型多。
- **桥梁解法**（「用什么笔画什么图形」类比，L24482-24483）：AbsView×AbsLangData双维抽象——JspView（直接替换资源项如{title}→「标题」，替换后存缓存目录提效）/SwfView（不能替换，重写URL传参）×GBLangData/ENLangData（Map结构）（L24513-24609）。ViewManager是视图模块唯一入口（L24610-24635）。
- **效果**：「即使以后增加语言也非常容易扩展」（L24636-24637）。

### 38.5 工具类：适配器+访问者

- **适配器**：DOM4J的Node/Element/Attribute「不能保证一个开发组的人都对这些都了解」→问题是「如何把一个DOM4J对象转换成自己设计的对象」→XmlActionNode extends ActionNode对象适配器，传入Element转为自设计的Action节点（L24639-24681）。价值：「系统开发人员就不用考虑开源工具对系统的影响，**屏蔽了工具系统的影响**」（L24711-24716）。
- **访问者**：getView用DOM4J提供的VisitorSupport优秀API——ViewPathVisitor遍历元素、找name等于result的元素取文本为视图路径（L24700-24743）。

### 38.6 对象管理：单例→原型→享元的演进链（L24744-24750）

- 每个HTTP请求产生一个线程，Action若是**单例**：并发足够多时阻塞、性能严重下降，特定情况下线程不安全→需多例。
- 多例实现：**原型模式**（Clone）——系统启动时初始化所有Action，每个请求拷贝一个，减少初始化性能消耗。
- 新问题：并发较多时可能**内存溢出**→**享元模式**上场，建对象池容纳足够多对象。
- 取舍：Action默认单例在一般应用足够，复杂情况用享元提高性能、减少单例隐患（L24762-24764）。

### 38.7 最佳实践：本章模式清单（12种，L24760-24787）

| 模式 | 落点 |
|---|---|
| 工厂方法 | 创建所有拦截器链，系统初始化时直接处理 |
| 单例 | Action默认单例；复杂情况用享元补充 |
| 责任链 | 拦截器链+过滤器链，任务链条化处理 |
| 迭代器 | 方便遍历拦截器链，无需自写遍历方法 |
| 中介者 | 核心控制器为核心，同事类为其打工，保证核心控制器瘦小稳定 |
| 观察者 | 配置文件修改即刻生效、无需重启应用 |
| 桥梁 | 不同视图配合不同语言文件 |
| 策略 | XML检查两种策略，测试机/生产机自由切换 |
| 访问者 | 解析XML时方便访问需要的对象 |
| 适配器 | 不熟悉对象→熟悉对象，避免工具对开发者影响 |
| 门面 | Action分发唯一入口 |
| 代理 | 大量动态代理，确保框架智能化 |

### 作者忠告

- 「看一本书是与作者进行了一次心灵交互，**看一份源码是与一群作者进行心灵交互**」——读Struts、Spring MVC源码是提高设计技能的重要途径（L24788-24791）。
- 框架设计定位：轻量型，希望程序在没有Struts/Spring MVC等框架的环境中不需大规模修改照样能运行（L24756-24757）。
