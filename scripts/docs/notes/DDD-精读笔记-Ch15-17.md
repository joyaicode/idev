## 第15章 精炼（Distillation，OCR 12403–13404，PDF 281–304）

### 15-1 CORE DOMAIN（核心域）：自主开发的最大价值来自对核心的完全控制｜PDF281｜行12403–12428
- 「自主开发的软件的最大价值来自于对CORE DOMAIN的完全控制。」（12422）
- 核心域不能靠短期外聘或购买：短期人员造成知识流失（12409–12411）、购买特定行业框架「除了PUBLISHED LANGUAGE能够促进数据交换以外，其他的结果并不理想」（12417–12418）。
- 框架约束超出限度有三种原因：①失去重要软件资产（让框架退出核心）②框架处理的部分并非核心（重划核心边界）③核心并无特殊需求（考虑购买集成）（12423–12427）。
- 「创建与众不同的软件……需要一支稳定工作的团队，他们不断积累和消化专业知识，并将这些知识转化为一个丰富的模型。没有捷径，也没有魔术弹。」（12427–12428）

### 15-2 精炼的逐步提升（Distillation progression）｜PDF282–283｜行12430–12452
- 精炼技术按投入递增：DOMAIN VISION STATEMENT（很少投入）→ HIGHLIGHTED CORE（改善沟通、指导决策，很少改动）→ 显式分离 GENERIC SUBDOMAIN → COHESIVE MECHANISM → SEGREGATED CORE（核心清晰可见）→ ABSTRACT CORE（全面重组重构，最积极）。
- 「每种技术都需要我们连续不断地投入越来越多的工作，但刀磨得越薄，就会越锋利。领域模型的连续精炼将为我们创造一项资产。」（12451–12452）

### 15-3 模式：GENERIC SUBDOMAIN（通用子领域）｜PDF283–285｜行12453–12520
- 「模型中有些部分除了增加复杂性以外并没有捕捉或传递任何专门的知识。任何外来因素都会使CORE DOMAIN更难以分辨和理解。」（12453–12455）
- 四种选择：①购买现成实现 ②采用公开发布的设计或模型 ③把实现外包出去 ④内部实现（12500–12540 区间）。外包应要求单元测试、指定/编写自动验收测试（12530–12535）。
- 通用子领域是「充分利用外部设计专家的地方」，因为专家不需要深入理解专有核心域（12540–12542）。

### 15-3.1 通用不等于可以重用｜PDF286–287｜行12610–12630
- 「我并没有提到代码的可重用性……不要特别关注代码的可重用性。因为如果这样做就会违反精炼的基本动机——我们应该尽可能把大部分精力投入到CORE DOMAIN工作中。」（12610–12614）
- 「我们不必把它开发成『万能的』模型。我们只要把业务所需的那部分建模出来并实现即可。」（12624–12625）
- 把行业专用概念引入通用子领域会：①妨碍将来扩展 ②这些专用概念要么属核心域、要么属更专业子领域，比通用子领域更有价值（12626–12630）。

### 15-3.2 项目风险管理｜PDF287–288｜行12631–12680
- 敏捷/XP 要求尽早解决最具风险的任务，但「试图建立一个周边系统来先处理支持性 GENERIC SUBDOMAIN」可能不利于风险管理——因为核心域才是最大的风险与价值所在。
- 时区双例对照（12640–12680）：运输项目把时区当 GENERIC 分离、核心成熟、用短期程序员；保险项目核心未开发、需求不明却试图做「万能」时区模块、最好的程序员没做核心。「技术人员喜欢处理那些可定义的问题……但严格地从优先级角度来看，他们应该先去完成CORE DOMAIN的工作。」（12674–12676）

### 15-4 模式：DOMAIN VISION STATEMENT（领域前景说明）｜PDF288–290｜行12681–12740
- 用一句话传达核心概念及其价值：核心域是什么、它为什么有价值、团队要朝什么方向努力。
- 它「只需很少的投入」，是精炼的起点，也是后续 HIGHLIGHTED CORE / GENERIC SUBDOMAIN 分离的依据。

### 15-5 模式：HIGHLIGHTED CORE（突出的核心）｜PDF290–292｜行12741–12840
- 在文档（如领域前景说明）和代码中把核心概念「突出」出来，改善沟通并指导决策制定。
- 精炼文档（Distillation Document）描述核心域及它与通用子领域的交互，作为团队共享的导航图。

### 15-6 模式：COHESIVE MECHANISM（内聚机制）｜PDF292–294｜行12841–12990
- 把复杂的计算问题（如图遍历、规格组合）封装成独立的机制框架，与领域模型分离。
- 「模型提出问题，COHESIVE MECHANISM解决问题。」（12930–12931）
- 好处：声明式风格描述组织、复杂代码分离到基于成熟算法的机制框架、可单独维护与单元测试（12910–12920）。

### 15-6.1 GENERIC SUBDOMAIN 与 COHESIVE MECHANISM 的比较｜PDF294–295｜行12991–13010
- 动机相同（为核心域减负），职责性质不同：GENERIC SUBDOMAIN 以「描述问题的模型」为基础，表示团队如何看待领域某方面；COHESIVE MECHANISM 不表示领域，只解决描述性模型提出的复杂计算问题。

### 15-6.2 MECHANISM 是 CORE DOMAIN 一部分（例外）｜PDF295–296｜行13011–13040
- 几乎总想把机制从核心分离，例外是「机制本身就是一个专有部分并且是软件的一项核心价值」（如投资银行高度机密的风险评估算法）。
- 是否精炼成更深层模型取决于成本-效益分析（13030–13035）。

### 15-7 通过精炼得到声明式风格｜PDF296–297｜行13041–13070
- 精炼的价值在于「使你能够看到自己正在做什么，不让无关细节分散你的注意力，并通过不断削减得到核心」。
- 支持性部分提供简练语言 + 封装计算方式 → 核心域可采用声明式设计；深层模型与柔性设计一起产生（13055–13060）。

### 15-8 模式：SEGREGATED CORE（隔离的核心）｜PDF297–299｜行13071–13160
- 「对模型进行重构，把核心概念从支持性元素中分离出来，并增强CORE的内聚性，同时减少它与其他代码的耦合。」（13120–13122）
- 五步：①识别核心子领域 ②把相关类移到新模块并按概念命名 ③把不直接表示概念的数据/功能分离出去 ④重构新核心模块使关系更简单清楚 ⑤对另一个核心子领域重复（13130–13140）。

### 15-8.1 创建 SEGREGATED CORE 的代价｜PDF299–300｜行13161–13200
- 隔离核心可能使核心与非核心类的关系更晦涩，但「CORE DOMAIN更清晰了，而且更易于处理，因此获得的好处还是足以抵偿这种代价」。

### 15-9 模式：ABSTRACT CORE（抽象内核）｜PDF300–304｜行13201–13404
- 用抽象形式表示最基本的概念和关系，需要对模型进行全面重组重构，是最积极的精炼技术。
- 重构优先级：「如果采用『哪儿痛治哪儿』……观察根源问题是否涉及CORE DOMAIN……如果确实涉及，那么就要接受挑战，首先修复核心。」（13380–13390）

## 第16章 大比例结构（Large-Scale Structure，OCR 13405–14774，PDF 305–336）

### 16-1 大比例结构：全局组织原则｜PDF305–307｜行13405–13480
- 大系统需要「全局性的原则」来解释元素在整体中的角色，否则「只见树木，不见森林」。
- 「大比例结构是一种语言，人们可以用它来从大局上讨论和理解系统。它用一组高级概念或规则（或两者兼有）来为整个系统的设计建立一种模式。」（13420–13422）
- 大部分大比例结构无法用 UML 表示，也不需要在设计中直接出现，只是「表达设计的另外一种方式」（13450–13452）。

### 16-2 模式：EVOLVING ORDER（演化秩序）｜PDF307–309｜行13481–13570
- 前期使用大比例结构成本很大，过早固定的架构「使很多前期设计决策定格，随着需求的更改和理解的深入，这些架构会使项目变得束手束脚」（13510–13513）。
- 结构应随理解加深而演化，不因「经理认为架构已定下来」而拒绝调整（13525–13535）。

### 16-3 模式：SYSTEM METAPHOR（系统隐喻）｜PDF309–311｜行13571–13660
- 当系统的一个具体类比「正好符合团队成员对系统的想象，并且能够引导他们向着一个有用的方向进行思考」时，把它用作大比例结构，并吸收到 UBIQUITOUS LANGUAGE 中（13600–13605）。
- 所有隐喻都不完全精确，应不断检查是否过度或不恰当，发现妨碍作用时随时准备放弃（13605–13608）。
- 「幼稚隐喻」（Naive Metaphor）这个术语应该停止使用——成熟领域模型绝不幼稚（13620–13630）。

### 16-4 模式：RESPONSIBILITY LAYER（责任层）｜PDF311–317｜行13661–14050
- 把分层与职责驱动设计结合：按主要职责做概念分层，层元素知道/使用「下面」层的服务，不知道「上面」层。
- 变体 RELAXED LAYERED SYSTEM（松散分层系统）：某层组件可访问任何更低层，不限于相邻下一层（13720–13725）。
- 选择层的指导：①场景描述（层应表达领域基本现实/业务优先级，是业务建模决策）②概念依赖性（高层依赖低层，低层独立于高层）③CONCEPTUAL CONTOUR（不同层对象变化频率/原因不同则层应容许）（14000–14020）。
- 典型层：潜能层（能做什么）/ 作业层（正在做什么）/ 决策支持层（应做什么策略）/ 策略层（规则和目标是什么）（14030–14100）。

### 16-5 模式：KNOWLEDGE LEVEL（知识级别）｜PDF317–325｜行14051–14400
- 当需要让用户对模型一部分有所控制、而模型又必须满足更大的一组规则时，用 KNOWLEDGE LEVEL 分离「知识」（规则/类型/角色）与「操作」（事物/实例）。
- 工资/养老金示例（14200–14400）：原模型把 Employee Type 与 Payroll 混在一起，分离出 KNOWLEDGE LEVEL 后 Payroll 才显式化，Employee Type 才能指定 Retirement Plan 与 Payroll 两种。
- 「KNOWLEDGE LEVEL 并不像其他分析模式那样对领域进行建模，而是用来构造模型的。」（14160–14162）
- 与 RESPONSIBILITY LAYER 的区别：两个级别之间依赖是双向的，而层次结构里低层不依赖高层（14380–14385）。

### 16-6 模式：PLUGGABLE COMPONENT FRAMEWORK（可插拔组件框架）｜PDF325–330｜行14401–14680
- 「从接口和交互中提炼出一个 ABSTRACT CORE，并创建一个框架，这个框架要允许这些接口的各种不同实现被自由替换。」（14520–14525）
- 高层抽象在整个系统共享，特化发生在 MODULE 中；中央 hub 是 SHARED KERNEL 内部的 ABSTRACT CORE（14525–14530）。
- 不适合作为项目第一个/第二个大比例结构——「最成功的例子都是在完全开发出了多个专门应用之后才采用这种结构的」（14650–14655）。

## 第17章 领域驱动设计的综合运用（Bringing the Strategy Together，OCR 14775–15570，PDF 337–380）

### 17-1 大比例结构与 BOUNDED CONTEXT / CONTEXT MAP 结合｜PDF337–341｜行14775–14900
- RESPONSIBILITY LAYER 可限定在一个 BOUNDED CONTEXT 内，也可跨越多个 BOUNDED CONTEXT 用于组织 CONTEXT MAP（14775–14780）。
- 遗留系统不必放弃分层：用 FACADE 把每项 SERVICE 设计到某个层，精确描述遗留系统的范围与角色（14820–14840）。
- 每个 BOUNDED CONTEXT 可用不同结构，但「使用过多的结构就会损害大比例结构作为项目统一概念集的价值」（14860–14865）。

### 17-2 将大比例结构与精炼结合起来使用｜PDF341–342｜行14901–14940
- 大比例结构帮助解释 CORE DOMAIN 内部关系及 GENERIC SUBDOMAIN 之间关系；大比例结构本身也可能是核心域的重要部分（如潜能/作业/策略/决策支持层的区分提炼出对业务问题的基本理解）。

### 17-3 首先评估（Assess first）｜PDF342–344｜行14941–15040
- 战略设计前先评估现状：①画 CONTEXT MAP（能否画出一致图，有无模棱两可）②注意语言使用（有无 UBIQUITOUS LANGUAGE，是否足够丰富）③理解重点（CORE DOMAIN 是否被识别，有无 DOMAIN VISION STATEMENT）④技术是否遵循 MODEL-DRIVEN DESIGN ⑤团队是否具备必要技能 ⑥开发人员是否……（14950–14960）。

### 17-4 战略设计需要遵守简约和谦逊的原则｜PDF344–348｜行15041–15200
- 「任何设计工作都必须精炼而简约，而战略设计更要简约。即使是一个非常小的设计失误也有可能会变成可怕的隐患。」（15190–15195）
- 约束自己使组织原则和核心模型「精简到只包含那些能够显著提高设计清晰度的内容」（15195–15200）。

### 17-5 计划必须允许演变｜PDF348–350｜行15201–15300
- 「有效的软件开发是一个高度动态的过程。如果最高层的决策已经固定下来，那么当团队需要对变更做出响应时，选择就会更少。遵循EVOLVING ORDER这一原则，可以避免出现这个问题。」（15260–15265）
- 原则必须随项目生命周期完善，不能过分限制应用开发人员的权力（15265–15270）。

### 17-6 架构团队不必把所有最好、最聪明的人员都吸收进来｜PDF350–352｜行15301–15400
- 把最有技术天分的开发人员都调到架构团队「会留下技术能力较差的人实际构建应用程序……注定会失败」（15330–15340）。
- 战略设计不是纯技术任务，需要领域知识与领域专家参与；架构团队应偶尔从事开发工作（15340–15360）。
