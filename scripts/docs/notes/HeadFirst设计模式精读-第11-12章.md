# 第11章 代理模式（L19989-L22810）

## 一、问题场景（这个模式解决什么问题，书中原始案例）

三个递进案例共用一个结构性动机——客户不应（或不能）直接持有真实对象的引用：

1. 远程访问：糖果公司 CEO 要求在办公室监控全国各地糖果机（GumballMachine）的存量与状态（L20043-20125）。机器在远程 JVM，客户代码无法 new 一台本地糖果机——需要"替身"代表远程对象。
2. 高开销创建：CD 封面查看器要显示网络图片，逐块下载耗时，界面不能空等（L21331-21347）——需要占位符先顶上，真图加载完成前先画图标。
3. 权限控制：约会服务系统里，PersonBean 的方法分属"本人"与"他人"两种调用者：本人可改自己的资料，他人只能评分、不能改别人的资料（L21802-21898）——调用前要按调用者身份裁决，且不能把检查逻辑撒进 PersonBeanImpl。

## 二、模式解法（结构、参与者、关键机制）

### 代理模式（定义 L21159-21167）
为另一个对象提供一个替身或占位符以控制对这个对象的访问。

参与者（类图 L21195-21227）：
- Subject（GumballMachineRemote）：为 RealSubject 与 Proxy 统一接口，使代理可出现在真对象能出现的任何地方
- RealSubject（GumballMachine）：真正做事的对象
- Proxy（远程桩/GumballMonitor 所持引用）：持有 RealSubject 引用，控制访问，并可负责其创建与删除

关键机制：客户面向 Subject 编程，代理拦截访问并按种类附加控制——远程代理管网络交互，虚拟代理管实例化时机，保护代理管调用者权限，动态代理在运行期合成代理类。

### 代理变体
- 远程代理：管理客户与远程对象之间的交互，代表客户处理网络通信（书中用 Java RMI 落地，规则 L20458-20522）
- 虚拟代理（L21232-21268）：作为创建开销大的对象的代表，直到真正需要该对象时才实例化它
- 保护代理：基于调用者控制对对象方法的访问；Java 无内建保护代理，以动态代理实现
- 动态代理：Java 内建支持，运行时合成代理类，所有调用被转发给 InvocationHandler（职责 L21793-21794；两步落地 L21994-21998）

## 三、关键代码例（要点级转述）

1. GumballMachineRemote 接口（L20850-20902）：继承 Remote，每个方法声明 throws RemoteException；不序列化机器本体，改返回可序列化的 GumballMachineState（携带 count/state/location）。
2. GumballMonitor 复用（L20969-20985、L21006）：构造器收 GumballMachineRemote，report() 只调接口方法取数打印——监控代码与本地版几乎相同，不知远程细节（L21099 远程执行，监视器根本不知道也不在乎；L21148 面向 GumballMachineRemote 接口编程）。
3. ImageProxy 两状态（机制三步 L21341-21347；代码 L21364-21373）：paint() 先立即画占位图标；未启动加载则起线程取 ImageIcon；加载完成 setImageIcon 后 repaint 换真图。
4. PersonBean 权限需求（L21813-21898）：接口含 get/set 基本信息、getHotOrNotRating、setHotOrNotRating；约束为"本人可设自己的信息，他人只能设置评分"（L21888-21898）。
5. 动态代理三件套（L21994-22116）：OwnerInvocationHandler（L22049-22051）与 NonOwnerInvocationHandler（L22094-22095）各实现 invoke()，按身份对 set 方法放行或抛 IllegalAccessException；getOwnerProxy（L22104-22116）用 Proxy.newProxyInstance(类加载器, 接口数组, handler) 合成代理。
6. 习题判定（L21499-21501）：ImageProxy 内"两种状态、条件切换行为"若重新设计，答案为状态模式——代理内部可内嵌状态模式管理生命周期。

## 四、OO 原则框（本章亮出的原则/要点，注明行号）

- 本章没有新的原则（L22444 原话"本章没有新的原则"）；设计箱原则清单维持八条（L22440-22443：依赖抽象、只和朋友交谈、别找我我会找你、类应该只有一个改变的理由等）。
- 既有原则兑现：针对接口编程（监视器面向 GumballMachineRemote，L21148）；封装变化（网络/延迟/权限三种变化各自收进代理，真对象不感知）。
- 工具箱新增模式：代理模式——为另一个对象提供一个替身或占位符以控制对这个对象的访问（L22447-22454）。

## 五、章末要点（L22455-22480 原话级概括）

- 代理模式为另一个对象提供代表，以便控制客户对对象的访问，管理访问的方式有许多种。（L22456-22459）
- 远程代理管理客户和远程对象之间的交互。（L22460-22461）
- 虚拟代理控制访问实例化开销大的对象。（L22462-22463）
- 保护代理基于调用者控制对对象方法的访问。（L22464-22465）
- 代理模式有许多变体，例如：缓存代理、同步代理、防火墙代理和写入时复制代理。（L22466-22469）
- 代理在结构上类似装饰者，但是目的不同。（L22470-22471）
- 装饰者模式为对象加上行为，而代理则是控制访问。（L22472-22473）
- Java 内置的代理支持，可以根据需要建立动态代理，并将所有调用分配到所选的处理器。（L22474-22477）
- 就和其他的包装者一样，代理会造成你的设计中类的数目增加。（L22478-22480）

## 六、判断性论述

1. 代理与装饰者的分界是"意图"而非"结构"（炉边谈话 L21689-21756）：两者同样包装主题、实现同一接口，但装饰者为对象加上行为、代理控制访问；代理可以负责实例化/管理主题（远程代理要建立通信），装饰者从不实例化被包装对象（L21735-21739）；代理很少把主题包装超过一次，装饰者可层层叠加（L21741-21743）。判据：为对象"加职责"选装饰者，"管访问"（位置/时机/权限）选代理。
2. 远程代理的价值是把"位置"从客户代码中抹掉（L21099 远程执行、监视器不知道也不在乎；L21148 面向 GumballMachineRemote 接口）：网络与 RMI 细节全被代理吸收，监控代码与本地版几乎相同。边界：RMI 只是 Java 实现远程代理的一种手段，代理模式本身不绑定 RMI。
3. 虚拟代理以"延迟实例化"换可用性（L21232-21268）：创建开销大的对象先立占位符，真正需要时才加载真身；代价是客户必须容忍"暂时不完整"状态，代理内部须管理"加载中/已就绪"两态切换。
4. 两态以上的虚拟代理本质是状态机，可用状态模式重写（习题解答 L21499-21501 判定 ImageProxy 属状态模式场景）：代理与状态模式结构相近，书中以"代理控制访问、状态随内部状态改变行为"区分，但两者可叠加——模式协作而非互斥。
5. 保护代理的权限规则应集中一处、与真对象解耦（需求 L21888-21898；Owner L22049-22051、NonOwner L22094-22095 两个 handler 分治）：PersonBeanImpl 对权限一无所知，方法放行与否全在 invoke() 内裁决——权限是横切关注点，不应侵入领域对象。
6. 动态代理的适用判据是"一批方法需要统一拦截、按上下文分派"（InvocationHandler 职责 L21793-21794；同一 PersonBean 接口配两个 handler，L21994-21998；问答 L22236-22262 确认所有方法调用都转给处理器）：静态代理每场景手写一个类（GumballMonitor/ImageProxy），动态代理由 JVM 合成代理类、按需插拔 handler——Owner/NonOwner 共享代理类、仅 handler 不同即证。
7. 代理是有代价的包装者（要点 L22478-22480 主动承认"代理会造成你的设计中类的数目增加"）：每引入一层代理就多一层间接与一批类；访问控制需求不足以支撑时，不应为"看起来更解耦"而上代理。

# 第12章 复合模式（L22811-L26259）

## 一、问题场景（这个模式解决什么问题，书中原始案例）

两条叙事线：

1. 鸭子模拟器进化史（L22853-23988）：第 1 章的 SimUDuck 长成"真系统"——科学家要给鸭叫计数（QuackCounter）、管理员要让鹅（Goose）混入鸭群（GooseAdapter）、要确保鸭子创建即被计数（抽象工厂）、巡逻员要一声令下让整群鸭子听命（Flock）、呱呱叫学家要追踪个别鸭子（QuackObservable/Quackologist）。一堆模式协同工作，但书中明言这只是"模式的结合使用"，还不是复合模式（L22840-22843）。
2. DJ 打碟工具（L23989-24765）：BeatModel 持节拍数据与状态，多个视图（BPM 输入框、脉动柱、灯光）需要同步更新，用户控制（开始/停止/设 BPM）要与模型交互——引入 MVC。随后心脏监视（HeartModel，L24811-24891）与 Web/手机版（Model 2，L24960-25100）检验 MVC 的复用弹性。

## 二、模式解法（结构、参与者、关键机制）

### 复合模式（定义 L22845-22849）
模式通常被一起使用，并在同一个应用中结合；复合模式在一个解决方案中结合两个或多个模式，以解决一般或重复发生的问题。

关键判断（L22840-22843）：仅仅"把一堆模式凑在一起用"不算复合模式——复合模式必须够一般性、适合解决许多问题；鸭子模拟器只是模式协同，MVC 才是书中认定的复合模式。

### MVC = 观察者 + 策略 + 组合（三层解耦）
- 模型：持有所有的数据、状态与程序逻辑（L24061-24067），用观察者模式实现——状态改变时通知所有注册的观察者，模型对视图毫无所知（L24524：视图注册为观察者、用模型 API 访问状态）。
- 视图：模型的窗口（L24052-24055），用组合模式实现用户界面——UI 通常组合嵌套组件如面板、框架和按钮（L25542-25545）；DJView 同时是观察者与 Action 监听者（L24546-24559）。
- 控制器：取得输入并解读对模型的操作（L24056-24058），是视图的策略（L24662-24663 控制器插进视图让视图聪明）；"控制器是 MVC 夹心饼中间的奶油"（L24702-24704）——收视图的用户输入改模型状态，也要求视图改变（L24098-24108）。
- 适配器作外围（L24834-24839）：HeartModel 接口与视图期望不符（getHeartRate vs getBPM）时，用适配器把新模型适配成现有视图/控制器需要的模型（L24826-24855）——视图与控制器零改动复用。

### Model 2 = MVC 在 Web 上的适配（L24970-25002）
浏览器/服务器环境无法常驻视图，故以 Servlet 为控制器、JSP/HTML 为视图：HTTP 请求→Servlet 解析并请求模型→结果打包成 JavaBean→控制权交给 JSP 产生页面→HTTP 响应回浏览器（五步，L24989-25002）。价值不止设计分割，还有"制作责任分割"——该编程的人编程、该做网页的人做网页（L25010-25023）；BeatModel 因不依赖任何外部类而在 Web 版直接复用（L25063-25070）。

## 三、关键代码例（要点级转述）

1. QuackCounter 装饰叫声计数（L23073 附近）与 GooseAdapter 适配鹅叫（L22987 附近）；鹅叫不计入计数（L23141-23142）。
2. 抽象工厂收口创建（L23179-23235）：AbstractDuckFactory 定义四个 createXxxDuck；CountingDuckFactory 每个方法都先用 QuackCounter 包装再返回（L23216-23227）——"科学家可以因此而放心，所有的叫声都会被计算进去"（L23230-23234）。
3. Flock 组合（L23341-23358）：implements Quackable，ArrayList 存 Quackable；quack() 取迭代器遍历逐个调用——组合与叶共享接口（L23338-23340），quack() 内嵌迭代器模式（L23360-23369 自曝"我们其实还偷偷用了另一个设计模式"）；主群里可加子群（flockOfDucks.add(flockOfMallards)，L23388-23410）。
4. 观察者辅助类（L23490-23556）：Quackable extends QuackObservable（L23501-23503）；Observable implements QuackObservable 封装注册/通知，"只需要一份代码"、全部委托（L23513-23519）；notifyObservers 把 duck 传给 update()，观察者因此知道谁在叫（L23541-23545）。
5. BeatModel（L24383-24430）：实现 BeatModelInterface；registerBeatObserver/registerBPMObserver 分类注册；状态改变时通知观察者。
6. DJView（L24546-24567）：implements ActionListener, BeatObserver, BPMObserver；构造器收 ControllerInterface 与 BeatModelInterface 并注册为观察者——视图知模型与控制器，模型不知视图（L24524）。
7. BeatController（L24690-24722）：创建模型与视图，start()/stop()/setBPM() 转发模型；"视图只知道如何将菜单项变成开和关，但并不知道在何种情况下要 enable/disable"——决定权在控制器（L24747-24751）。
8. HeartAdapter（L24844-24855）：getBPM() 返回 heart.getHeartRate()，观察者方法直接转交 heart；HeartController 只替换模型适配（L24890-24891）。

## 四、OO 原则框（本章亮出的原则/要点，注明行号）

- 本章无新增 OO 原则；设计箱维持既有清单（L25515-25518：封装变化、多用组合少用继承、针对接口编程、松耦合、开放-关闭、依赖抽象、只和朋友交谈、别找我我会找你、类应该只有一个改变的理由）。
- 工具箱新增模式类目"复合模式"（L25523-25527），并明言"MVC 和 Model 2 属于复合模式"（L25528-25530）。
- 既有原则的大规模兑现：观察者（"别找我，我会找你"）撑起模型-视图解耦；策略（"封装变化"）撑起视图-控制器解耦；组合撑起视图内部组件结构。

## 五、章末要点（L25532-25558 原话级概括）

- MVC 是复合模式，结合了观察者模式、策略模式和组合模式。（L25532-25534）
- 模型使用观察者模式，以便观察者更新，同时保持两者之间解耦。（L25535-25537）
- 控制器是视图的策略，视图可以使用不同的控制器实现，得到不同的行为。（L25538-25541）
- 视图使用组合模式实现用户界面，用户界面通常组合了嵌套的组件，像面板、框架和按钮。（L25542-25545）
- 这些模式携手合作，把 MVC 模型的三层解耦，这样可以保持设计干净又有弹性。（L25546-25549）
- 适配器模式用来将新的模型适配成已有的视图和控制器。（L25550-25552）
- Model 2 是 MVC 在 Web 上的应用。（L25553-25554）
- 在 Model 2 中，控制器实现成 Servlet，而 JSP/HTML 实现视图。（L25555-25558）

## 六、判断性论述

1. "模式一起用"不等于复合模式（L22840-22843）：判据是"够一般性、适合解决许多问题"——鸭子模拟器把观察者/装饰者/抽象工厂/组合/适配器/迭代器凑在一起解决单一应用的问题，只是模式协同；MVC 因可推广到几乎一切交互应用才被认定为复合模式。误把"堆模式"当"复合模式"会造出过度设计。
2. 装饰若为系统性约束，创建必须收口到工厂（L23163-23174"必须包装才有效果，没包装就没有效果"）：QuackCounter 靠人肉记得包装迟早遗漏；抽象工厂把"创建+装饰"集中一处（CountingDuckFactory，L23216-23234），调用者拿到的必是被计数的鸭子。判据：装饰是可选增强→留给调用方；装饰是不可绕过的约束→工厂强制。边界：鹅经适配器的叫声不计入计数（L23141-23142）。
3. 组合模式的触发条件是"要像操作单个对象一样操作一群"（L23326-23336 巡逻员要管理鸭群、一声令下整群听命），且组合必须与叶实现同一接口（L23338-23340 Flock implements Quackable）。没有"群组化操作"需求时不必上组合。
4. 组合与迭代器天然配套而非互相替代（L23360-23369 书中自曝 Flock.quack() 里"偷偷用了迭代器模式"）：组合负责树形结构，迭代器负责统一遍历——群的 quack() 借迭代器走访子元素（含嵌套子群）。
5. 重复的观察者样板应收进辅助类（L23513-23519：注册/通知封装进 Observable、"只需要一份代码"、调用全委托）：若在每个 Quackable 实现里各写一份必然重复；与 Observable 组合（has-a）而非继承，是"多用组合"原则在观察者落地上的兑现。代价：update() 需携带主题引用（L23541-23545 把 duck 传给观察者），观察者才知道谁在叫。
6. 模型必须对视图与控制器一无所知（L24061-24067 模型没有注意到视图和控制器；L24524 BeatModel 对视图毫无所知；L25063-25070 Web 版直接复用）：模型只知道"有一些观察者要通知"。解耦的验收标准是"换掉整个交互环境（桌面→Web），模型代码一行不改"。
7. 控制器是视图的策略，也是"决定权"的归置（L24662-24663 控制器插进视图让视图聪明；L24747-24751 视图只知如何开关菜单项、不知何时开关——决定在控制器）：视图保持"哑"渲染才能配不同控制器复用（HeartController 即例，L24890-24891）；把交互决策写进视图会同时毁掉策略性与复用性。
8. 适配器是 MVC 的标准外围而非组成部件（L24834-24839"适配器其实是使用 MVC 时经常附带用到的技巧"）：新模型接口不符时适配成 BeatModelInterface（L24826-24855），复用全部视图与控制器；适配器属于复合模式的"允许扩展"，不属于 MVC 定义本身。
9. Model 2 的核心价值包含"制作责任分割"（L24971-24973；L25010-25023"该编程的人就编程，该做网页的人就做网页"）：MVC 到 Web 不只是技术适配（Servlet/JSP 五步流程），也是职责边界与分工的适配——架构模式的价值不止代码解耦，还有组织意义。
