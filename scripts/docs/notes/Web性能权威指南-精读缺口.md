### 2. 过程/领域类经验已有入口或不应落，不重复立编码条

- **延迟是瓶颈（而非带宽）**：本书最核心的观察（L4540–L4589「增加带宽没有那么重要」「减少往返次数」）是 T9「先度量」的具体推论——优化前先问「往返几次、延迟多少」而非「带宽多大」。T9 已要求「基线数字、目标、测量方法」，不另立「延迟优先于带宽」的绝对规则，因为那会与 T9「先选对数据结构与算法」的通用性打架，且「往返」在非网络域（如 DB/跨服务调用）已由 T10「串行调用链」信号覆盖。
- **队首阻塞（HOL）**：本书从 TCP 层讲到 HTTP 1.x 再到 HTTP 2.0/WebSocket/WebRTC 的「消息切分避免队首阻塞」（L1161–L1175、L4937、L5882）。工程面等价于「消除串行依赖/有序交付导致的排队」，已由 T10「跨服务调用链 A→B→C 且要求整体一致」与 T11「慢响应是最坏的故障模式」承载；协议层的多路复用/分帧是浏览器与服务器实现细节，不落。
- **移动端省电/爆发传输/预取**：L3757「轮询在移动网络中代价极高，少用」、L3761「推送比轮询效果更好」、第 8 章「批量请求、预先下载、让无线模块空闲」是移动域的性能权衡。原则层「减少唤醒/批量」可归 T9 优化目标；具体省电策略随平台/场景变化，不落成通用规则。

## 三、真缺口

### 1. 连接重用/持久连接不是「设上限」而是「默认复用」

**书中依据**：L830「提高 TCP 应用性能的关键，在于想办法重用连接」；L1262「重用 TCP 连接是提升性能的关键」；L1279「尽最大可能重用已经建立的 TCP 连接」；L4230「HTTP 1.1 …默认使用持久连接」；L1061「keep-alive、流水线和多路复用」。本书反复强调：每次新建连接都要付三次握手（1 RTT）+ 慢启动 + TLS 握手（2 RTT）的固定税，N 次请求复用连接能省 (N−1)×RTT。

**idev 现状**：T11 只写了「连接池上限」「连接池按下游独立」——这是资源隔离的**负面约束**（别让一个下游拖垮其它下游），没有写「外部调用**默认复用持久连接**」这个**正面默认**（摊销握手成本）。「连接池」一词隐含复用，但规约从未把「复用本身是默认、新建连接是例外」说清楚，执行者可能配了池上限却仍每次新建连接。

**落点**：`conventions/canon.md` T11 的 DO 增补一句（最小 diff，不动编号）：外部 HTTP/下游调用默认走持久连接与连接池复用，不逐请求新建连接；确需短连接（如一次性脚本、明确不重用的对端）写理由。同步 §2 信号可加「新增外部调用却逐请求新建连接（无 keep-alive/连接池）」命中 T11。

**效果**：把「连接复用」从 T11 隐含的资源隔离，补成显式的性能默认，与 T9「先度量」、T11「慢响应是最坏故障」共同兜住「新建连接税」这一最常见的隐性性能损失。

### 2. 实时/流式需求先选传输机制，再写实现

**书中依据**：L7336「WebSocket 并不能取代 HTTP、XHR 或 SSE，为了追求最佳性能，关键还是要利用这些机制的长处」；L6945–L7100（15.7 实时通知与交付：轮询 vs 长轮询 vs 流式的取舍）；L3757/L3761（移动端「轮询代价极高，推送比轮询好」）。本书给出明确决策框架：请求/响应用 XHR/fetch；单向服务器推送用 SSE；双向用 WebSocket；端到端音视频/数据用 WebRTC；只有都不行才退回轮询/长轮询。

**idev 现状**：T11 管「队列/事件/异步/重试/定时任务」的纪律，但没有「按实时/流式需求选传输机制」的规则。执行者遇到「要实时通知」时可能直接上轮询（移动端电池杀手）或滥用 WebSocket（自定义协议要自己管状态/压缩/缓存），没有一条规则让它停下来先对照「单向还是双向、要不要二进制、要不要 P2P」。

**落点**：`deliver/SKILL.md` arch 步骤（或 `conventions/canon.md` A2「依赖方向/统一语言」旁）增补一句：出现实时/流式/推送需求时，先声明传输机制选择（XHR/fetch vs SSE vs WebSocket vs WebRTC）及被拒方案，写明「单向还是双向、二进制还是文本、要不要 P2P、延迟与电量预算」；不默认轮询，不把 WebSocket 当 HTTP 的万能替代。此为 arch 阶段检查，不新增 T/C/P/R 编号。

**效果**：把本书的传输取舍框架前移到方案阶段，避免「实时需求」落到编码期才想起选错机制，与 A2/A3（依赖方向、被拒方案）同轮成稿。

## 四、重点候选裁定（防后人重复发现）

1. **「延迟优先于带宽」不另立绝对规则。** T9 已要求「基线数字、目标、测量方法」，优化前先度量自然会把往返次数/延迟暴露出来；另立「延迟优先」会与 T9 通用性打架，且非网络域的「往返」已由 T10「串行调用链」信号覆盖。
2. **队首阻塞不单独立条。** 工程面（消除串行依赖/有序交付的排队）已由 T10/T11 承载；协议层多路复用/分帧是浏览器与服务器实现，不落。
3. **移动省电/爆发传输/预取不落成通用规则。** 原则层归 T9 优化目标；具体策略（批量、预取、Wi-Fi 转移）随平台与场景变化，预设会鼓励过度预取与无使用方的下载。
4. **自适应比特流/媒体优化不预设。** 属媒体与移动网络专有，无真实需求不落。
5. **HTTP 1.x 权宜优化（域名分区/连接拼合/图标拼合/嵌入）不落。** 本书明言这些是「针对 HTTP 1.1 局限性的权宜之计」（L162），HTTP 2.0 已内置解决；把它们抄进规约会把过时优化当教条。
6. **协议机制细节（TCP 慢启动/拥塞窗口/TLS 会话恢复/HTTP 2.0 帧格式/WebRTC ICE）不落。** 属网络协议事实，与软件工程规约不同域，只作溯源。
