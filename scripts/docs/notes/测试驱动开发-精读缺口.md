## 二、对照结论

### 1. TDD 循环与测试纪律

| TDD 主题 | 书中要点 | idev 落点 | 结论 |
|---|---|---|---|
| 红绿重构、测试先行 | 先写会失败的自动测试，再写实现，再消除重复；一次只远离绿灯一步 | T6 护栏先行、小步可逆、两顶帽子；R1–R4（护栏、行为不变、不混帽、步步绿）；`coding-tables.md` §3.2 修 bug 先写能复现的失败测试 | 承载 |
| 严格 test-first 作为全过程仪式 | 测试在实现前定义行为，用来控制构思与反馈的差距 | idev 的可执行要求是「触及面可红可绿」而非全仓覆盖教条：T6 / R1 管护栏，R2 管行为改动换帽子先写 / 改测试，verify 管 PASS/FAIL/UNPROVEN 证据 | 不另立过程教条 |
| 测试列表、一步测试、启动测试 | 把待测行为列出来，选择有指导意义且能完成的下一步 | A5 最薄真实链路、A6 护栏与回退；T6 RECORD 记护栏与回退方式；列表属个人工作流 | 不落 |
| 断言优先 | 先写测试完成时应通过的断言，再反推 setup 与调用 | C26 一测一方向、命名 `Test_<函数>_<情形>`、Input/Expected/Actual；T6 断言取自契约或用户现象；F5 禁自证式测试 | 承载 |
| 显然数据 | 输入与期望的关系要在测试里读得出来，不为编排而编排 | C26 最小声明、最简输入覆盖同一分支；T5 命名表达意图 | 承载 |

## 三、真缺口

**无。** 本书没有产生需要新增编号或修改既有编号的产品级真缺口。

理由有四：

1. **操作核心已经落地。** 红绿重构、小步可逆、两顶帽子、触及面护栏由 T6 与 R1–R7 承载；自证式测试由 F5 拦截；断言来源与消息纪律由 T6 / C26 承载。
2. **测试套件质量已有更具体的表。** 单测写法归 C26，金字塔与速度归 C28，随机失败 / 注释测试 / 长期红灯归 C29，过度 mock 归 C30。TDD 书中的顺序独立性、setup 债、慢套件、脆弱测试都能落到这些现有条目。
3. **第三方学习测试已由《代码整洁之道》批次落进 F2。** 本书“只测试自己写的代码 / 不信任时写学习测试”没有超出该条。
4. **模式与手法目录已被 GoF、重构、修改代码的艺术三批精读收编。** 值对象归 T14 / C25，命令 / 模板 / 组合归 P8 / P12 / P13，解依赖与重构手法归 R 系；再抄 TDD 的模式目录会违反 `coding.md` 的不抄目录边界。

## 四、重点候选裁定（防后人重复发现）

1. **严格 test-first 不另立。** TDD 全过程仪式有价值，但产品真源的可执行判据是「触及面可红可绿」：T6 / R1 管护栏，R2 管行为改动先写 / 改测试，修 bug 路径已要求先写复现失败测试。把“所有产品代码必须先写测试”写成硬规约会把 UI 壳、协议形状、生成代码和纯文档型变更一并卷进来，超出当前工程收益。
2. **测试顺序独立性不新增编号。** 顺序依赖通常表现为随机失败或局部运行失败，C29 已要求随机失败当轮处理（修稳或移出并记录）；C19 管资源与状态复原，C26 管最小 setup。若把每个测试框架语义都拆成独立条目，会造成 C 表重复。
3. **期望异常测试模板不落。** “未抛出也 fail、只捕获期望类型”是正确写法，但属语言 / 框架模板；原则层已由 T6（断言来自契约或用户现象）与 F5（禁自证）承载。《重构》精读批次已对同一主题做过相同裁定。
4. **提交前全量测试与禁注释测试不另立。** `verify/SKILL.md` 的 plan / run 与 `workflows/test-pack.yaml` 管执行证据；C6 管注释掉的代码；C29 管被注释 / 跳过 / 长期红灯的测试。它属于流程出门，不是新的编码表号。
5. **学习测试不重复落。** F2 已明确“第三方 API 先写学习性测试钉住行为假设，升级依赖先跑它”，来源可追溯到《代码整洁之道》批次；本书只是再次确认。
6. **测试数量、删除、MTBF 阈值不落。** 这是风险与沟通价值的项目级判断。C26 / C28 / C29 已给出可执行方向；固定数字阈值会随领域风险（内部工具 vs 起搏器）失效。

## 五、不建议落的（防后人重复发现）

1. **TDD 模式名录与机械步骤**：测试列表、一步测试、伪实现、三角法、显明实现、自分流、日志字符串、清扫测试死角等属于工作法；原则层由 T6 / R4 / C26 / C30 承载。
2. **xUnit 框架实现细节**：TestCase 类结构、setUp / tearDown 方法名、AllTests 静态方法、Smalltalk / Java 语法细节，随语言与测试框架变化。
3. **书籍案例**：多币种资金、xUnit 自举、斐波纳契数列、三角形分类，不进产品真源。
4. **XP 组织实践**：结对编程、精神饱满地工作、ATDD 的责任转移、持续交付节奏，属团队流程与组织选择，不是当前编码规约。
5. **影响图形式**：系统思考工具可辅助 T12 / A 系列记录，但正负连接画法不是代码约束。
6. **作者对 TDD 有效性的开放讨论**：书中明说缺少对照研究；工程上仍以 verify 的可运行证据与 PASS/FAIL/UNPROVEN 为准，不把叙事当证明。
