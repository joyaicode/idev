# 《代码整洁之道》精读缺口清单

- **精读范围**：《代码整洁之道》（Robert C. Martin，404 页 OCR 本）目录与第 1 章通读；逐章精读第 2–6 章（命名、函数、注释、格式、对象与数据结构）、第 7 章错误处理（PDF 103–121）、第 8 章边界（PDF 122–130）、第 9 章单元测试、第 10 章类、第 11 章系统、第 12 章涌现设计、第 13 章并发（PDF 179–196）、第 17 章「味道与启发」（G19–G36 逐条核对，PDF 295–304，J/N 系列抽查）；第 14–16 章案例研究与附录 A–B 按增量重构叙事处理，归《修改代码的艺术》精读产物，未单独立条。

## 真缺口

1. **禁火车失事式链式取值——得墨忒耳律（G36 + 6.3）**
   - 书中出处：PDF 第 304 页，第 17 章 G36「避免传递浏览」；PDF 第 109–111 页，第 6 章 6.3「得墨忒耳律」、6.3.1「火车失事」。
   - 关键论据：G36：「如果 A 与 B 协作，B 与 C 协作，我们不想让使用 A 的模块了解 C 的信息（我们不想写类似 a.getB().getC().doSomething() 的代码）」；多处出现 a.getB().getC() 时，想在 B 与 C 之间插入 Q 极难，系统失去柔性；正确做法是「让直接协作者提供所需的全部服务」（myCollaborator.doSomething()）。6.3：方法只应调用自身、自己创建的对象、传给自己的参数、自己的组件（「只跟朋友谈话，不与陌生人谈话」）；ctxt.getOptions().getScratchDir().getAbsolutePath() 应改为 ctxt.createScratchFilestream(...)；纯数据结构豁免（数据与行为的反对称性），半对象半数据结构最糟。
   - 建议落点：coding-tables.md §2 新增 C 条：气味＝调用点出现 a.getB().getC().doSomething() 式跨对象链式取值（调用方被迫了解协作者的内部协作拓扑）；纠正＝让直接协作者提供服务方法，或明确按纯数据结构对待。编号与《程序设计方法》精读报告预留的 C20/C21 在集成阶段统一编排。
   - 与最相近现有条目的区别：T3 的 TRIGGER 已有「把内部结构当 API 暴露」，但那是提供方视角的设计原则；C12 管 util/helper 类无意义词改名，C15 管公开 API 形状与契约一致——真源缺调用侧可直接 grep 的形态信号（链式取值），也缺「直接协作者提供服务」的纠正处方。

2. **注释禁元数据——署名、修改历史、编号不进注释（4.4.11）**
   - 书中出处：PDF 第 81 页，第 4 章 4.4.11「归属与署名」。
   - 关键论据：「源代码控制系统非常善于记住是谁在何时添加了什么」——/* Added by Rick */ 式署名注释随代码演化只会越来越不准确，是噪音；同理修改历史、条目编号等元数据该由 git 承载，不占注释行。
   - 建议落点：coding-tables.md §2 C5 增补一句：注释不写署名、修改人、修改历史、条目编号等元数据（git 记得住），发现即删。
   - 与最相近现有条目的区别：底线 4 管「何时写」（只写代码看不出的那一句为什么），C5 现文管「注释与代码不一致则改删」——两者都不规定内容禁区：署名/历史类注释即使「与代码一致」也不该存在。增补后 C5 覆盖注释缺陷三态（不写废话、不写元数据、过期改删）。

3. **null 双向纪律——查询无结果按契约返回业务空集或抛错（不返回 null），可选缺参走工厂（不传 null）（7.7 + 7.8）**
   - 书中出处：PDF 第 119–120 页，第 7 章 7.7「别返回 null 值」；PDF 第 120–121 页，7.8「别传递 null 值」。
   - 关键论据：「返回 null 值，基本上是在给自己增加工作量，也是在给调用者添乱」——每个调用点被迫判空，漏判一处就把空指针推迟到远处爆；「将 null 值传递给其他方法就更糟糕了……恰当的做法就是禁止传入 null 值」——大多数语言无法在方法内保证调用者不传 null，与其在方法里 if (x == null) 防御，不如契约上不给 null 合法席位。
   - 建议落点：coding-tables.md §1 P15 增补两句：返回端——「查无结果」按契约返回业务空集（列表类返回约定空集合）或抛错，禁止返回 null 让每个调用方各自判空；传入端——方法契约不把 null 当合法值，可选缺参走 P2 的两个工厂。
   - 与最相近现有条目的区别：P2 只管 of(..., null) 一种特定坏味道（用 null 在两种创建语义间切换），P15 现文管「失败语境下缺值伪装成功」，T8/C7/C2 管失败处理方向——真源均未规定「正常路径查无结果返回什么」与「传入端一般禁令」。措辞须注明：业务性无数据的空集合是契约的一部分，与 P15 禁的「失败伪装成功」不冲突；书的「特例对象」处方（7.6，PDF 第 118 页）与 P15 冲突，不采纳。

4. **时序耦合显式化——多步必须按次序调用时，用参数链把次序依赖变成数据流（G31）**
   - 书中出处：PDF 第 300–301 页，第 17 章 G31「掩蔽时序耦合」。
   - 关键论据：MoogDiver.dive() 依次调 saturateGradient()/reticulateSplines()/diveForMoog(reason)，次序重要但代码未强制，「其他程序员可以在调用 saturateGradient 之前调用 reticulateSplines，从而导致抛出 UnsaturatedGradientException」；改法是把每步产出作为下一步参数（Gradient gradient = saturateGradient(); reticulateSplines(gradient); diveForMoog(splines, reason)），「每个函数都产生出下一个函数所需的结果，这样一来就没理由不按顺序调用了」；书承认这增加了复杂度，「不过这点额外的复杂度却暴露了该种情况真正的时序复杂性」。
   - 建议落点：coding-tables.md §2 新增 C 条：气味＝同一流程上连续调用多个方法且后步依赖前步隐式状态，次序错了才在运行时爆；纠正＝每步产出显式作为下一步入参。
   - 与最相近现有条目的区别：C1 管变更理由数量的职责拆分，不问次序依赖的表达；T3 DESCEND 管「调用方不必知道内部步骤顺序」的模块接口设计，本条管流程内隐式次序的物化手法；§2.4 圈复杂度筛不出「错误次序才炸」的问题。

5. **函数语句同一抽象层级——概念层与实现语法层不混排（G34）**
   - 书中出处：PDF 第 302–303 页，第 17 章 G34「函数应该只在一个抽象层级上」。
   - 关键论据：「函数中的语句应该在同一抽象层级上，该层级应该是函数名所示操作的下一层」；render() 例同时混「横线有尺寸」的概念层与 hr 标记的 HTML 语法层，「拆分不同抽象层级是重构的最重要功能之一，也是最难做的一个」；且拆分会挖出被原结构掩蔽的新界线——首轮拆分后尺寸翻译与标记构建仍混层，最终拆出 HtmlTag 管语法，顺带发现 XHTML 结束斜线漏写的 bug。
   - 建议落点：coding-tables.md §2 新增 C 条：气味＝函数内同时出现业务概念语句（决定尺寸、取值、组织）与底层语法/协议语句（拼标记、属性字符串、字节序列）；纠正＝按层级拆函数，概念层只调实现层模块。与缺口 1、4 的新增 C 条同批统一编号。
   - 与最相近现有条目的区别：C1 管变更理由数量，§2.4 行数/圈复杂度是量化粗筛，底线 4「顺着读能看见重点」是精神——真源没有「语句层级一致性」这个可操作判定。与缺口 4 是姊妹条（一个管次序显式化、一个管层级一致性），纠正手法不同（参数化 vs 拆层）。

6. **隐式假设物化——逻辑依赖改物理依赖，权责值归权责方（G22）**
   - 书中出处：PDF 第 296 页，第 17 章 G22「把逻辑依赖改为物理依赖」。
   - 关键论据：「如果某个模块依赖于另一个模块，依赖就该是物理上的而不是逻辑上的。依赖者模块不应对被依赖者模块有假定……它应当明确地询问后者全部信息」；HourlyReporter 私有声明 PAGE_SIZE = 55 传给 HourlyReportFormatter——「HourlyReporter 为什么要知道页面尺寸？页面尺寸只该是 HourlyReportFormatter 的权责」，这是位置错误的权责；改法由 Formatter 提供 getMaxPageSize()，让被依赖方「明确被询问」。
   - 建议落点：canon.md §3 T4 增补一句 DO：依赖不止是 import——被调用方不假设调用方持有的常量/配置/上限（grep import 抓不到的语义依赖），所需值由权责方持有或提供方法供调用方显式获取。
   - 与最相近现有条目的区别：T4 现文管依赖方向与边界（业务不 import 框架、走 ports），管「谁允许依赖谁」；本条管依赖已存在但未走显式契约——值写在调用方等于对被调用方行为做隐式假定。T4 触发条件不含此形态。

7. **条件与中间值意图名——复杂布尔提炼肯定式谓词、边界值先命名、函数名从调用点可判行为（G28 + G29 + G19 + G33 + G20）**
   - 书中出处：PDF 第 299 页，第 17 章 G28「封装条件」、G29「避免否定性条件」；PDF 第 295 页，G19「使用解释性变量」、G20「函数名称应该表达其行为」；PDF 第 301–302 页，G33「封装边界条件」。
   - 关键论据：G28：「如果没有 if 或 while 语句的上下文，布尔逻辑就难以理解。应该把解释了条件意图的函数抽离出来」——if (shouldBeDeleted(timer)) 好于 if (timer.hasExpired() && !timer.isRecurrent())；G29 否定式比肯定式难懂；G19：「让程序可读的最有力方法之一，就是将计算过程打散成在有意义的单词命名的变量中放置的中间值……这事很难做过头。解释性变量多比少好」；G33：「把处理边界条件的代码集中到一处……我们不想见到四处散见的 +1 和 -1 字面量」（level+1 出现两次 → int nextLevel = level + 1）；G20：Calendar.add(5) 从调用点看不出加的是天还是周、改不改原值——「如果你必须查看函数的实现才知道它是做什么的，就该换个更好的函数名」。
   - 建议落点：canon.md §3 T5 增补一句：命名不止概念名——布尔条件不自解释时提炼为肯定式谓词函数；同一边界值/中间计算使用前先命名；函数名须从调用点可判断行为（含变换方向与是否改原值）。
   - 与最相近现有条目的区别：T5 现文管「同一概念跨面同一字符串」的词表一致性，不管表达手法；C4 管入参出参同名不同义，C10 管魔法字符串第 2 次重复，圈复杂度管分支数量——都触发不了「这个 if 读不出意图」。底线 4 允许用注释补那一句为什么；本条是更优解——先把意图放进名字，少写一条注释。

8. **学习性测试钉第三方行为——用测试钉住对第三方 API 的假设，升级依赖先跑它（8.4）**
   - 书中出处：PDF 第 126 页，第 8 章 8.4「学习性测试让边界更整洁」。
   - 关键论据：为第三方程序包写测试「与其说是测试，不如说是学习」，把「我们希望第三方 API 该怎么工作」的知识固化成测试；「当第三方程序包发布了新版本，我们可以运行学习性测试，看看程序包的行为有没有改变」——差异在我方暴露而非客户处；「无论测试通过还是失败，边界都是整洁的」。
   - 建议落点：canon.md §5 F2 增补纠正手法：使用第三方 SDK/API 前，先写学习性测试钉住关键行为假设（调用方式、抛错时机、边界值语义）；升级依赖版本时先跑学习性测试再合入。
   - 与最相近现有条目的区别：F2 现文管「幻觉依赖」的定义，纠正停在「先读源码或契约」；P3 管 Adapter 结构手段；T6 管断言来源；R1 面测试以重构为语境——真源没有「把第三方行为假设变成可回归资产」的手法，也没有「升级依赖先跑钉子」的时序要求。

9. **并发代码的组织纪律——并发代码与业务代码分离、共享数据与锁绑定封装、临界区最小、先让单线程版可工作（13.3.1 + 13.3.2 + 13.7 + 13.9.2）**
   - 书中出处：PDF 第 182 页，第 13 章 13.3.1「分离并发相关代码与其他代码」；PDF 第 182–183 页，13.3.2「严格限制共享数据访问」；PDF 第 186 页，13.7「尽可能减小同步区域」；PDF 第 187 页，13.9.2「先使非线程代码可工作」。
   - 关键论据：13.3.1 并发相关代码「有属于自己的生命周期、自己的开发、修改与调整轨迹」，线程控制混进业务对象两败俱伤（书例把 ThreadProxy 与业务逻辑分离）；13.3.2 严格限制共享数据访问——数据封装于线程公域之外，拿不到锁就拿不到数据；13.7 临界区越大越易死锁，守护范围越小越好，同步块外的代码挪出去；13.9.2「确保代码在并发版可工作前，先在单线程版可工作」——并发是另一维度的复杂度，用测试同时证明两种版本。
   - 建议落点：canon.md §3 T10 增补一条 DO：已决定引入并发后——并发控制代码与业务逻辑分离放置；共享可变数据与锁绑定封装；临界区最小化；先让单线程版本测试通过再引入线程，两种版本同测。
   - 与最相近现有条目的区别：T10 现文是数据系统五项权衡，T11 管可运维性，canon.md §2 只把「新增并发/锁/共享可变状态」当排查信号、§4 念头表管「要不要并发」——真源在决策层完备，缺「已决定并发后代码怎么组织」的写法纪律。《程序设计方法》精读缺口 5（计算与效果分离）管纯度纠缠，不覆盖并发分离。
