## 第14章 中介者模式（Mediator）｜L7246-7896

**① 模式意图**：用一个中介对象封装一系列对象的交互，使各对象不需显式相互引用，从而松散耦合、且可独立地改变它们之间的交互（定义 L7694-7700）。

**② 使用场景与触发条件**
- 何时用（L7890-7896）：①N 个对象之间产生了相互依赖关系（N>2）；②依赖行为尚不确定或有改变可能（降低变更风险扩散）；③产品开发——以稳定、高效、扩展为宗旨（如 MVC 框架），项目开发以交付投产为目标则未必。
- 判别标准（L7837-7840）：紧耦合的标准是"在类图中出现了蜘蛛网状结构"，此时一定要考虑用中介者把蜘蛛网梳理为星型结构。
- 何时不用（L7830-7837）：并非有多个依赖就该用——"中介者模式未必能帮你把原本凌乱的逻辑整理得清清楚楚"；原本简单的几个对象依赖，为用模式而加中介者，"必然导致中介者的逻辑复杂化"，使用需"量力而行"。

**③ 不用时的做法、反例、缺点/代价**
- 不用时：对象间直接相互调用。进销存示例中 Purchase 内部直接 new Stock/Sale 并调用（L7309-7318）；Stock.clearStock 直接 new Purchase/Sale 并指挥折价销售、停止采购（L7357-7366）。
- 反例问题（L7443-7447）：三个类彼此关联，每个类都与其他两个类产生依赖。迪米特法则认为"每个类只和朋友类交流"，朋友类越多耦合越大，"要想修改一个就得修改一片"。扩展到六模块时成蛛网结构，"就是给人看估计也能让一大批人昏倒"（L7455）。
- 用了之后的代价（L7821-7823）：中介者会膨胀得很大、逻辑复杂；同事类越多中介者逻辑越复杂——依赖没有消失，只是集中转移到中介者身上。

**④ 论据**
- 改造思路（L7459-7463）：借星型网络拓扑——各计算机通过交换机交互、彼此不直接通信，结构简单且稳定。
- 改造后结构（L7483-7485, L7687-7692）：加入中介者作为交流核心；每个模块只负责自己的业务逻辑，不属于自己的丢给中介者处理；同事类只与中介者产生依赖，"类间的耦合性大大减少"。
- 角色与行为二分（L7713-7717）：同事类行为分两种——自发行为（Self-Method，如改变对象本身状态、处理自己的行为，不依赖任何同事/中介者）与依赖方法（Dep-Method，必须依赖中介者才能完成）。
- 注入方式不对称的原因（L7814-7815）：同事类用构造函数注入中介者（同事类必须有中介者），中介者用 getter/setter 注入同事类（中介者可以只有部分同事类）。
- 中介者实现手法（L7581-7583）：把原有一个对象依赖多个对象的情况移到中介者的 private 方法中实现；实际项目一般按职责划分中介者，每个中介者处理一个或多个类似关联请求。
- 优点论据（L7818-7820）："把原有的一对多的依赖变成了一对一的依赖"，减少依赖、降低耦合。

**⑤ 最佳实践/作者忠告**
- 同事类之间不能提炼共性就不要刻意追求抽象，"抽象只要定义出模式需要的角色即可"（L7874-7882）；"从这点也可以看出继承是高侵入性的"（L7877）——这是本章少用接口/抽象类、与依赖倒置原则冲突的原因。
- 中介者抽象类一般只有一个实现者，"对于中介者来说，抽象已经没有太多的必要"（L7883-7886）。
- "一个对象依赖几个对象是再正常不过的事情，但是纯理论家就会要求使用中介者模式来封装这种依赖关系，这是非常危险的！"（L7887-7889）
- 实际应用类比（L7845-7872）：机场调度中心；MVC 框架的 Controller（前端控制器，隔离 M 与 V 并协调二者）；媒体网关（MSN 服务器中转 vs 飞鸽 IPMsg 无中介者的 UDP 广播——每个客户端既是客户端也是服务器端）；租房/出国等中介服务。

**补充**
- 模式间关系：作者以 MVC 框架作为中介者模式在产品中的落地例证；中介者把多对多交互收敛为一对一，与"星型拓扑"结构同构。
- 代码示例一句话概括：进销存三模块（Purchase/Sale/Stock）从相互 new 与互调，改造为继承 AbstractColleague（构造持 mediator 引用），跨模块事件一律走 super.mediator.execute("purchase.buy", number) 由 Mediator 按字符串分派统一调度（L7534-7547）。

## 第15章 命令模式（Command）｜L7899-8575

**① 模式意图**：将一个请求封装成一个对象，从而用不同的请求把客户端参数化，支持对请求排队或记录日志，并提供命令的撤销和恢复功能（定义 L8278-8281）。

**② 使用场景与触发条件**
- 何时用（L8415-8418）："只要你认为是命令的地方就可以采用命令模式"——GUI 开发中按钮的点击、模拟 DOS 命令、触发一反馈机制的处理等。
- 典型触发：请求方（客户/高层）只应下命令，不应知道谁来干、怎么干（旅行社项目里客户只与"接头人"小三打交道）。
- 何时不用/慎用（L8411-8414）：命令数量大时 Command 子类膨胀严重，"这个就需要读者在项目中慎重考虑使用"。

**③ 不用时的做法、反例、缺点/代价**
- 反例一：客户直接与各执行组交互——增加需求时客户要先找需求组、再找美工组、再找代码组，"你想让客户跳楼啊！"（L8421-8426）。
- 反例二（15.1 节演进中间态，L7899-8245）：让接头人 Invoker 接收字符串命令——字符串无类型约束力，不是好方案。
- 用了之后的代价（L8411-8414）：N 个命令就是 N 个 Command 子类，类膨胀非常大。

**④ 论据**
- 封装性论据（L8275-8276, L8303-8304）：客户只改一行 new 哪个命令即可，"客户也不用知道到底由谁来修改，高内聚的要求体现出来了"；命令模式"把请求方（Invoker）和执行方（Receiver）分开了"，扩展性有很好的保障。
- 三角色（L8293-8299）：Receiver 接收者=干活的角色（Group 的三个实现类）；Command 命令=需要执行的所有命令都在这里声明；Invoker 调用者=接收命令并执行（例中即项目经理/接头人，"就像是一个受气包"L8378）。
- 优点（L8402-8410）：类间解耦（调用者只调 Command 抽象类的 execute，不需了解哪个接收者执行）；可扩展性（Command 子类易扩展，与 Invoker/Client 不产生严重耦合）；"命令模式结合其他模式会更优秀"——结合责任链实现命令族解析，结合模板方法减少 Command 子类膨胀。
- 扩展一·命令组合（L8428-8449）：增加一项需求需同时加页面加功能时，只需在 AddRequirementCommand.execute 中追加 super.pg.add()/super.cg.add()——命令内部协调一个或多个接收者，"客户Client只需要发布命令……命令模式做了一层非常好的封装"。
- 扩展二·反悔问题（L8450-8495）：两种方法——①结合备忘录模式还原最后状态，适合接收者为状态变更的情况，不适合事件处理；②增加一个新的反命令（Command 子类）实现事件回滚，接收者（Group）增加 rollBack() 方法按事务日志回滚；"真正实现起来那是异常复杂的……想想数据库的日志处理吧"（L8493-8495）。

**⑤ 最佳实践/作者忠告**
- "约定的优先级最高"（L8503）：Receiver 在实际项目中一般都会被封装掉，通过有意义的类名或命令名处理命令角色与接收者角色的耦合关系（这就是约定），减少 Client 对低层模块的依赖，提高系统整体稳定性（L8502-8506）。
- 推荐形态"完美的 Command 类"（L8513-8524）：父类声明 protected final Receiver，构造函数约定每个具体命令必须指定（默认）接收者；具体命令再提供可覆盖的注入构造。"每个命令完成单一的职责，而不是根据接收者的不同完成不同的职责"（L8560）；"高层次的模块不需要知道接收者"（L8574）。

**补充**
- 模式间关系：命令模式与责任链结合→命令族解析；与模板方法结合→减少 Command 子类膨胀；与备忘录结合→状态还原式撤销（vs 反命令的事件回滚式撤销）。
- 代码示例一句话概括：旅行社项目中 Group 抽象类（find/add/delete/change/plan）派生需求组/美工组/代码组；Command 抽象类持有三个组引用、仅一个 execute() 抽象方法；客户只对 Invoker（接头人）setCommand 后 action()。

## 第16章 责任链模式（Chain of Responsibility）｜L8577-9174

**① 模式意图**：使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系——将这些对象连成一条链，沿链传递该请求，直到有对象处理它为止（定义 L8988-8996）。

**② 使用场景与触发条件**
- 何时用：请求类型与处理者的对应关系不固定、处理者可能扩展；请求发出后"必然有一个唯一的处理人给出唯一的答复"的流转场景（L8760-8762）。
- 补救模式用法（L9146-9151）：项目初期"一个请求一个处理者"（银行存款只处理人民币），业务发展（美元、日元……）后在第一个处理者后面建链，"这些都不用在对原有的业务逻辑产生很大改变，通过扩展实现类就可以很好地解决这些需求变更的问题"。
- 何时不用/慎用：链较长时性能与调试代价大；链中节点数量需控制（L9131-9134）。

**③ 不用时的做法、反例、缺点/代价**
- 不用时做法：Client 中按 women.getType() 写 if-else 匹配 Father/Husband/Son（L8704-8722）。
- 反例四大问题（L8741-8758）：①职责界定不清晰——女儿的请示本应由 Father 类决定，却在 Client 中组装出来；②代码臃肿——if-else 判断随可处理类型增多而膨胀，无可读性；③耦合过重——根据 type 决定用哪个 IHandler 实现，"如果IHandler的实现类继续扩展怎么办？修改Client类？与开闭原则违背了"（L8755）；④异常情况欠考虑——妻子向父亲请示等越界场景程序未体现，"逻辑失败了"。
- 用了之后的代价（L9127-9130）：①性能问题——每个请求从链头遍历到链尾，链长时是很大的问题；②调试不方便——采用类似递归的方式，链条长、环节多时调试逻辑复杂。

**④ 论据**
- 结构核心（L8774-8775）：每个节点有两个选择——"要么承担责任，做出回应；要么把请求转发到后续环节"。
- Handler 抽象类三职责（L9031-9033）：①定义请求处理方法 handleMessage（唯一对外开放）；②定义链的编排方法 setNext；③定义子类必须实现的两个方法——处理级别 getHandlerLevel 与具体处理任务 echo。
- 模板方法融合（L8836-8838）：handleMessage（final）中判断请求级别与自身处理级别，相同则调用基本方法 response 做出反馈，不等则传递到下一环节，到链尾则直接按不同意处理——"其实在这里也用到模板方法模式"。
- 无处理者兜底（L8822-8824, L8889-8890）：没有后续处理人时打印"没地方请示了，按不同意处理"；请求类型 4 即如此。
- 优点论据（L9119-9122）：将请求和处理分开——请求者不用知道是谁处理的，处理者可以不用知道请求的全貌（J2EE 中可剥离出无状态 Bean 由责任链处理），两者解耦，提高系统灵活性。
- 解耦效果（L8977-8979）：业务调用类 Client 不用判断需要谁处理；Handler 子类可继续增加，"只需要扩展传递链而已，调用类可以不用了解变化过程，甚至是谁在处理这个请求都不用知道"。
- 实战案例（L9152-9173）：用户注册——VIP 用户（邮件自动激活）与普通用户（短信激活）流程不同；Struts2 的 RegisterAction 组装 HashMap（UserInfoMap）传入统一处理入口，由 CommonRegister/VIPRegister 按用户标识决定谁来处理。

**⑤ 最佳实践/作者忠告**
- 建议用"抽象 Handler + 模板方法"形态（L9135-9142）：父类实现请求传递，子类实现请求处理（只实现 echo 与 getHandlerLevel），"符合单一职责原则……只有一个原因引起类的改变"，同时呼应迪米特法则；好处是子类实现非常简单、链的建立非常灵活。
- 链长度控制（L9131-9134）：一般做法是在 Handler 中设置最大节点数量，setNext 时判断是否超过阈值，超过则不允许建链，"避免无意识地破坏系统性能"。
- 封装类建议（L9114-9116）：实际应用中一般用一个封装类对责任链进行封装、替代 Client，直接返回链中第一个处理者，链的具体设置不需要高层模块关心，更简化调用、减少模块间耦合。
- 不必纠结纯/不纯责任链（L9038-9040）：一个请求发送到链中后，前一节点可消费部分消息再交由后续节点继续处理，"最终可以有处理结果也可以没有处理结果，读者可以不用理会什么纯的、不纯的责任链模式"。

**补充**
- 模式间关系：Handler 的 final handleMessage 是模板方法模式的应用（呼应第10章）；第15章明言命令模式可结合责任链实现命令族解析。
- 代码示例一句话概括："三从四德"——Women（type：1未嫁/2出嫁/3夫死）的请示从 Father 起，Handler 持 level 与 nextHandler，级别匹配则 response() 回应，否则经 setNext 串起的链传递给 Husband、Son。

## 第17章 装饰模式（Decorator）｜L9176-9638

**① 模式意图**：动态地给一个对象添加一些额外的职责；就增加功能来说，装饰模式相比生成子类更为灵活（定义 L9481-9488）。

**② 使用场景与触发条件**
- 何时用（L9612-9615）：①需要扩展一个类的功能，或给一个类增加附加功能；②需要动态地给一个对象增加功能，这些功能可以再动态地撤销；③需要为一批的兄弟类进行改装或加装功能（首选）。
- 触发信号（L9363-9366）：装饰条件的组合多变——老爸可能听完最高分就签名、也可能要先看排名，"继续扩展？你能扩展多少个类？……一旦需要装饰的条件非常多，比如20个，你还通过继承来解决，你想象的子类有多少个？你是不是马上就要崩溃了！"
- 何时不用/慎用（L9609-9611）：多层装饰复杂，"尽量减少装饰类的数量，以便降低系统的复杂度"。

**③ 不用时的做法、反例、缺点/代价**
- 不用时做法：继承——SugarFouthGradeSchoolReport extends FouthGradeSchoolReport，重写 report() 前后插入 reportHighScore()/reportSort() 两个私有修饰方法（L9316-9334），"这确实是一个比较好的办法"但走不远。
- 反例缺点（L9363-9370）：①类爆炸、类数量激增，本质相似的代码一大摊，"谁愿意接收这么一大摊本质相似的代码维护工作？"；②"在面向对象的设计中，如果超过两层继承，你就应该想想是不是出设计问题了……这是经验值，不是什么绝对的，继承层次越多以后的维护成本越多"。
- 用了之后的代价（L9608-9611）："多层的装饰是比较复杂的……就像剥洋葱一样，你剥到了最后才发现是最里层的装饰出现了问题"。

**④ 论据**
- 结构论据（L9389-9391, L9415-9416）：Decorator 抽象类的作用是封装 SchoolReport，"装饰类还是把动作的执行委托给需要装饰的对象"；"如果大家还记得代理模式，那么很容易看懂这个类图，装饰类的作用也就是一个特殊的代理类，真实的执行者还是被代理的角色"。
- 四角色（L9492-9512）：Component 抽象构件（"必然有一个最基本、最核心、最原始的接口或抽象类充当" L9502-9503）；ConcreteComponent 具体构件（被装饰的对象）；Decorator 装饰角色（一般是抽象类，"在它的属性里必然有一个private变量指向Component抽象构件" L9507-9508）；ConcreteDecorator 具体装饰角色。
- 静态 vs 动态（L9624-9626）：继承是静态地给类增加功能，装饰模式是动态地增加——不想要 SortDecorator 这层封装，"直接在Father中去掉就可以了，如果你用继承就必须修改程序"。
- 优点（L9600-9606）：①装饰类和被装饰类可以独立发展而不会相互耦合，Component 无须知道 Decorator；②是继承关系的一个替代方案——"不管装饰多少层，返回的对象还是Component，实现的还是is-a的关系"；③可动态扩展实现类功能。
- Son 增强案例（L9630-9635）：Father→Son→GrandSon 继承链上要增强 Son，"你增强的功能是修改Son类中的方法吗？……对GrandSon的影响呢？特别是GrandSon有多个的情况……这是不允许的"；建立 SonDecorator 修饰 Son，"对原有程序没有变更，通过扩展很好地完成了这次变更"。

**⑤ 最佳实践/作者忠告**
- 装饰模式是对继承的有力补充，可替代继承解决类膨胀问题（L9616-9624）。
- 若只有一个装饰类，可以没有抽象装饰角色，直接实现具体装饰角色即可（L9547）。
- "原始方法和装饰方法的执行顺序在具体的装饰类是固定的，可以通过方法重载实现多种执行顺序。"（L9580-9581）

**补充**
- 模式间关系：作者明言装饰类"也就是一个特殊的代理类"——结构同代理、意图在附加职责；同时是继承的替代方案（保留 is-a 但运行时组装）。
- 代码示例一句话概括：成绩单场景——Decorator 抽象类持 private SchoolReport 委托执行；HighScoreDecorator 在 super.report() 前汇报最高分、SortDecorator 在其后汇报排名，Father 中 new SortDecorator(new HighScoreDecorator(sr)) 层层包裹后调用，增加修饰条件只需新实现一个 Decorator 子类。

## 第18章 策略模式（Strategy）｜L9639-10127

**① 模式意图**：定义一组算法，将每个算法都封装起来，并且使它们之间可以互换（定义 L9786-9790；也叫政策模式 Policy Pattern）。

**② 使用场景与触发条件**
- 何时用（L9900-9908）：①多个类只有在算法或行为上稍有不同的场景；②算法需要自由切换的场景（算法由使用者决定，或算法始终在进化——技术前沿行业"连业务专家都无法给你保证这样的系统规则能够存在多长时间"）；③需要屏蔽算法规则的场景。
- 数量阈值（L9909-9911）："如果系统中的一个策略家族的具体策略数量超过4个，则需要考虑使用混合模式，解决策略类膨胀和对外暴露的问题，否则日后的系统维护就会成为一个烫手山芋。"

**③ 不用时的做法、反例、缺点/代价**
- 不用时做法：多重条件语句（if-else 或三目运算符）分支选择算法——扩展章节方案一/二（L9919-9977）。
- 反例缺点（L9880-9884）："多重条件语句不易维护，而且出错的概率大大增强"；用策略模式后由其他模块决定采用何种策略，对外接口就是封装类。
- 用了之后的代价（L9889-9899）：①策略类数量增多——"每一个策略都是一个类，复用的可能性很小"；②所有策略类都需要对外暴露——上层模块必须知道有哪些策略才能选用，"这与迪米特法则是相违背的"，"我只是想使用了一个策略，我凭什么就要了解这个策略呢？那要你的封装类还有什么意义？"

**④ 论据**
- 三角色（L9806-9817）：Context 封装角色（上下文，"起承上启下封装作用，屏蔽高层模块对策略、算法的直接访问，封装可能存在的变化"）；Strategy 抽象策略角色（算法家族的抽象，定义每个策略必须具有的方法和属性）；ConcreteStrategy 具体策略角色（含具体算法）。
- 实现本质（L9803, L9871-9874）："使用的就是面向对象的继承和多态机制，非常容易理解和掌握……其他没什么玄机"；但真实业务"一个类实现多个接口很正常，你要有火眼金睛看清楚哪个接口是抽象策略接口……这就是你作为系统分析师的价值所在"。
- 与代理模式之别（L9838-9840）：策略模式的重点就是封装角色，"它是借用了代理模式的思路……差别就是策略模式的封装角色和被封装的策略类不用是同一个接口，如果是同一个接口那就成为了代理模式"。
- 优点（L9876-9888）：算法可自由切换；避免多重条件判断；扩展性良好——"在现有的系统中增加一个策略太容易了，只要实现接口就可以了……类似于一个可反复拆卸的插件，这大大地符合了OCP原则"。
- 扩展·策略枚举（L10054-10112）：把原有定义在抽象策略中的方法移植到枚举中，每个枚举成员就成为一个具体策略（L10088-10089）；"它是一个枚举；它是一个浓缩了的策略模式的枚举"（L10090-10091）；调用 Calculator.ADD.exec(a,b) "真实地面向对象……拿出计算器，对a和b进行加法运算，并立刻执行"（L10108-10112）。

**⑤ 最佳实践/作者忠告**
- 策略模式单独使用的地方比较少，"因它有致命缺陷：所有的策略都需要暴露出去"（L10120-10121）；"在实际项目中，我们一般通过工厂方法模式来实现策略类的声明"（L10125-10126）。
- 策略枚举"是一个非常优秀和方便的模式"，但受枚举类型限制——每个枚举项都是 public、final、static 的，扩展性受约束，"策略枚举一般担当不经常发生变化的角色"（L10116-10118）。
- "代码是让人读的，然后才是让机器执行，别把顺序搞反了！"（L10094）
- 锦囊比喻（L10121-10125）：赵云不知道锦囊里是 BackDoor 还是别的计，诸葛亮已规定"适当的场景拆开适当的锦囊"——策略模式只实现了锦囊的管理，未严格定义场景与锦囊的匹配，这正是要用工厂方法补足之处。

**补充**
- 模式间关系：封装角色借代理模式思路（不同接口即策略、同接口即代理，L9838-9840）；策略暴露缺陷可用工厂方法、代理或享元修正（L9898-9899）；超过 4 个策略建议与工厂方法混编。
- 代码示例一句话概括：刘备招亲——BackDoor/GivenGreenLight/BlockEnemy 三个妙计实现 IStrategy.operate()，Context（锦囊）构造注入策略并代为 operate()，赵云按时机 new Context(new XxxStrategy()) 依次拆囊执行；扩展示例为加减法运算四方案演进（if-else→三目→策略类→策略枚举）。

## 第19章 适配器模式（Adapter）｜L10128-10795

**① 模式意图**：将一个类的接口变换成客户端所期待的另一种接口，从而使原本因接口不匹配而无法在一起工作的两个类能够在一起工作（定义 L10447-10451；又叫变压器模式、包装模式 Wrapper）。

**② 使用场景与触发条件**
- 何时用（L10557-10560）："适配器应用的场景只要记住一点就足够了：你有动机修改一个已经投产中的接口时，适配器模式可能是最适合你的模式"——如系统扩展需要用一个已有或新建的类，但该类不符合系统接口。
- 何时不用（L10562-10566）：详细设计阶段不要考虑它，"它不是为了解决还处在开发阶段的问题，而是解决正在服役的项目问题"；"没有一个系统分析师会在做详细设计的时候考虑使用适配器模式"。

**③ 不用时的做法、反例、缺点/代价**
- 不用时做法：为了对接外系统对已运行良好的系统"动大手术"，大规模修改既有代码（L10314-10315 "我们不可能为了这一小小的功能而对我们已经运行良好系统进行大手术"）。
- 代价对比：用适配器后"只修改了一句话，其他的业务逻辑都不用修改就解决了系统对接的问题……尽量少的修改，通过扩展的方式解决了该问题"（L10442-10444）。
- 用了之后的代价/依赖条件：适配器能成立的前提是原系统"严格遵守了依赖倒置原则和里氏替换原则，否则即使增加了中转类也无法解决问题"（L10345-10346，原文"注意"框）；类适配器受 Java 单继承限制，只能通过覆写源角色方法扩展（L10573-10574, L10780-10781）。

**④ 论据**
- 三角色（L10489-10497）：Target 目标角色（期望接口，"通常情况下是一个接口或者是抽象类，一般不会是实现类" L10503-10504）；Adaptee 源角色（"已经存在的、运行良好的类或对象"）；Adapter 适配器角色（核心、需新建，"把源角色转换为目标角色……通过继承或是类关联的方式"）。
- 优点（L10543-10556）：①让两个没有任何关系的类在一起运行；②增加类的透明性（"我们访问的Target目标角色，但是具体的实现都委托给了源角色，而这些对高层次模块是透明的"）；③提高类的复用度（源角色在原系统照常使用，在目标角色中"也可以充当新的演员"）；④灵活性非常好（删除适配器即可，"类似一个灵活的构件，想用就用，不想就卸载"）。
- 类适配器 vs 对象适配器（L10777-10781）：根本区别是"类适配器是类间继承，对象适配器是对象的合成关系，也可以说是类的关联关系"；对象适配器耦合更松、设计更灵活（可修补源角色隐形缺陷、关联其他对象），"在实际项目中，对象适配器使用到场景相对较多"。
- 扩展案例（L10569-10760）：对方系统拆成三接口三实现时不能再用继承（Java 不支持多继承），改用对象适配器——OuterUserInfo 关联三个接口对象并在构造函数中注入（L10741-10760）；"OuterUserInfo变成了委托服务……它的委托是通过对象层次的关联关系进行委托的，而不是继承关系"（L10758-10760）。拆接口本身符合单一职责原则："类可以有多重职责，但是接口一定要职责单一"（L10629-10631）。

**⑤ 最佳实践/作者忠告**
- 定性（L10782-10784）："适配器模式是一个补偿模式，或者说是一个'补救'模式……在百分之百的完美设计中是不可能使用到的。"
- 它是"救世主"：在"需求巨变、业务飞速而导致你极度郁闷、烦躁、崩溃的时候横空出世，它通过把非本系统接口的对象包装成本系统可以接受的对象，从而简化了系统大规模变更风险的存在"（L10790-10792）。
- 再次提醒（L10567-10568）：项目一定要遵守依赖倒置原则和里氏替换原则，否则即使在适合使用适配器的场合，也会带来非常大的改造。
- 中转类实现里大量 (String) 强转是历史局限，"如果使用泛型的话，就可以完全避免这个转化"（L10409-10410）。

**补充**
- 模式间关系：适配器又叫包装模式，但包装模式还包括第17章的装饰模式（L10452-10454）——同是"加一层衣服"，装饰注重动态增强、适配器注重接口转换；对象适配器的"委托服务"写法与装饰/代理的委托思路同源。
- 代码示例一句话概括：2004 系统的 IUserInfo（6 个 String getter）对接 2005 劳服公司 IOuterUser（3 个返回 Map 的 getter）——类适配器版 OuterUserInfo extends OuterUser implements IUserInfo 在 getter 里从 Map 取值转换；对象适配器版改为构造函数注入三个接口对象再取 Map 委托，Boss 端只需把 new UserInfo() 改为 new OuterUserInfo(...) 一句话。

## 第20章 迭代器模式（Iterator）｜L10797-11251

**① 模式意图**：提供一种方法访问一个容器对象中各个元素，而又不需暴露该对象的内部细节（L11090-11092）——迭代器是为容器服务的（L11093-11094）。

**② 使用场景与触发条件**
- 何时用（L11088-11089）："目前已经是一个没落的模式，基本上没人会单独写一个迭代器，除非是产品性质的开发"——即自研容器/框架等产品级开发才考虑手写。
- 何时不用（L11239-11243, L11249-11251）：Java 已把迭代器融入基本 API（Iterable 及大量实现类），"我们再去写迭代器，就有点多余了……基本上很少有项目再独立写迭代器了，直接使用 Collection 下的实现类就可以完美地解决问题"；最佳实践："如果你是做 Java 开发，尽量不要自己写迭代器模式！省省吧，使用 Java 提供的 Iterator 一般就能满足你的要求了"。只有使用"古董级（指版本号）的编程语言"才需自己动手（L11246-11248）。

**③ 不用时的做法、反例、缺点/代价**
- 不用时做法：直接复用 JDK 容器——第一版 IProject.getProjectInfo()，Boss 持 ArrayList 用 for-each 遍历（L10815-10903）；for-each 之所以能运行，"还不是因为 ArrayList 已经实现了 iterator() 方法"（L11225-11226）。
- 反例/代价：第二版为演示模式手写 Iterator，运行结果与第一版完全相同（L11065-11080），但"程序复杂性增加了不少"——"难道我们退回到原始时代了吗？非也，非也，只是我们回退到 JDK1.0.8 版本的编程时代了"（L11084-11086）；在简单应用中套迭代器反而"使原本简单的应用变得复杂起来"（L11224）。
- 手写的坑：remove 语义易错——"迭代器的删除方法应该完成两个逻辑：一是删除当前元素，二是当前游标指向下一个元素"（L11166-11167）。

**④ 论据**
- 演进案例：Boss 要 103 个项目的最新报表（L10800-10812）→ 第二版 IProject 增加 add() 与 iterator()（L10933-10938），ProjectIterator 以游标实现 hasNext/next/remove（L10999-11032），Boss 改用 while(iterator.hasNext()) 遍历（L11041-11063）。
- 四角色（L11109-11118）：Iterator 抽象迭代器——"基本上是有固定的 3 个方法：first()、next()、isDone()（Java 叫做 hasNext() 方法）"；ConcreteIterator 具体迭代器；Aggregate 抽象容器——"必然提供一个类似 createIterator() 这样的方法，在 Java 中一般是 iterator() 方法"；ConcreteAggregate 具体容器。
- 职责分离（L11106-11107）："迭代器模式提供了遍历容器的方便性，容器只要管理增减元素就可以了，需要遍历时交由迭代器进行"；"迭代器就类似于一个数据库中的游标，可以在一个容器内上下翻滚"（L11221-11222）。
- 通用源码（L11124-11213）：抽象迭代器仅声明 next()/hasNext()/remove()；具体迭代器持 Vector 与游标 cursor，next() 先判 hasNext() 再 vector.get(cursor++)；具体容器 iterator() 返回 new ConcreteIterator(this.vector)。
- 作者习惯（L10993-10997）：实现容器或其他 API 提供接口时，"我一般都自己先写一个接口继承，然后再继承自己写的接口，保证自己的实现类只用实现自己写的接口……程序阅读也清晰一些"；"杀猪杀尾巴，各有各的杀法"（L10994）。
- 没落论据（L11228-11248）：JDK 1.2 增加 java.util.Iterator 并逐步应用到各聚集类；JDK 1.5 的 Iterable 被 Collection/List/Queue/Set 等继承，ArrayList/LinkedList/Vector/HashSet 等大量实现（L11229-11238）；"一些大师级人物甚至建议把迭代器模式从 23 个模式中删除……就是因为现在它太普通了，已经融入到各个语言和工具中了"（L11244-11248）。

**⑤ 最佳实践/作者忠告**
- "如果你是做 Java 开发，尽量不要自己写迭代器模式！省省吧"（L11249-11251）。
- 产品性质开发才自写迭代器（L11088-11089）；若必须自写，remove 双逻辑（L11166-11167）+ 自建接口先继承 JDK 接口的封装习惯（L10993-10997）。

**补充**
- 模式间关系：与第21章组合模式直接衔接——组合模式树枝构件的 getChildren() "一般返回的结果为 Iterable 的实现类"（L12127-12128），组合树的遍历建在迭代器设施之上；"容器管增减、迭代器管遍历"与组合模式递归遍历树是同一职责（遍历）的两种载体。
- 代码示例一句话概括：IProject 声明 add() 与 iterator()，Project 内部用 ArrayList 存 Project 并返回 new ProjectIterator(projectList)，ProjectIterator 以游标实现 hasNext/next/remove，Boss 由 for-each 改为 while(hasNext()) 逐个 next() 打印 103 个项目报表——先"回退到 JDK1.0.8 时代"手写，再点破 JDK 已内建。

## 第21章 组合模式（Composite）｜L11254-12295

**① 模式意图**：将对象组合成树形结构以表示"部分-整体"的层次结构，使得用户对单个对象和组合对象的使用具有一致性（L11942-11947；又叫合成模式、部分-整体模式 Part-Whole，主要用来描述部分与整体的关系）。

**② 使用场景与触发条件**
- 何时用（L12050-12052）：①维护和展示部分-整体关系的场景，如树形菜单、文件和文件夹管理；②从一个整体中能够独立出部分模块或功能的场景。
- 触发判断（L12053-12055）："只要是树形结构，就要考虑使用组合模式，这个一定要记住，只要是要体现局部和整体的关系的时候，而且这种关系还可能比较深，考虑一下组合模式吧。"
- 何时慎用（L12046-12049）：安全模式下场景类"直接使用了实现类！这在面向接口编程上是很不恰当的，与依赖倒置原则冲突……它限制了你接口的影响范围"——需按 DIP 要求在透明/安全两式间显式权衡。

**③ 不用时的做法、反例、缺点/代价**
- 初学者反例（L11308-11334, L11631-11635）：为根/树枝/树叶定义 IRoot/IBranch/ILeaf 三接口三实现——getInfo 每个接口都有却未抽象；"Root 类和 Branch 类有什么差别？根节点本身就是树枝节点的一种，为什么要定义成两个接口两个类？"；"如果我要加一个任职期限，你是不是每个类都需要修改？"；后序遍历（从员工找上级）做不到——"彻底晕菜了！"
- 场景类代价（L11577-11578）：组装代码一大坨——"你写一大坨的程序给谁呀，以后还要维护，程序要短小精悍！"
- 模式自身缺点（L12046-12049）：破坏依赖倒置——场景类依赖 Branch/Leaf 具体类并以 instanceof+强转分支遍历。
- 透明模式的代价（L12126-12130）：组合方法上提到抽象构件后叶枝结构相同，需"通过判断 getChildren 的返回值确认是叶子节点还是树枝节点，如果处理不当，这个会在运行期出现问题，不是很建议的方式"。

**④ 论据**
- 场景与三版演进（L11256-11941）：公司人事架构是典型树状结构（L11262-11303），节点分根/树枝/树叶（L11304-11307）。第一版三接口三实现（L11335-11576）→ 自省缺陷（L11631-11635）→ 第二版合并 IRoot 与 IBranch（"确认无疑的事我们先做"L11636-11637），以"接口的作用……定义一类事物所具有的共性"（L11638-11639）提炼 ICorp 承载 getInfo；ILeaf 成空接口——"空接口有何意义呀？有意义！它是每个树叶节点的代表，系统扩容的时候你就会发现它是多么'栋梁'"（L11675-11676）→ 第三版把 Leaf/Branch 共有字段与 getInfo 上收到抽象类 Corp："接口没有了，改成抽象类了……太精简了！而且场景类只认定抽象类 Corp 就成"（L11862-11864）；"这就是组合模式"（L11941）。
- 三角色（L11958-11968）：Component 抽象构件——定义共有方法和属性、可定义默认行为（例中 getInfo 封装到抽象类）；Leaf 叶子构件——"其下再也没有其他的分支，也就是遍历的最小单位"；Composite 树枝构件——"组合树枝节点和叶子节点形成一个树形结构"。
- 优点（L12036-12042）：①高层模块调用简单——"一棵树形机构中的所有节点都是 Component，局部和整体对调用者来说没有任何区别……简化了高层模块的代码"；②节点自由增加——"只要找到它的父节点就成，非常容易扩展，符合开闭原则"。
- 原则冲突预告（L12033-12034）："组合模式是对依赖倒转原则的破坏，但是它还有其他类型的变形"——引出扩展小节。
- 真实项目形态（L12056-12113）：树的组装"是跑不了的"，但谁分配到枝/叶应由业务人员维护进数据库——单表（主键/唯一编码/名称/是否叶子节点/父节点，图21-7）存树，程序"用 for 循环加上递归就可以完成这个读取"（L12106-12107）；"这才是组合模式的真实引用，它依靠了关系数据库的非对象存储性能，非常方便地保存了一个树形结构"（L12112-12113）。
- 透明 vs 安全（L12114-12196）：透明模式 Leaf 空实现 add/remove/getChildren 并抛 UnsupportedOperationException，加 @Deprecated"就是在编译器期告诉调用者……该方法已经失效"（L12156-12176）；遍历不再强转（L12177-12191），"好处就是它基本遵循了依赖倒转原则，方便系统进行扩展"（L12192-12196）；安全模式"把树枝节点和树叶节点彻底分开，树枝节点单独拥有用来组合的方法，这种方法比较安全，我们的例子使用了安全模式"（L12130-12132）。
- 双向遍历（L12197-12279）：Corp 增 setParent/getParent，Branch.addSubordinate 中先 corp.setParent(this) 再入列表（L12257-12272），"除了根节点外每个节点都有一个父节点"；"什么后序遍历（从下往上找）、中序遍历（从中间某个环节往上或往下遍历）都解决了"（L12278-12279）；叶/枝排序（"排位"）留作思考（L12280-12282）。

**⑤ 最佳实践/作者忠告**
- 口诀式忠告（L12053-12055）："只要是树形结构，就要考虑使用组合模式。"
- 项目中无处不在：页面导航菜单是树形（大量 JavaScript 实现，L12284-12289）；XML 是树形——根/元素/值元素"都与我们的组合模式相匹配"，但"很少有人还直接读写 XML 文件，一般都是用 JDOM 或者 DOM4J 了"（L12290-12292）；家族谱系"很典型的树形结构"（L12293-12295）。
- 真实落地优先"数据库存树 + for/递归读"，别在代码里硬编码整棵树（L12106-12113）。

**补充**
- 模式间关系：承上——树枝构件 getChildren() "一般返回的结果为 Iterable 的实现类"（L12127-12128），组合模式的遍历直接建在第20章迭代器模式之上；原则面——安全式"破坏依赖倒转"（L12033）与透明式"基本遵循了依赖倒转原则"（L12196）正反呼应六大原则之 DIP，优点②"符合开闭原则"（L12042）。
- 代码示例一句话概括：组织架构树三版演进——①IRoot/IBranch/ILeaf 三接口三实现；②提炼 ICorp（getInfo）+ IBranch（addSubordinate/getSubordinate）+ ILeaf 空接口；③抽象类 Corp 收编共有字段与 getInfo，Branch 只剩 subordinateList 与 add/get，Client 递归 getTreeInfo(root) 以 instanceof Leaf 分支打印；扩展版再给每个节点挂 parent 指针支持向上遍历。
