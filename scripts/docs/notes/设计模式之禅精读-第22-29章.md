## 第22章 观察者模式（Observer）｜L12300-13001

**① 模式意图**：定义对象间一种一对多的依赖关系，使得每当一个对象改变状态，所有依赖于它的对象都会得到通知并被自动更新（定义 L12735-12737）；也称发布订阅模式（Publish/Subscribe），"是一个在项目中经常使用的模式"（L12732-12734）。

**② 使用场景与触发条件**
- 何时用（L12857-12860）：①关联行为场景——注意"关联行为是可拆分的，而不是'组合'关系"；②事件多级触发场景；③跨系统的消息交换场景，如消息队列的处理机制。
- 典型触发：一个对象（被观察者）的状态变更需要通知"不确定多数"的对象——韩非子的活动"有一大帮的各国类似于李斯这样的人在看着他"（L12556-12558）。
- 何时不用/慎用：广播链过长时——"链一旦建立，这个逻辑就比较复杂，可维护性非常差"（L12867-12869）；对运行效率敏感且观察者处理耗时长时——Java 中消息通知默认顺序执行，"一个观察者卡壳，会影响整体的执行效率"（L12852-12854）。

**③ 不用时的做法、反例、缺点/代价**
- 反例一·死循环监控（L12327-12333, L12429-12459）：写一个 Spy 后台线程 while(true) 死循环轮询被观察者状态。作者痛批："结果正确但并不表示你有成绩，我告诉你：你的成绩是O，甚至是负的！……使用了死循环while(true)来做监听，要是用到项目中，你要多少硬件投入进来？……一台服务器就跑你这一个程序就完事！"（L12495-12499）且"这个程序根本就不是面向对象的程序，这完全是面向过程的"（L12500-12501）。
- 反例二·硬编码聚合单一观察者（L12507-12527）：在 HanFeizi 中 private ILiSi liSi = new Lisi() 直接通知。问题：被观察者只能通知固定一个观察者——"这样一来只有李斯才能观察到韩非子，这是不对的"（L12563-12564）；且观察内容被写死——"李斯只观察韩非子的吃饭、娱乐吗？政治倾向不关心吗？"（L12565-12566）；"这和开闭原则严重违背呀"（L12567）。
- 用了之后的代价（L12852-12855）：需考虑开发效率和运行效率——一个被观察者、多个观察者时开发和调试比较复杂；消息通知默认顺序执行，一个观察者卡壳拖累整体，此时一般考虑异步；"多级触发时的效率更是让人担忧"。

**④ 论据**
- 演进论证（L12327-12731）：从"线程监控"→"聚合单一观察者"→"Observable 接口 + Observer 接口"，每一步先暴露上一步缺陷（CPU 飙升、面向过程、违背开闭），模式是被问题逼出来的。
- 第三版结构（L12590-12613）：增加 Observable 接口（addObserver/deleteObserver/notifyObservers），ILiSi 改名 Observer 以显抽象化——被观察者"我可以允许有多个对象来察看……我的改变或动作执行，会通知其他的对象"（L12597-12600）。改造后"结果也正确了，也符合开闭原则了，同时也实现类间解耦，想再加观察者？继续实现Observer接口就成了……这就是观察者模式"（L12729-12731）。
- 四角色（L12749-12766）：Subject 被观察者——"必须能够动态地增加、取消观察者"，仅完成管理与通知观察者的职责；Observer 观察者——接收消息后即 update 处理；ConcreteSubject 具体被观察者——"定义被观察者自己的业务逻辑，同时定义对哪些事件进行通知"；ConcreteObserver 具体观察者——"每个观察者在接收到消息后的处理反应是不同"，各有处理逻辑。
- 优点一·抽象耦合（L12838-12840）：增加观察者或被观察者都非常容易扩展，"而且在Java中都已经实现的抽象层级的定义"。
- 优点二·触发机制（L12841-12850）：单一职责原则下每个类职责单一，"怎么把各个单一的职责串联成真实世界的复杂的逻辑关系呢？"——打猎触发链（打死母鹿→三幼崽饿死→尸体被两只秃鹰争抢→斗殴→赢弱者死→生存者扩大地盘），"观察者模式可以完美地实现这里的链条形式"。
- ArrayList vs Vector（L12788-12789）："没有太大的差别，ArrayList是线程异步，不安全，Vector是线程同步，安全——就这点区别。"

**⑤ 最佳实践/作者忠告**
- 广播链上限（L12867-12869）：观察者可兼双重身份，但"根据经验建议，在一个观察者模式中最多出现一个对象既是观察者也是被观察者，也就是说消息最多转发一次（传递两次）"。
- 异步处理（L12873-12876）：观察者多且处理时间长时用异步，"异步处理就要考虑线程安全和队列的问题"，建议看 Message Queue 加深理解。
- 用 Java 自带实现（L12884-12944）：java.util.Observable 实现类 + java.util.Observer 接口可直接使用（super.setChanged() 后 notifyObservers）；"在Java的世界里横行时，多看看API……很多东西Java已经帮你设计了一个良好的框架了"。
- 项目实战三个改装（L12945-12970）：①update 接受两个参数——被观察者 + DTO（"纯洁的JavaBean，由被观察者生成，由观察者消费"），远程传输用 XML；②观察者快速响应两法——多线程（异步架构）或缓存（同步架构，"代价就是开发难度很大，而且压力测试要做的足够充分"）；③被观察者尽量自己做主——重载 doSomething(boolean isNotifyObs) 在源头决定是否通知，"而不是在消息到达观察者时才判断是否要消费"。
- 订阅发布模型（L12971-12981）：EJB 的 MessageDriven Bean"从原理上看很简单，就是观察者模式的升级版，或者说是观察者模式的BOSS版"。
- 生活例证（L12984-12999）：文件系统（新建文件同时通知目录管理器与磁盘管理器）、猫鼠游戏（猫叫→老鼠跑、主人醒）、ATM 吞卡（摄像头快拍+通知监控系统走观察者模式，初始化屏幕返回初始状态由异常完成）、广播收音机（电台=被观察者，收音机=观察者）。

**补充**
- 模式间对比：与责任链模式的最大区别在消息可变性——广播链传播中"消息是随时更改的，它是由相邻的两个节点协商的消息结构；而责任链模式在消息传递过程中基本上保持消息不可变，如果要改变，也只是在原有的消息上进行修正"（L12870-12872）；广播链问题类比数据库触发器链（表 A→B→C 级联，"这个数据库基本上就毁掉了！"L12863-12866）；"纯净的观察者在具体项目中有很多变种"（L12802）。
- 代码示例一句话概括：韩非子被监控案例从 Spy 死循环线程、到聚合单个 Lisi，最终演进为 HanFeizi implements Observable+IHanFeizi 持 ArrayList<Observer> 在 haveBreakfast/haveFun 中 notifyObservers，李斯（汇报秦王）、王斯（哭）、刘斯（乐）三个观察者各自 update 反应（L12618-12694）。

## 第23章 门面模式（Facade Pattern）｜L13002-13432

**① 模式意图**：要求一个子系统的外部与其内部的通信必须通过一个统一的对象进行，门面模式提供一个高层次的接口，使得子系统更易于使用（定义 L13218-13221）；又称外观模式，是比较常用的封装模式之一。

**② 使用场景与触发条件**
- 引子（L13005-13091）：投递一封信要 4 个步骤——写信内容、写信封、装信封、投递，一个都不能少、顺序不能颠倒，客户端必须知道全部步骤与顺序；一旦要发的信多了（如广告信），每封都这么运转一遍就非常麻烦。
- 何时用（L13309-13317）：①为一个复杂的模块或子系统提供一个供外界访问的接口；②子系统相对独立——外界只需黑箱操作即可，如利息计算（输入金额、存期，返回利息，内部算法外界不关心）；③预防低水平人员带来的风险扩散——"画地为牢"，把水平较差的成员安排在子系统中开发，只提供门面接口。
- 何时需要多个门面（L13319-13347）：①门面庞大到不能忍受（经验值：超过 200 行代码建议按功能拆分，如数据库操作门面拆为查询、删除、更新门面）；②子系统可提供不同访问路径——如某模块只允许访问部分方法，可新建门面 Facade2 委托给已有门面，而非重新写委托到子系统的代码，"尽量保持相同的代码只编写一遍，避免以后到处修改相似代码的悲剧"。

**③ 不用时的做法、反例、缺点/代价**
- 不用时的做法（L13057-13087）：客户端直接持有 ILetterProcess，自己按序调用写信、写信封、装信封、投递 4 个方法。
- 缺点（L13085-13091）：与高内聚要求相差甚远，"更不要说迪米特法则、接口隔离原则了"，根本没完成一个类的单一职责；信件一多，逐一运转非常麻烦。
- 门面自身的缺点（L13304-13308）：不符合开闭原则，对修改关闭——投产后发现小错误，继承、覆写都不顶用，唯一能做的就是修改门面代码，风险相当大，设计时"慎之又慎"。

**④ 论据**
- 优点三条（L13290-13303）：①减少系统的相互依赖——不用门面时外界直接依赖子系统内部，强耦合"你死我就死"；使用后所有依赖都是对门面对象的依赖，与子系统无关；②提高灵活性——只要不影响门面对象，子系统内部"想怎么动就怎么动"；③提高安全性——不在门面上开通的方法"休想访问到"。
- 透明扩展论证（L13149-13213）：非常时期对寄往 God Province 的信必须安全检查，新增 Police 类后只在 ModenPostOffice 内部插入检查调用，高层模块零改动——"这个变更对客户来说是透明的"；不改变子系统对外暴露的接口、方法，只改变内部的处理逻辑，"这就是门面模式的妙处所在"（L13211-13213）。
- 角色定义（L13238-13246）：Facade 门面角色——知晓子系统的所有功能和责任，本质是委托类，没有实际业务逻辑；Subsystem 子系统角色——可以是一个或多个，"子系统并不知道门面的存在，对子系统而言，门面仅仅是另外一个客户端而已"。
- 唯一通道警示（L13222-13235）：门面模式注重"统一的对象"，除门面接口外不允许有任何访问子系统的行为发生；门面对象是外界访问子系统内部的唯一通道，作者并以"金玉其外，败絮其中"作警示。

**⑤ 最佳实践/作者忠告**
- 门面不参与子系统内的业务逻辑（L13348-13379）：若某方法需要先调 ClassA 再调 ClassC，绝不能在门面里直接写两段调用（清单 23-11，被批"非常不靠谱"）——门面一旦参与业务逻辑，就会产生倒依赖问题：子系统必须依赖门面才能被访问，既违反单一职责原则，又破坏系统的封装性。正解（清单 23-12/23-13）：建立封装类 Context，把该业务逻辑 complexMethod 放在子系统内、只依赖子系统相关对象，门面只调用 context.complexMethod（L13380-13414）。
- 稳定性忠告（L13415-13422）："门面角色应该是稳定的，它不应该经常变化，一个系统一旦投入运行它就不应该被改变"；业务逻辑是经常变化的，应把变化封装在子系统内部——"这才是架构师最希望看到的结构"。
- 23.5 最佳实践（L13423-13431）：子系统复杂时尽量封装出一个或多个门面，项目结构简单、扩展性好；较大项目用门面规避人员风险——技术水平差的成员安排独立模块开发，程序封装到门面里；书中以"高人"写代码的笑话作靶（所有逻辑堆在一个 public 方法里）；并建议对门面进行单元测试，约束项目成员的代码质量。

**补充**
- 模式间对比：不用门面被批"更不要说迪米特法则、接口隔离原则了"（L13085-13086），门面是这两个原则在子系统边界上的直接落地；本章"门面稳定、变化封装在子系统内部"（L13415-13422）延续了全书"封装变化"的主线。
- 代码示例一句话概括：投递信件案例——客户端自己按序调 4 步（23-1~23-3）；ModenPostOffice（"地狱路邮局"）封装 4 步后客户端只调 sendLetter（23-4/23-5）；加警察安全检查仅改门面内部、客户端无感（23-6/23-7）；通用源码 ClassA/B/C 子系统 + Facade 委托（23-8/23-9）；受限门面 Facade2 委托原门面（L13327-13344）；反例门面参与业务逻辑 vs 正解封装类 Context（23-11~23-13）。

## 第24章 备忘录模式（Memento Pattern）｜L13434-14294

**① 模式意图**：在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，以便以后把该对象恢复到原先保存的状态（定义 L13693-13700）；通俗地说就是一个对象的备份模式，提供程序数据的备份方法（L13701）。

**② 使用场景与触发条件**
- 引子（L13437-13458）：《预见未来》（Next）主角可预视未来、不断重试搭讪，失败即回到原点——最重要的是"原始状态的保留和恢复"，需要在程序中定义中间变量保留原始状态。
- 何时用（L13797-13805）：①需要保存和恢复数据的相关状态场景；②提供一个可回滚（rollback）的操作——Word 的 CTRL+Z、IE 的后退按钮、文件管理器的 backspace；③需要监控的副本场景（监控属边缘应用：备份主线程对象供分析程序分析，分析后再备份）；④数据库连接的事务管理就是用备忘录模式（可据此实现 JDBC 驱动的事务）。

**③ 不用时的做法、反例、缺点/代价**
- 反例一（L13492-13528）：高层模块（场景类）自己 new 一个 Boy 作备份对象，修改后逐字段回填。缺点：backup 变量对高层模块完全是多余的，状态的保存与恢复本应是 Boy 类的职责，该写法破坏了 Boy 类的封装。
- 反例二（L13555-13623）：Boy 增加 createMemento/restoreMemento，把备份职责收回类内。仍不足：高层模块还要亲自接触 Memento 对象——"这对迪米特法则是一个亵渎"，高层只希望"创建一个备份点、恢复一个备份点"，不想关心有没有备忘录这个类。
- 使用代价（L13806-13813）：①备忘录的生命期——创建后要在"最近"的代码中使用，不用就立刻删除引用等待垃圾回收；②备忘录的性能——不要在频繁建立备份的场景（如 for 循环）中使用：备份对象数量控制不了，大对象的建立又消耗资源；出现这种代码"设计师就应该好好想想怎么修改架构了"。
- 多备份的内存风险（L14196-14198）：备份一旦产生就装入内存、没有销毁意向，非常危险；要严格限定备忘录的创建，建议给 Map 容器增加上限。

**④ 论据**
- 演进论证（L13458-13691）：定义中间变量保留原始状态 → 引入 Memento 独立承担保存/恢复职责（Boy 的职责是"追女孩"，状态的保留和恢复应由另外一个类承担，L13529-13533）→ 再引入管理类 Caretaker：备份者类似"备份的仓库管理员"，高层只创建/恢复备份点——"这就是备忘录模式"（L13688-13691）。
- 三角色（L13712-13718）：Originator 发起人角色——记录当前时刻的内部状态，定义哪些属于备份范围，创建、恢复备忘录数据；Memento 备忘录角色——存储发起人角色的内部状态，需要时提供；Caretaker 备忘录管理员角色——对备忘录进行管理、保存和提供。
- 多状态备份论据（L13956-13959）：实际项目中 JavaBean 多状态是常态，照搬单状态写法要写一堆备份/还原语句，"非智力劳动"越多、犯错误的几率就越大。

**⑤ 最佳实践/作者忠告**
- 扩展一·clone 方式（L13815-13954）：发起人实现 Cloneable 即可融合发起人与备忘录双重角色（createMemento 返回 this.clone()，L13835-13864）；管理员改存 Originator（L13867-13880）；甚至可精简掉管理员——发起人自持 backup 字段、自主备份恢复（L13883-13916）。作者坦承这与定义"在该对象之外保存状态"不符——设计模式定义的诞生比 Java 出世略早，"我们把它弥补回来"（L13917-13924）。适用边界：clone 方式适用于比较简单或单一的场景；复杂场景下深拷贝浅拷贝问题会让程序逻辑异常混乱、错误难以跟踪，不要与其他对象产生严重耦合（L13951-13954）。
- 扩展二·多状态（L13955-14155）：用工具类 BeanUtils（Introspector 内省 + PropertyDescriptor 遍历属性、getter 反射取值）把发起人全部属性备份进 HashMap，"不管有多少状态都没有问题"（L14052-14053）；不直接用 Originator 拷贝——会破坏发起人的通用性，恢复时多次赋值也容易出错（L13983-13984）。BeanUtils 这类工具在项目中常用，Spring、Apache commons 等也提供（L14091-14092）；设计运行期决定备份状态的框架建议采用 AOP 实现，避免动态代理无谓增加程序逻辑复杂性（L14154-14155）。
- 扩展三·多备份（L14156-14198）：引入检查点（Check Point）概念——备份时的戳记，系统级备份一般是时间戳，程序中的检查点一般是"有意义的字符串"（L14166-14167）；Caretaker 容器改为 HashMap<String, Memento>，可创建"001"、"002"等多个备份并按标记恢复指定备份（L14169-14195）。
- 扩展四·封装得更好一点（L14199-14287）：备份数据"完全绝对不能修改"，要保证数据洁净、避免污染；应缩小备忘录的阅读权限，只有发起人可读——用空接口 IMemento + 发起人内置 private 类 Memento（全 private 访问权限）实现"双接口设计"：一个类可实现多个接口，业务正常接口是宽接口（提供必要的业务逻辑），空接口是窄接口（提供给子系统外模块如容器对象访问，相对安全）（L14283-14287）。同时提醒："安全是相对的，没有绝对的安全，可以使用 reflect 反射修改 Memento 的数据"（L14281-14282）。
- 24.5 最佳实践（L14288-14293）：备忘录模式是设计上的"月光宝盒"、程序数据的"后悔药"、设计人员的定心丸——最坏情况下也能获得最近一个点的对象状态；忠告：不要使用数据库临时表作缓存备份数据——加大数据库操作频繁度、把压力下放到数据库，最好用备忘录模式。

**补充**
- 模式间对比：clone 方式备忘录直接借用第 13 章原型模式（L13815-13817）；反例二被批"对迪米特法则是一个亵渎"（L13620-13623），模式演进的目标正是让高层模块不接触 Memento 细节。
- 代码示例一句话概括：追女孩案例三级演进——场景类自建备份对象（24-1/24-2）→ Boy+Memento（24-3~24-5）→ 再加 Caretaker 管理员（24-6/24-7）；通用源码三角色（24-8~24-11）；四种扩展依次为 clone 融合式（24-12~24-15）、BeanUtils 全属性 HashMap 备份（24-16~24-19）、Map 容器多备份+检查点（24-20/24-21）、空接口+内置类的双接口封装（24-22~24-24）。

## 第25章 访问者模式（Visitor Pattern）｜L14296-15264

**① 模式意图**：封装一些作用于某种数据结构中的各元素的操作，它可以在不改变数据结构的前提下定义作用于这些元素的新的操作（定义 L14705-14712）；作者称其"是一个相对简单的模式"（L14705）。

**② 使用场景与触发条件**
- 引子（L14298-14307）：公司 700 多名技术人员分布全国，要把所有人员信息打印成报表呈报领导——前两章组合模式搭好组织机构树、迭代器模式遍历出"有人去世了还在领退休金""拿高工资而不干活的尸位素餐"等情况，本章把这些情况统计成报表呈报上去。
- 触发条件（L14467-14477）：①大老板只看部门经理的报表，小兵的报表可看可不看；②多个大老板的"嗜好"不同——主管销售的关心营销情况、主管会计的关心整体财务运行状态、主管技术的看研发情况。综合结论："这个报表会修改：数据的修改以及报表的展现修改，按照开闭原则……就需要在设计时考虑通过扩展来避开未来需求变更而引起的代码修改风险"。
- 何时用（L14865-14877）：①一个对象结构包含很多类对象、有不同的接口，想对这些对象实施一些依赖于其具体类的操作——"也就是说用迭代器模式已经不能胜任的情景"；②需要对一个对象结构中的对象进行很多不同并且不相关的操作，而想避免让这些操作"污染"这些对象的类。一句话总结："业务规则要求遍历多个不同的对象。这本身也是访问者模式出发点"（L14873-14874）。
- 何时不用：数据同类或同接口时迭代器模式即可胜任（L14874-14875）；用 instanceof 固然能访问所有数据、"这没有争论"，但不是好办法（L14874-14875, L14850-14852）。

**③ 不用时的做法、反例、缺点/代价**
- 不用时的做法（L14333-14334, L14477-14478）：抽象 Employee 用模板方法模式——report 固定打印姓名/性别/薪水，getOtherInfo 抽象方法由子类扩展（普通员工报"工作"、经理报"业绩"）。
- 缺点：report 自父类继承，"他无法为每一个子类定制特殊的属性"；报表展现一变就得动原有类，未按开闭原则预留扩展点（L14475-14478）。
- 统计场景反例（L14846-14852）：统计工资总和可以"把所有人的工资for循环加一遍"；但"员工工资×1.2，部门经理×1.4，总经理×1.8，然后把这些工资加起来"怎么办？用 for 循环 + instanceof 判断是员工还是经理——"这可以解决，但不是个好办法"，好办法是通过访问者模式，把数据扔给访问者进行统计计算。
- 模式自身缺点（L14853-14863）：①具体元素对访问者公布细节——"访问者关注了其他类的内部细节，这是迪米特法则所不建议的"；②具体元素变更比较困难——想增加成员变量如年龄 age，Visitor 就需要修改，"如果Visitor是一个还好办，多个呢？业务逻辑再复杂点呢？"；③违背依赖倒置原则——访问者依赖具体元素而非抽象元素，"抛弃了对接口的依赖，而直接依赖实现类，扩展比较难"。

**④ 论据**
- 演进论证（L14482-14485, L14497-14498）：引入"参观"类比——把对象当作名胜古迹，每类不同的名胜古迹由不同的访问者参观，"参观的对象不同，描述的结果也当然不同"；Visitor 依赖具体元素而非抽象 Employee，"猛一看还真有点委托的意味……但是它与委托还有非常大的差距"——它封装了角色的职责。
- accept 方法意义（L14527-14528）："说我这个类可以允许谁来访问，也就是定义一类访问者"。
- Employee 类三处变动（L14604-14608）：删掉 report、删掉 getOtherInfo、增加 accept(visitor)——"数据报表就应该由访问者来实现，而不是由员工对象来实现，访问者对被访问的对象是'心知肚明'的"。
- 运行机制五步（L14692-14697）：①Visitor 声明可访问元素并重载 visit；②元素声明 accept 并以自己为参数调 visitor.visit(this)；③ObjectStructure 遍历容器内元素逐个 accept；④具体访问者按元素具体类型做相应计算；⑤输出结果。
- 变更扩展对比（L14698-14703）：数据结构变更（加、减元素）——访问者模式与普通方案都要改，两者无优劣；格式或算法变更——访问者模式"绝对是有优势的"，只需增加一个 IVisitor 的实现类即可，Spring 环境下甚至只需改一个 ref 配置。
- 五个角色（L14729-14740）：Visitor——声明可访问元素，visit 方法的参数定义了可访问哪些对象；ConcreteVisitor；Element——声明接受哪一类访问者访问，accept 参数；ConcreteElement——"通常是visitor.visit（this）"；ObjectStructure——容器角色（List/Set/Map），"项目中一般很少抽象出这个角色"，例中承载元素的 List 即是（L14726-14728）。
- 访客类比（L14741-14748）：到朋友家拜访，朋友加官进爵、工资涨 30%、买了大房子，表面上握手说恭喜（方法一），心里却在盘算（Visitor-self-method）"你这么有钱，我去年要借 10 万你都不借"——同一件事两套思维逻辑，方法一充当双重职责。
- 优点（L14838-14852）：①符合单一职责——数据加载（Employee）与报表展现（Visitor）分离，"各自演绎变化"；②扩展性——只要继承 Visitor 类，"甭管它是什么对象，只要它在一个容器中，都可以通过访问者来访问，任务集中化。这就是访问者模式"（L14830-14832）；③灵活性——每个对象不再被动接受规则，统计类、UI 类等都能把它扔给对应的访问者处理。
- 双分派机制（L15151-15258）：重载（编译期、静态绑定，看表面类型）与覆写（运行期、动态绑定，看实际类型）分工不同（L15215-15216）；OldActor 引用 + Role 表面类型时 act(role) 输出"演员可以扮演任何角色"，act(new KungFuRole()) 却输出"年龄大了，不能演功夫角色"（L15212-15216）；给角色加 accept 反调 actor.act(this)，两步双分派后成功匹配；"双分派意味着得到执行的操作决定于请求的种类和两个接收者的类型，它是多分派的一个特例……Java是一个支持双分派的单分派语言"（L15256-15258）。

**⑤ 最佳实践/作者忠告**
- 该模式是"集中规整模式，特别适用于大规模重构的项目"——把功能和数据分离，把一些全局性、共性的功能剥离出来集中规整，"功能集中化，如一个统一的报表运算、UI展现等，非常适合访问者模式"（L15260-15264）。
- 统计实现忠告（25.4.1, L14881-14991）：作者"不建议使用数据库的存储过程来实现"统计，除非数据量巨大——"一个晚上要批处理上亿、几十亿条的数据，除了存储过程来处理还没有其他办法"，否则海量数据传入应用服务器会"使得网络100%的占用"（L14882-14886）；计薪系数普通员工×2、部门经理×5 由 Visitor 实现（L14930-14957）。
- 多访问者（25.4.2, L14992-15150）：展示表与汇总表是"对同一堆数据的两种处理方式"（L14993-14997）；用 IShowVisitor/ITotalVisitor 分别 accept 两类访问者（L15121-15133）；多访问者还可用于数据挖掘的上切、下钻分析（L15149-15150）。
- 访问者可充当拦截器 Interceptor 角色，具体在混编模式章节讲解（L14877）。

**补充（模式间对比与代码示例）**
- 与迭代器模式：本章是迭代器模式的扩充——遍历"同一堆数据、同类或同接口"时迭代器即可，对象结构含"很多不同类型、不同接口"且操作依赖具体类时才轮到访问者（L14873-14876）。
- 与模板方法模式：访问者版本对 Employee 的改造正是弃用模板方法（report+getOtherInfo）的结果——报表职责从元素移交给访问者（L14333-14334, L14604-14608）。
- ObjectStructure 可用工厂方法模式模拟：传入元素类型动态创建员工/经理对象（L14804-14807）。
- 代码示例一句话概括：25-1~25-4 演示模板方法版员工报表（report 固定格式+getOtherInfo 子类定制）；25-5~25-10 演示访问者版改造（IVisitor 重载 visit(Employee/Manager)、Employee.accept 委派）；25-11~25-16 演示通用源码（抽象 Element/ConcreteElement/ObjectStructure 容器+访问者实现）；25-17~25-19 演示工资统计（员工×2、经理×5 的薪酬访问者）；25-20~25-24 演示多访问者（普通员工表+管理干部汇总表两类 Visitor 同时 accept）；25-25~25-30 演示演员角色双分派（OldActor/YoungActor 重载 act 匹配 KungFuRole/IdiotRole）。

## 第26章 状态模式（State Pattern）｜L15267-16017

**① 模式意图**：当一个对象内在状态改变时允许其改变行为，这个对象看起来像改变了其类（定义 L15825-15831）；"状态模式的核心是封装，状态的变更引起了行为的变更，从外部看起来就好像这个对象对应的类发生了改变一样"（L15835-15836）。

**② 使用场景与触发条件**
- 引子（L15269-15354）：用程序表现电梯运作——电梯有开门、关门、运行、停止 4 个动作；第一版直接实现后发现"电梯门可以打开，但不是随时都可以开，是有前提条件的"，"电梯的这4个动作的执行都有前置条件，具体点说就是在特定状态下才能做特定事"（L15351-15354）。
- 四种状态（L15355-15364）：敞门状态只能做关门动作；闭门状态可开门/停止/运行；运行状态只能停止；停止状态可继续运行和开门。
- 场景一（L15966-15969）：行为随状态改变而改变的场景——"这也是状态模式的根本出发点"，例如权限设计，"人员的状态不同即使执行相同的行为结果也会不同"。
- 场景二（L15970-15972）：条件、分支判断语句的替代者——大量 switch/if 判断导致"程序结构不清晰，逻辑混乱"，"它通过扩展子类实现了条件的判断处理"。
- 注意事项（L15973-15976）：适用于"在行为受状态约束的情况下"，且"使用时对象的状态最好不要超过5个"。

**③ 不用时的做法、反例、缺点/代价**
- 做法一（L15278-15348）：ILift 接口 + Lift 实现类直接实现四动作——"太简单的程序了！每个程序员都会写"，没有任何状态校验，不严谨。
- 做法二（L15380-15566）：接口加 4 个状态静态常量 + setState，实现类每个方法内 switch..case 判断当前状态是否允许执行，动作本身由私有 WithoutLogic 方法承载。
- 三大问题（L15567-15587）：①实现类太长——大量 switch..case 判断"避免不了加长程序"，"较长的方法和类无法带来良好的维护性，毕竟，程序首先是给人阅读的，然后才是机器执行"；②扩展性非常差——再增加通电、断电状态时 open/close/run/stop 四个方法都要加判断，"这与开闭原则相违背"；③非常规状态无法实现——故障、检修等业务下"一个小小的增加或改动都使得我们这个电梯类产生了修改，这在项目开发上是有很大风险的"（违背单一职责原则）。
- 模式自身缺点（L15961-15965）："只有一个缺点，子类会太多，也就是类膨胀"，"如果完全使用状态模式就会有太多的子类，不好管理"；替代方案是"如在数据库中建立一个状态表，然后根据状态执行相应的操作"。

**④ 论据**
- 视角转换（L15588-15598）：从"电梯的方法以及这些方法执行的条件"换到"电梯在具有这些状态的时候能够做什么事情"——以状态为参考模型，每个状态只需实现两个任务模型："这个状态是如何产生的，以及在这个状态下还能做什么其他动作（也就是这个状态怎么过渡到其他状态）"（L15595-15597）。
- 封装目的（L15623-15625）：LiftState 抽象类聚合受保护的 Context 变量"串联各个状态的封装类。封装的目的很明显，就是电梯对象内部状态的变化不被调用类知晓，也就是迪米特法则了（我的类内部情节你知道得越少越好）"。
- 状态过渡机制（L15674-15678, L15715-15717）：状态子类在触发方法中先 super.context.setLiftState 切换状态、再 super.context.getLiftState().xxx() 把动作委托给新状态类执行；"Context是一个环境角色，它的作用是串联各个状态的过渡"，4 个具体实现类"自己根据环境来决定如何进行状态的过渡"。
- 三角色（L15839-15847）：State——抽象状态角色，接口或抽象类，负责对象状态定义并封装环境角色以实现状态切换；ConcreteState——具体状态角色，"每一个具体状态必须完成两个职责：本状态的行为管理以及趋向状态处理"；Context——环境角色，"定义客户端需要的接口，并且负责具体状态的切换"。
- 水的三态类比（L15848-15851）："通过状态变更促使行为的变化，就类似水的状态变更一样"，液态水加热变气态，"状态的改变同时也引起体积的扩大，然后就产生了一个新的行为：鸣笛或顶起壶盖，瓦特就是这么发明蒸汽机的"。
- 环境角色两个不成文约束（L15929-15931）：①"把状态对象声明为静态常量，有几个状态对象就声明几个静态常量"；②"环境角色具有状态抽象角色定义的所有行为，具体执行使用委托方式"。
- 效果（L15945-15946）："我们已经隐藏了状态的变化过程，它的切换引起了行为的变化。对外来说，我们只看到行为的发生改变，而不用知道是状态变化引起的"。
- 优点（L15948-15960）：结构清晰（避免过多 switch..case/if..else，提高可维护性）；遵循设计原则（开闭+单一职责，"你要增加状态就要增加子类，你要修改状态，你只修改一个子类就可以了"）；封装性非常好（"状态变换放置到类的内部来实现，外部的调用不用知道类内部如何实现状态和行为的变换"）。
- 回应批判（L15815-15821）：子类化后"每个子类的代码都很短，而且也取消了switch...case条件的判断"；加状态"只是在原有类中的方法上增加，而不去做修改"；"只有与这个状态有关的因素修改了，这个类才修改，符合迪米特法则，非常完美！这就是状态模式"。

**⑤ 最佳实践/作者忠告**
- 市面资料"大家都只讲了一个状态到另一个状态的过渡"，而"项目中遇到的大多数情况都是一个状态可以转换为几种状态"（蛛网结构）（L15980-15995）；如收费网站用户状态（普通用户/普通会员/VIP会员/白金级用户）"这个状态的变更你不允许跳跃？！这不可能"——要按可自由切换的复杂情形掌握，"这才是最经常用到的状态模式"（L16001-16005）。
- 多套运行逻辑（正常：开门->关门->运行->停止；紧急如火灾：关门->停止；维修：任何情况都可以）需要"把已经有的几种状态按照一定的顺序再重新组装一下"——"建造模式+状态模式会起到非常好的封装作用"（L16006-16012）。
- 工作流开发中用状态机（State Machine）管理节点与流程实例状态（初始化/挂起/完成等），状态机"就是我们上面提到的Context类的升级变态BOSS！"（L16013-16017）。

**补充（模式间对比与代码示例）**
- 与建造者模式混编：自由切换的多套状态逻辑=按顺序重新组装既有状态（L16010-16012）。
- 与状态机：Context 即雏形，状态机是其升级形态（L16016-16017）。
- 与数据库状态表：状态过多导致类膨胀时的替代方案（L15964-15965）。

## 第27章 解释器模式（Interpreter Pattern）｜L16022-16416

**① 模式意图**：按规定的语法进行解析的方案——"给定一门语言，定义它的文法的一种表示，并定义一个解释器，该解释器使用该表示来解释语言中的句子"（定义 L16291-16294）；一句话：把每条文法规则映射为一个表达式类，递归组装成语法树后解释执行，使公式"在运行时定义，而不是在运行前就制定好"（L16283-16284）。

**② 使用场景与触发条件**
- 引子（L16025-16032）：银行、证券类项目的模型运算——"通过对现有数据的统计、分析而预测不可知或未来可能发生的商业行为"；公式虽只有加减乘除，但"有可能有十多个参数，而且上百个业务品各有不同的取参路径"；业务需求即"输入一个模型公式（加、减运算），然后输入模型中的参数，运算出结果"。
- 设计三要求（L16033-16036）：①公式可运行时编辑且符合正常算术书写方式（如 a+b-c）；②高扩展性——未来增加指数、开方、极限、求导等运算符号时较少改动；③"效率可以不用考虑，晚间批量运算"。
- 触发条件（L16037-16045）：仅对数字做四则运算人人会写，但引入可变公式后"如果使用直接计算数值的方法需要为每个品种写一个算法，目前仅仅是3个业务种类，那上百个品种呢？歇菜了吧"——"建立公式，然后通过公式运算才是王道"。
- 何时用（L16391-16403）：①重复发生的问题——如多台应用服务器日志格式不同但数据要素相同（"终结符表达式都是相同的，但是非终结符表达式就需要制定了"），"可以通过程序来一劳永逸地解决"；②一个简单语法需要解释的场景——"一般用来解析比较标准的字符集，例如SQL语法分析"，但"该部分逐渐被专用工具所取代"；特定商业环境（模型运算等）也会采用。
- 何时不用（L16397-16408）：文法复杂时——"文法规则越多，复杂度越高，而且类间还要进行递归调用"，排查问题需要极大耐心；重要模块（"否则维护会是一个很大的问题"）；效率敏感场合。

**③ 不用时的做法、反例、缺点/代价**
- 直接计算法（L16037-16045）：为每个业务品种写一个算法、不建公式——3 个品种尚可接受，上百个品种无法维护，且完全无法满足"公式运行时可编辑"的设计要求。
- 模式自身缺点（L16376-16390）：①引起类膨胀——"每个语法都要产生一个非终结符表达式，语法规则比较复杂时，就可能产生大量的类文件，为维护带来了非常多的麻烦"；②采用递归调用方法——要知道最终结果"必须一层一层地剥茧"，排查一个语法错误"要一个一个断点地调试下去，直到最小的语法单元"，调试非常复杂；③效率问题——"由于使用了大量的循环和递归，效率是一个不容忽视的问题，特别是用于解析复杂、冗长的语法时，效率是难以忍受的"。
- 替代方案（L16404-16416）："在项目中可以使用shell、JRuby、Groovy等脚本语言来代替解释器模式，弥补Java编译型语言的不足"；或直接采用 Expression4J、MESP、Jep 等开源解析工具包，"自己没有必要从头开始编写解释器"。

**④ 论据**
- 两类元素（L16054-16060）：公式中仅有两类元素——运算元素（a、b、c 等需具体赋值的对象）即终结符号，"这是语法中最小的单元逻辑，不可再拆分"；运算符号即非终结符号，每个都要对应处理单元。共同点是都要被解析；不同点是运算元素功能相同可用一个类表示，运算符号需分别解释（加法要加法解析器，减法要减法解析器）。
- 递归组合（L16154-16156, L16328-16329, L16348-16354）：每个运算符号"只和自己左右两个数字有关系，但左右两个数字有可能也是一个解析的结果"，无论何种类型都是 Expression 的实现类，故非终结符子类用构造函数传递左右两个表达式；"抽象表达式是生成语法集合（也叫做语法树）的关键……它是通过递归调用的方式，最终由最小的语法单元进行解析完成"；"每个文法规则都只关心自己周边的文法规则的结果（注意是结果）"，终结符表达式"不能够再参与比自己更小的文法运算了"。
- 栈控顺序（L16224-16230）：Calculator 构造函数把表达式转为 char 数组逐字符判断——遇运算符则弹出栈顶作 left、游标 ++ 取右操作数，组合成新表达式压回栈；以 a+b-c 为例完整演算了弹栈-组合-压栈过程，用栈"安排运算的先后顺序"（加减法不用考虑，但乘除法必须考虑，为扩展留路）。
- 运行时公式（L16282-16285）："公式是在运行时定义的，而不是在运行前就制定好的"，先公式后赋值再出结果，"是不是类似于初中学过的'代数'这门课"。
- 扩展性（L16286-16288, L16373-16374）："若需要扩展也非常容易，只要增加SymbolExpression的子类就可以了，这就是解释器模式"；优点即扩展性——"修改语法规则只要修改相应的非终结符表达式就可以了，若扩展语法，则只要增加非终结符类就可以了"。
- 四个通用角色（L16303-16321）：AbstractExpression 抽象解释器，具体解释任务由实现类完成；TerminalExpression 终结符表达式——"通常一个解释器模式中只有一个终结符表达式，但有多个实例，对应不同的终结符"（例中即 VarExpression，表达式中的每个终结符都在栈中产生一个对象）；NonterminalExpression 非终结符表达式——"原则上每个文法规则都对应一个非终结符表达式"（例中即 Add/SubExpression）；Context 环境角色（例中用 HashMap 代替）。
- 封装（L16080-16081, L16369-16370）：Calculator 的作用是封装，"根据迪米特法则，Client只与直接的朋友Calculator交流，与其他类没关系"；通用结构中 Client 通常也是封装类——"传递进来一个规范语法文件，解析器分析后产生结果并返回，避免了调用者与语法解析器的耦合关系"。

**⑤ 最佳实践/作者忠告**
- "尽量不要在重要的模块中使用解释器模式，否则维护会是一个很大的问题"；可用 shell、JRuby、Groovy 等脚本语言替代——作者在一个银行分析型项目中就采用 JRuby 进行运算处理，"避免使用解释器模式的四则运算，效率和性能各方面表现良好"（L16404-16408）。
- 解释器模式在实际系统开发中"使用得非常少"，一般在大中型框架型项目（数据分析工具、报表设计工具、科学计算工具等）能找到它的身影；确实遇到"一种特定类型的问题发生的频率足够高"的情况要用时，先考虑 Expression4J、MESP、Jep 等开源解析工具包——"功能都异常强大，而且非常容易使用，效率也还不错"（L16409-16415）。
- 金句收尾："有人已经建立了一条康庄大道，何必再走自己的泥泞小路呢？"（L16416）

**补充（模式间对比与代码示例）**
- 与六大原则的关联：Calculator 封装层的存在理由直接引自迪米特法则——Client 只与直接朋友交流（L16080-16081）；通用 Client 封装类同样是为"避免调用者与语法解析器的耦合关系"（L16369-16370）。
- 结构本质：抽象表达式经递归调用生成语法树，非终结符表达式只关心左右子表达式的"结果"而非过程（L16348-16350）——逐层委托、最小语法单元收口，是解释器模式递归结构的要害。
- 代码示例一句话概括：27-1~27-7 演示加减法公式解释器（Expression 抽象类仅一个 interpreter 方法、VarExpression 从 map 取 key 对应值、SymbolExpression 抽象持有 left/right、Add/SubExpression 递归解释左右表达式、Calculator 用 Stack 边解析边组装语法树、Client 从键盘读公式并逐个参数赋值后运行）；27-8~27-11 演示通用源码（抽象/终结符/非终结符表达式三分 + Client 封装类，非终结符构造函数接收多个依赖表达式）。

## 第28章 享元模式（Flyweight Pattern）｜L16419-17065

**① 模式意图**

使用共享技术有效地支持大量的细粒度对象——享元模式是池技术的重要实现方式（定义原文：Use sharing to support large numbers of fine-grained objects efficiently，L16680-16683）。

**② 使用场景与触发条件**

- 引子：全国开放的报考系统只运行3天、两天宕机4次，厂商定位为 OutOfMemory 且无内存泄漏，属"对象太多"型溢出——内存由800MB飙升至1.4GB，仅 SignInfo 类对象就占400MB（L16421-16445, L16534-16543）
- 触发条件（作者的诊断思路）：内存溢出只有两种可能——内存泄漏或对象太多；"既然已经定位是内存中对象太多，那就应该想到使用一种共享的技术减少对象数量"；几十万 SignInfo 对象中考试科目仅4个、考试地点30多个，相同属性可提取共享、不同属性在系统内赋值（L16431-16436, L16544-16568）
- 何时用（L16809-16815）：①系统中存在大量的相似对象；②细粒度对象都具备较接近的外部状态，而且内部状态与环境无关，即对象没有特定身份；③需要缓冲池的场景
- 何时不用/慎用（由缺点与扩展反推）：外部状态无法固化、会随内部状态改变时用之将致逻辑混乱（L16807-16808）；享元对象设得过少（如仅按科目分池）会引发线程不安全（L16890-16895）

**③ 不用时的做法、反例、缺点/代价**

- 不用时的做法与反例：报考系统原实现是"很标准的工厂方法模式"（在框架下编程必须有对象工厂，Spring 也有），代码本身没有问题，但高并发下产生几万个 SignInfo 对象把内存耗尽（L16456-16471, L16534-16537）
- 曾考虑的替代：引入对象池开源工具（如 Apache commons-pool），作者认为"暂时还用不到这种重量级的工具"，故自建轻量共享池，只需实现"容器定义"与"提供客户端访问的接口"两个功能（L16546-16556）
- 模式代价（L16805-16808）：提高了系统复杂性——需要分离出外部状态和内部状态，而且外部状态具有固化特性，不应该随内部状态改变而改变，否则导致系统逻辑混乱
- 扩展风险——线程不安全：享元模式"有太大的几率发生线程不安全"；反例：把外部状态从"科目+地点"缩减为仅"科目"，池中只剩4个对象，多线程取得同一对象并各自修改属性，立刻出现"编号LiSi/考试地址ZhangSan"的不和谐数据（L16820-16890）
- 扩展风险——性能陷阱：用自编类作外部状态必须覆写 equals 和 hashCode，执行效率还低（作者："一半的效率"），"这种吃力不讨好的事情最好别做"（L17031-17035）

**④ 论据**

- 内外状态划分：内部状态（intrinsic）是可共享出来的信息，存储在享元对象内部且不随环境改变而改变（例中 id、postAddress 等动态附加信息）；外部状态（extrinsic）是对象得以依赖的一个标记，随环境改变、不可共享（例中"考试科目+考试地点"复合字符串，是一批对象的统一标识、唯一索引值）（L16686-16698）
- 池的构造标准：一个 key 值唯一对应池中一个对象；"池中的对象生命周期是由池容器决定，而不是由使用者决定的"（L16609-16612）
- 为何用带 key 的子类而非新建含 subject/location 的类：①修改的工作量太大——新类由谁来创建、SignInfo 类是否也要改，两段相同的 POJO 程序不能并存于同一模块；②性能问题（28.4.2 展开）（L16613-16617）
- 实际效果：改造后内存中最多120个 SignInfo 对象（4科目×30地点），"相比之前几万个 SignInfo 对象优化了非常多"；第三天系统运行非常稳定，CPU 占用率下降，此后再未出现类似问题（L16673-16679）
- 变更控制：SignInfo4Pool 只在工厂方法中使用，"尽量缩小变更引起的风险"，调用方只需在展示层拼一个字符串传给工厂方法（L16675-16677）
- 通用角色四分（L16710-16721）：Flyweight 抽象享元角色——产品的抽象类，定义出外部状态和内部状态的接口或实现；ConcreteFlyweight 具体享元角色——实现业务，内部状态处理应与环境无关，"不应该出现一个操作改变了内部状态，同时修改了外部状态，这是绝对不允许的"；unsharedConcreteFlyweight 不可共享的享元角色——不存在外部状态或安全要求（如线程安全）不能使用共享技术，一般不会出现在享元工厂中；FlyweightFactory 享元工厂——构造一个池容器，同时提供从池中获得对象的方法
- final 保护外部状态：抽象享元对外部状态加 final，"获得了一个外部状态，然后无意修改了一下，池就混乱了"（L16773-16778）
- 线程安全应对：没什么可参考的标准，"只有依靠经验，在需要的地方考虑一下线程安全，在大部分的场景下都不用考虑"；使用时"对象池中的享元对象尽量多，多到足够满足业务为止"（L16892-16895）
- equals/hashCode：把对象作为 Map 的键值一定要重写两方法，"否则会出现通过键值搜索失败的情况，例如 map.get(object)、map.contains(object) 等会返回失败的结果"（L16956-16960）

**⑤ 最佳实践/作者忠告**

- 外部状态最好以 Java 基本类型作为标志（String、int 等），可大幅提升效率；自编类作外部状态吃力不讨好（L17033-17035）
- 确认只需要一次赋值的属性则设置为 final，避免无意修改导致逻辑混乱，特别是 Session 级的常量或变量（L16779-16780）
- 不要有删除投产代码的念头：确实不再使用的方法/类加 @Deprecated 注解，保持历史原貌、有助于版本向下兼容，特别是产品级研发（L16644-16646）
- 命名溯源：Flyweight 是拳击"特轻量级"（51公斤级）专有名词，寓意类要轻量级、粒度要小；"粒度小了，带来的问题就是对象太多，那就用共享技术来解决"（L17037-17043）
- 设计哲学：多使用细粒度的对象，便于重用或重构（L16722-16723）

**补充（模式间对比与代码示例）**

- 与工厂方法模式的关系：报考系统原架构即工厂方法模式（表现层经对象工厂创建对象，传递给业务层和持久层）；享元改造不动原结构，仅在工厂类上增加 HashMap 池容器、产品上增加带 key 的子类 SignInfo4Pool（L16458-16471, L16569-16583）
- 与对象池（Object Pool）的区别：对象池着重在对象的复用，池中每个对象是可替换的，同一池中取得 A 对象与 B 对象对客户端完全相同；享元模式着重解决对象的共享问题，关注如何建立多个可共享的细粒度对象（L17062-17065）
- Java API 佐证：String 的 intern() 方法即享元应用——对象池中有该类型的值则直接返回池中对象，故 (str1+str2).intern() 后与池中字符串做 == 比较为 true（L17044-17061）
- 代码示例一句话概括：28-1~28-3（L16472-16533）演示报考系统原始工厂方法实现（SignInfo 四属性 POJO + 简单对象工厂 + 场景类）；28-4~28-6（L16585-16664）演示带对象池改造（SignInfo4Pool 子类携带 key、工厂用 HashMap 判存则建池否则直取、预初始化4科目×30地点后调用直接命中池）；28-7~28-9（L16724-16802）演示通用源码（抽象享元以 final 接收外部状态、具体享元按外部状态处理业务、享元工厂 HashMap 池）；28-10~28-12（L16827-16884）演示线程不安全反例（以科目为 key 池中仅4对象，while(true) 交替 setId/setLocation 启动多线程，MultiThread 检测 id≠location 即报警）；28-13~28-16（L16919-17028）演示性能对比（ExtrinsicState 类覆写 equals/hashCode 作 key 执行100万次172ms，String 拼接 key 仅78ms）；28-17（L17046-17059）演示 String intern() 的享元现象。
