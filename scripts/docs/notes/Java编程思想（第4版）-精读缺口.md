## 三、真缺口

### 1. 显式资源清理（不依赖 GC/finalizer，覆盖所有路径）

**书中依据**：5.5.2「你必须实施清理」（PDF 124，L7070–L7085）「记住，无论是"垃圾回收"还是"终结"，都不保证一定会发生」；18 章「唯一安全的方式就是对文件显式地调用 close()」（PDF 576，L33300）；「在任何打开文件的代码在 finally 子句中，作为防卫措施都添加了对文件的 close() 调用」（PDF 583，L33677）；21 章「对 lock() 的调用，你必须放置在 finally 子句中带有 unlock() 的 try-finally 语句中」（PDF 715，L41298）。

**论据**：Java 的 GC/finalize 不保证发生，不能当析构函数用；除内存之外的资源（文件、连接、锁）必须显式释放；释放要覆盖所有路径（含异常 / 提前返回），用 finally / try-with-resources 兜底。

**建议落点**：`conventions/coding-tables.md` §2 C19 增补一句（最小 diff，不新增编号）：

> 释放必须显式（close/release），且覆盖所有路径（含异常 / 提前返回），不依赖 GC/finalizer 隐式清理。

**与最相近现有条目的区别**：C19 现文管「资源获取与释放在同一抽象层次、由获取方释放」，不含「显式 vs 隐式（GC/finalizer）」与「覆盖所有路径（含异常）」两个维度。

## 四、重点候选裁定（防后人重复发现）

1. **OOP 三/四特征（抽象/封装/继承/多态）不另立。** T1/T3/T4/C27 已承载；再加会变成口号。
2. **组合优于继承不另立。** C27 已承载（复用走组合 / 依赖 / 聚集）。
3. **异常快速失败不另立。** T8/C7 已承载。
4. **死锁避免不另立。** T10 已落（锁排序），本书 21.6 哲学家就餐是同一结论。
5. **构造器不调用可覆写方法不另立。** C32 已承载。
6. **初始化位置决定生命周期不另立。** T14 已落（HTDP）。
7. **终结条件（finalize 校验对象状态）不落。** 依赖 finalize 本身就是反模式（书引 Bloch「避免使用终结函数」），且 Java 特有。
8. **内部类 / 闭包 / 回调 / 多重实现继承不落。** Java 语言机制，非通用工程原则。
9. **泛型 / 反射 / 注解 / 枚举 / GUI / 并发类库不落。** 语言 / 类库事实。
