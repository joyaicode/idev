# 排查闭环（通用真源）

分析、论证、推测都只是待证命题，**必须带辅助证据**。没有用例、没有证据、没有复现，就不能定性，更不能编码。  
复杂问题可并行多个 Agent，但不能用「另一个 Agent 猜过了」代替证据。红绿走 idev verify 模块。

任何产品仓**不要再写一份**本页正文；只许指针。

## 证据怎么用

| 材料 | 可信度 | 怎么用 |
|------|--------|--------|
| AI 反馈 | **不可信** | 只当待证命题，不能当证据 |
| 文档 | **不可信** | 只当线索；和代码或现象打架时以可运行证据为准 |
| 代码 | **代码逻辑可信** | 读懂实际行为；仍须用例证明就是用户那条现象的根因 |

**每一步先设计用例并证明，通过后才决定推导的下一步。** 证明失败则反思（环境 / 产物 / 证据是否覆盖原现象），换命题，不写结论、不改代码。反复直到根因。

## 禁止

- 把「看起来像」「应该是」「刷新就好」写成结论
- 未确认用户看的是哪套环境 / 哪份产物（本地 webpack、本机 jar、测试域名已发布包）就改代码或让用户验收
- 修失败后在原变更上叠补丁碰运气
- 只测主路径、不测影响面；口头推理当验收

## 闭环（必须按序；失败回到第 1 步）

### 1. 猜想 → 用例 + 证据 → 复现 → 反思

| 项 | 要求 |
|----|------|
| 用例 | 可运行、能红能绿，断言用户原现象，不是「进程没挂」 |
| 证据 | 请求/响应、日志、源码、部署物、环境与 URL、对照金样板；贴出实际输出 |
| 复现 | 在用户同一现象上至少红过一次 |

复现失败 = 猜想未成立：换命题，**不写结论**。

### 2. 根因层停

- 能解释用户看到的**全部**现象
- 能用用例红/绿切换（固定根因则红，去掉则绿）
- 修在产生该现象的那一层，不是下游症状

### 3. 根因上给方案，评估影响范围

写清改什么 / 不改什么；谁调用、谁契约、本地 vs 已发布。影响范围要可检验。

### 4. 先设计用例，再编码

1. **正确性**：根因修复后由红转绿  
2. **影响范围**：不该变的路径保持原行为  
3. **验收**：用户原现象消失（含实际环境与 URL）

### 5. 编码 → 立刻跑用例

不绿：回退本次变更 → 回到第 1 步。禁止在错误修复上打补丁。

**有界修复（可判定的红线，命中立刻停）：** 满足任一即**强制停止叠改、升级人工决策**，不许继续碰运气——

- 相同**失败签名**连续出现 3 次
- 连续 2 次修改无有效代码变化（或语义与历史提案等价）
- 单条根因修复反复超过 ~15 分钟仍红

失败签名 = `[异常类型] [失败用例] [归一化错误信息]`（去掉行号/时间戳/临时路径后比较）。每轮修复记一句：`失败签名 | 代码变化量 | 与上轮是否语义不同 | 决策(继续/升级)`。升级时把三条红线中命中的哪条写清，交人决策，不静默再试。

### 6. 纵向验收

从发现层走到根因层（UI / Network / 网关 / OpenAPI / DAO / 部署物）再验一遍。

### 7. 收尾

反思哪条证据本该更早拿到；扫同类缺陷；未修的在当前票目录另开 issue（仓库已有债务目录时写那里），不假装已修，不为此新建目录。

## 反例

用户在测试环境上看旧包缺字段。只改本机源码并说「刷新就能看到」= 闭环未开始。
