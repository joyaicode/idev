# CANON：编码与架构执行规范（Agent 版）

关键词按 RFC 2119：**MUST**=必须，**MUST NOT**=禁止，**SHOULD**=默认应做，偏离须在记录里写理由。
本页是**规范，不是建议**。人类读者请看每条的 `WHY`，Agent 只需执行 `TRIGGER → DO → RECORD`。

## 0. 定位与优先级

- 层级：产品仓契约 > 本页 (T/A) > [coding.md](coding.md) (P/C/R) > 个人偏好。冲突时按此顺序取胜。
- 本页是 P/C/R 的上游：**先用本页判断“该不该做这件事、做在哪一层”，再用 P/C/R 决定“这一行怎么写”。**
- 编号真源：`T1`–`T12`（原则）、`A1`–`A8`（架构出门）、`F1`–`F7`（失败模式）只认本页。MUST NOT 另造码表或严重度。
- 证据规则不被本页替代：AI 输出与文档不可信，见 [evidence.md](evidence.md)。
- 本页不是门禁脚本。`check-feature` 不检查它；执行由 Agent 自觉、`review.md` 记账、人签字核对。

## 1. 何时加载 / 怎么用（执行协议）

**加载条件（满足任一即读 §3 命中表）：**
1. 当前阶段是 `arch`；
2. 你的计划或 diff 出现 §2 的任何**可观察信号**；
3. 你产生了 §3 触发表里的“念头”；
4. 被要求做 Review。

**协议（按序执行，不得跳步）：**
1. **DECLARE**：用一句话写出本轮变化及类型：`structure`（只改结构）/ `behavior`（改可观察行为）/ `both`（禁止，拆成两轮）。
2. **SCAN**：用 §2 信号扫 diff/计划，用 §3 扫念头。每命中一条，记下 `T#`。
3. **DO**：按命中条的 `DO` 做完，再继续写下一处。零命中则写最直白的实现，MUST NOT 为对称、美观或“以后可能用”添加抽象。
4. **RECORD**：按 §7 模板写入 `review.md`（或 `arch` 说明）。零命中也要写“已扫，无命中”。
5. **DESCEND**：命中后仍需按 [coding.md](coding.md) §0 用 P/C/R 落到具体代码纠正。

**停止条件**：命中条写了 `ESCALATE` 时，MUST 停止实现并按该条处理（自动唤起 grilling 或标 `UNPROVEN`），MUST NOT 自行拍板。

| 信号 | 命中 |
|------|------|

| 新增顶层目录、模块、服务、独立进程 | T1 T4 T12 |
| 新增依赖（`pom.xml`、`package.json`、`go.mod` 有增项） | T4 T12 |

| 新增 cache / 索引 / 冗余字段 / 派生表 | T10 T9 |

| 新增 `catch` 后 return 空值 / `false` / 吞异常；或 `x == null` 分支当成功 | T8 |

| 新增跨服务调用链 A→B→C 且要求整体一致 | T10 |

## 3. 规则（T1–T12）

每条格式：`TRIGGER` 触发 · `DO` 必须做 · `DON'T` 禁止 · `RECORD` 记什么 · `ESCALATE` 何时停 · `WHY` 一句话。

### T1 先砍偶然复杂度
- **TRIGGER**：§2 中新增层 / 服务 / 配置 / 抽象；念头“拆一下”“做成通用”“加个开关”“先留好扩展点”。
- **DO**：写出本质问题一句话；列出这次新增的每个抽象/配置及其**现有的**使用方；使用方 <1 则删除该抽象。
- **DON'T**：为未来需求预置扩展点；为“显得架构好”加层。
- **RECORD**：`T1: 本质问题=…；新增抽象=…；现有使用方=…；已删=…`
- **ESCALATE**：确有 2 个以上真实使用方但方案仍复杂 → 走 grilling。
- **WHY**：复杂度是唯一的敌人；每个新层都在借债。

### T2 概念完整性：先读后写
- **TRIGGER**：进入不熟悉的模块；念头“我按更好的方式写”“大家都这么写”。
- **DO**：写之前读该模块 ≥3 个已有实现，抽取它的命名、分层、错误处理、测试风格并沿用；确需偏离，写一句理由。
- **DON'T**：引入新风格；“顺便”重写一个更漂亮的版本。
- **RECORD**：`T2: 已沿用=…；偏离=…（理由）`
- **WHY**：系统应像一个人设计的；局部正确、全局漂移是 AI 的常见病。

### T3 深模块：接口小、内部厚
- **TRIGGER**：新增 interface/类；函数只转一手；暴露内部结构当 API。
- **DO**：公开面最小；调用方不必知道内部步骤顺序或下游协议；只有 1 种实现就写具体类型。
- **DON'T**：浅包装（改名转发）；`IXxx` 只有 1 个实现（对应 P6）；为测试暴露内部。
- **RECORD**：`T3: 公开面=…；隐藏的细节=…`
- **WHY**：信息隐藏让变化被限制在模块内。

### T4 依赖规则与边界
- **TRIGGER**：业务类 import 框架 / ORM / SDK / DTO；跨模块直接读对方内部；新增依赖。
- **DO**：画出依赖方向（`A → B` 表示 A 依赖 B），业务核心 MUST NOT 依赖框架与协议；跨上下文只走显式契约（接口 / 消息 / API）；新增依赖写清收益、替换成本、失败时怎么办。
- **DON'T**：Controller 里写业务；领域对象带 HTTP/ORM 注解；两个上下文共享一张表当接口。
- **RECORD**：`T4: 依赖方向=…；新增依赖=…（收益/替换成本/失败处理）`
- **WHY**：变化快的依赖变化慢的，反之即腐烂。

### T5 统一语言，命名即设计
- **TRIGGER**：同一概念多个名字；名字含 `util/helper/manager/data`；新增字段/接口名。
- **DO**：代码、契约、页面、文档用**同一字符串**；先在仓内 grep 现有词；做不出名字 = 职责不清，先拆再命名。
- **DON'T**：为“更好懂”发明第二套词；猜 API / 字段名（MUST 读源码或契约，见 evidence.md）。
- **RECORD**：`T5: 词表=概念→名字；已 grep=…`
- **WHY**：命名是最便宜、最持久的设计。

### T6 护栏先行，小步可逆，两顶帽子
- **TRIGGER**：改结构；触及面无测试；一个变更里既重构又加功能。
- **DO**：先补触及面测试钉住现有行为并转绿；每步可绿可回退；`structure` 与 `behavior` 分轮；断言取自契约或用户现象。
- **DON'T**：无测试大改；结构与行为混做；从实现反推断言（自证式测试）。
- **RECORD**：`T6: 本轮帽子=structure|behavior；护栏=测试名/verify case；回退方式=…`
- **ESCALATE**：无法补护栏 → 缩小步子；仍不行则停并标 `UNPROVEN`。
- **WHY**：没有护栏的改动不可信，也不可逆。

### T7 DRY 是知识单一来源
- **TRIGGER**：相同代码 / 字面量 / 校验第 2、3 次出现；念头“复制一份改改”“合成一个”。
- **DO**：先问“这两处变化的原因是否相同”；相同才抽，且第 3 次才抽；相反或不同的规则保持两份。
- **DON'T**：为少写几行合并语义相反的逻辑；第 2 次就上通用框架。
- **RECORD**：`T7: 重复点=…；变化原因相同?=是/否；处理=抽/保留`
- **WHY**：过早抽象比重复更贵。

### T8 快速失败，禁静默兜底
- **TRIGGER**：`catch` 后返回空值 / `false`；缺值当成功；请求期补默认值；念头“别影响主流程”。
- **DO**：非法输入立刻抛错或返回 4xx；`catch` 只处理你能处理的；默认值只写在显式配置里；确需降级，写明范围、日志与指标。
- **DON'T**：吞异常；返回 `{}`/`[]` 假装成功；请求期猜默认值。
- **RECORD**：`T8: 失败条件=…；降级(如有)=范围/日志/指标`
- **WHY**：静默兜底把错误推迟成更难查的错误。

### T9 先正确清晰，再度量再优化
- **TRIGGER**：任何“更快”“优化”“减少调用”的动机。
- **DO**：先选对数据结构与算法；写出基线数字、目标、测量方法；优化后再测并记录。
- **DON'T**：无基线的优化；用复杂度换假想的性能。
- **RECORD**：`T9: 基线=…；目标=…；结果=…`（无数字则不优化）
- **WHY**：直觉常错，度量才可信。

### T10 数据系统是权衡
- **TRIGGER**：cache / 索引 / 副本 / 队列 / 异步 / 重试 / 跨服务事务 / 并发。
- **DO**：写清五项——① 真相之源（哪个存储为准）② 派生与副本（如何生成、何时过期）③ 失败语义（重试是否幂等、顺序、至少/至多一次）④ 一致性等级（强 / 最终，谁能容忍多久）⑤ Schema 演进（如何兼容旧数据）。
- **DON'T**：双写不管一致性；无幂等的重试；无失效策略的缓存；隐式分布式事务；无界重试。
- **RECORD**：`T10: 真相之源=…；派生=…；失败语义=…；一致性=…；演进=…`
- **ESCALATE**：任一项答不出 → 标 `UNPROVEN`，走 grilling，MUST NOT 上线。
- **WHY**：数据系统的问题几乎都出在这五项没想清。

### T11 可运维性是架构特性
- **TRIGGER**：新增上线路径 / 定时任务 / 外部依赖调用 / 降级。
- **DO**：交付前具备：指标、结构化日志、告警条件、回滚路径、降级开关；先选简单方案。
- **DON'T**：只交功能不交观测；无回滚方案就上线。
- **RECORD**：`T11: 指标=…；日志=…；告警=…；回滚=…；降级=…`
- **WHY**：无法观测与回滚的系统，故障时无法恢复。

### T12 架构 = 有记录的权衡
- **TRIGGER**：任何方案选择、依赖引入、边界变更、契约变更。
- **DO**：记录决策、**至少一个被拒方案**、放弃了什么、后果、触发重审的条件；能写成可运行检查的约束写成检查（测试、脚本、lint）；决策变了，文档同轮更新。
- **DON'T**：只写结论；靠口头约定守架构；文档与代码分叉。
- **RECORD**：`T12: 决策=…；被拒=…；放弃=…；重审条件=…；检查=…`
- **WHY**：没有权衡记录的方案，下次只能重做一遍推理。

补充启发（不编号，审查时使用）：曳光弹（先打通最薄的一条真实链路再铺开）；Conway 定律（组织边界会长进系统边界，加 Agent/人不等于加速，先订死接口再并行）；破窗（发现坏味道当轮改或明确记账）；YAGNI。

## 4. 念头触发表（自查用，补充 §2 的信号）

| 你产生的念头 | 命中 | 动作 |
|--------------|------|------|
| 拆成微服务 / 拆库 | T1 T4 T12 | 写出：拆的是哪个变化原因；现有边界为何不够；新增的运维与一致性成本谁付。写不出 = 不拆 |
| 加缓存 / 索引 / 冗余字段 | T10 T9 | 给基线；写 T10 五项；无基线不加 |
| 加队列 / 异步 / 事件 | T10 T11 | 写顺序、重试、幂等、死信、观测；同步能满足则不异步 |
| 重试一下 | T10 T8 | 先确认幂等；限次数与退避；禁止无界重试 |
| 抽个通用平台 / 框架 | T1 T2 T7 | 数真实使用方；<3 个则写具体实现 |
| 旧的太乱，重写 | T2 T6 T12 | 先用测试钉旧行为；小步替换可回退；警惕第二系统效应 |
| 加配置开关，以后灵活 | T1 T8 | 每个开关是新分支和新测试面；无现有使用方不加 |
| 这个依赖很方便 | T4 T12 | 写收益、替换成本、失败处理；业务核心不直接依赖 |
| 加锁 / 并发 | T10 T11 | 先问能否不可变或单写者；补竞争条件测试 |
| A 调 B 再调 C，事务一起 | T10 T4 | 明确一致性等级；能补偿就补偿；避免隐式分布式事务 |
| 没出过事，先不管监控 | T11 | 缺项不出门 |
| 先上线，文档以后补 | T12 T5 | 决策与契约同轮更新 |
| 函数长但能跑 | T3 T5 | 说出它的“并且”，拆职责再命名 |
| 先复制一份改改 | T7 | 判断变化原因是否相同 |
| 先加 `if (空) 用默认` | T8 | 改为立刻抛错 |
| 接口先抽好以后换 | T1 T3 | 只有 1 种实现就写具体类型 |
| 没测试，改动很小 | T6 | 先补触及面测试 |
| 顺便整理下结构 | T6 | 换重构帽，加功能另轮 |
| 这样应该更快 | T9 | 要数字 |
| 我猜一下这个 API / 字段 | T5 T12 | 读源码 / 契约；不许猜 |
| 测试我自己写自己过 | T6 | 断言必须来自契约或用户现象 |
| 异常吞掉别影响主流程 | T8 T11 | 该失败就失败；确需降级按 T8 |
| 多开几个 Agent 就快了 | T1 T2 | 先订死任务边界与接口，再并行；估合并成本 |

每项 MUST 给出**具体内容**。答不出的项 MUST 标 `UNPROVEN` 并写“补证据的动作与责任人”，MUST NOT 写“无”或留空冒充完成。

| # | 必答 | 对应 |
|---|------|------|
| A1 | 本质问题（一句话）；已砍掉的偶然复杂度清单 | T1 |
| A2 | 依赖方向图（`A → B`）；业务核心不依赖什么；统一语言词表 | T3 T4 T5 |
| A3 | ≥1 个被拒方案；放弃了什么；回退路径 | T12 |
| A4 | 数据真相之源、派生 / 副本、失败语义、一致性等级、Schema 演进 | T10 |
| A5 | 最薄的一条真实链路（曳光弹）及先打通的顺序 | T2 T6 |

| A7 | 沿用了哪些现有做法；每个新抽象是否已有 ≥3 个使用方 | T2 T7 |

## 6. 失败模式（F1–F7，Agent 的已知系统性错误）

出现即视为拒过，MUST 当轮纠正。

| # | 模式 | 观察到 | 纠正 |
|---|------|--------|------|
| F1 | 模式堆砌 | 只有 1 个实现的 interface / 工厂 / 策略 / 事件 | T1 T3；写具体类型（P6） |
| F2 | 幻觉依赖 | 使用了没读过源码或契约的 API / 字段 / 配置 | T5 T12；先读源码再写 |
| F3 | 局部正确，全局漂移 | 每处对，风格与边界不一致 | T2 T4；对照现有实现纠偏 |
| F4 | 静默兜底 | 吞异常、返回空值当成功 | T8；改为立刻失败 |
| F5 | 自证式测试 | 断言从实现反推，永远绿 | T6；断言取自契约或用户现象 |
| F6 | 无护栏大改 | 大 diff、无测试、无回退 | T6；缩小步子，补护栏 |
| F7 | 只写 what 不写 why | 方案没有被拒选项与代价 | T12；补 A3 |

## 7. RECORD 模板（写入 `review.md` 或 `arch` 说明）

```
## 架构范式（canon）
- 本轮类型: structure | behavior
- 已扫: §2 信号 / §4 念头 / §6 失败模式
- 命中: T# … （每条附 §3 的 RECORD 一行）
- 零命中: 已扫，无命中
- A1–A8（仅 arch 阶段）: 已答 | UNPROVEN(补证据动作/责任人)
- 未决权衡: （有则已走 grilling / 无）
```

## 8. 自检（Agent 交付前逐条回答）

1. 我有没有先 DECLARE 本轮是 `structure` 还是 `behavior`，且没有 `both`？
2. §2 里的每个信号，我是否都扫了并记录命中或零命中？
3. 每个新增抽象、依赖、配置，是否有现有使用方和记录？
4. 我有没有猜 API / 字段 / 配置？（有 = F2）
5. 我有没有吞异常或补默认值？（有 = F4）
6. 断言是否来自契约或用户现象，而不是从实现反推？
7. A1–A8 里答不出的项，是否都标了 `UNPROVEN` 而不是留空？
8. 有权衡未决时，我是否停下来走了 grilling，而不是自行拍板？

任一项答“否”：当轮纠正后再交付。
