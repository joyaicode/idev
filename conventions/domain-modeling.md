# 领域建模 / 通用语言（公共规约一类）

由 `idev` 在 **arch 阶段涉及新领域概念 / 跨模块术语**时调起（可选透镜，不是每轮强制）。本目录不是独立 Skill。  
密封基线仍是尺；本页只回答「概念/术语怎么统一，边界怎么划」，不引入分数、不做通过率。

通用语言不一致 = **停下来对齐**，不猜、不各写一份。

## 术语表模板

术语表随票走（写进 `<票目录>/` 或 arch 方案里），不进 idev 核心、不进产品仓当第二份契约。

| 术语 | 同义词 | 定义 | 代码标识 |
|------|--------|------|----------|
| Order | 订单 / 交易 | 客户提交的一次购买请求 | `Order` |
| LineItem | 订单项 / 商品行 | 订单内单个商品条目 | `LineItem` |

代码标识、契约字段、UI 词必须用同一字符串（对齐 [coding-tables.md](coding-tables.md) C15）。

借入他域术语整义移植：连同源域定义一起进表。同名异物 = 假同源，按术语漂移同级拒过；要改义先登记新定义，必要时换词。

## 核心域与通用子领域（可检查）

- [ ] arch 方案识别核心域（CORE DOMAIN）与通用子领域（GENERIC SUBDOMAIN）：写清哪部分是自主开发的核心价值（竞争优势所在）、哪部分是支持性通用部分（无专有知识，可购买 / 外包 / 复用）；精力优先投入核心域，不为通用子领域开发「万能」模型

## 限界上下文（可检查）

- [ ] 划边界先问「这个上下文做什么用」（业务能力），再问「需要什么数据」；按数据切分起步 = 贫血 CRUD 服务
- [ ] 分包后无家可归的代码（哪都放不下的剩余部分）= 遗漏的限界上下文，具象化为新概念，不硬塞进现成包
- [ ] 多个上下文都要写同一份数据（如财务与仓库都写客户表）= 领域概念隐式建模在数据库里；把它具象化为代码概念 + API，不让共享表继续当接口
- [ ] 不同上下文的**同名概念**必须显式转换，不共用一个类跨界
- [ ] 跨上下文依赖只走接口 / 契约，不直接引用对方实体
- [ ] 上下文边界无循环依赖
- [ ] 上下文间关系显式选定一种模式（SHARED KERNEL / CUSTOMER-SUPPLIER / SEPARATE WAY / OPEN HOST SERVICE / ANTICORRUPTION LAYER）并写进 arch 方案；每个限界上下文有名称、进术语表
- [ ] 集成外部 / 遗留模型走防腐层：FACADE 严格按对方系统模型编写、不改其模型，转换器隔离双向转换；模型完整性优先于省转换成本

## 聚合根（可检查）

- [ ] 每个聚合恰好一个根实体，外部只经根访问内部
- [ ] 事务边界落在单个聚合内
- [ ] 跨聚合改动引入补偿 / 最终一致，不在一个事务里横跨多聚合
- [ ] 聚合不变量（固定规则）表述为断言：前置条件、后置条件、聚合整体的固定规则；语言不支持就写成自动单元测试（设前置 → 执行 → 查后置）

## 受约束数据定义（可检查）

- [ ] 同一非法输入分支（同一 null / 空串 / 负数 / 越界防御）在 ≥2 个消费函数重复出现 → 收窄数据定义使非法不可表示：构造即校验、类型收窄（非空类型 / 值对象 / 区间类型）、去掉宽松默认
- [ ] 校验只写在数据进入的那一层（构造 / 反序列化 / 入口），消费方拿到即合法，不再防御性分支

## 相等语义（可检查）

- [ ] 每个领域类型在契约里声明相等语义：**值相等**（两个实例字段相同即等价）还是**身份相等**（同一实体）
- [ ] 身份相等的类型禁止用值相等替代判定（Java 见 [java.md](java.md) Qodana 表 `==` / `equals` 行）；值对象实现值相等，实体按标识判定

## 通用语言反模式（拒过并拷问）

| 反模式 | 信号 | 处理 |
|--------|------|------|
| 术语漂移 | 代码术语与术语表不一致 | 拒过，改代码或改术语表对齐，不双语并存 |
| 一物多名 | 同一概念多个名字散落各处 | 统一到术语表一个词 |
| 跨界直引 | A 上下文直接 new / import B 的实体 | 改走接口；边界含糊先拷问，不默许 |
| 贫血跨聚合事务 | 一个事务改多个聚合 | 拆聚合 / 引补偿，事务收回单聚合 |
| 哑对象 | 新类型只有字段和 get/set，业务在外面铺开 | 按 [coding.md](coding.md) 底线 5，行为收回类型；协议形状除外 |
